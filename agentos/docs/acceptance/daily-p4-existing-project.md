# P4 已有项目验收

从固定提交的 AgentOS 源码创建隔离工作区，分别执行缺陷修复和功能迭代。每个场景都必须有独立评审、通过的验收命令、冻结候选预览和应用记录。两场景中至少一个须完成真实的要求修改、关联新 Run、重测和批准。单个场景直接获得独立批准时保留该结果，不补造返工记录。

计划声明分步交付时，初次实现按首轮范围提交，评审仍检查完整验收要求。角色配置分别提醒规划者保留该边界、实现者遵守首轮交付约束、评审者核对实际缺失的证据。后续实现只依据已记录的真实反馈返工；两场景都直接批准的运行保留为未覆盖返工验收的失败，不能通过修改收据补齐。

运行入口为 `node scripts/capture-existing-project-acceptance.mjs`，参数沿用原运行器。捕获器保存子进程的实际退出码、命令、时间、日志哈希以及原始收据哈希，随后使用 `--verify-receipt` 重新验证。运行器内部的通过状态和外部进程退出证据分别记录；没有外部退出记录的旧收据不能证明新门禁通过。

真实 Windows 模式使用本机操作者管理的官方 npm `@openai/codex` 安装。校验官方 wrapper 和 Windows 平台包的关联版本、CLI 版本、包元数据与可执行文件哈希，拒绝模拟夹具和任意同名 wrapper。此证据说明本机安装与运行身份，信任边界不包含恶意操作者替换整个安装目录，也不证明远端服务的模型权重。模型字段记录配置的模型，调用数记录实际启动的 Provider 会话。

真实调用还独立读取 Windows `OpenProcess/GetProcessTimes` 出生身份，与持久进程和会话逐一核对。候选正文和 manifest 内容哈希独立重算，命令结果、评审记录、预览请求和应用记录必须绑定同一候选。源码冻结检查同时拒绝未跟踪的构建输入；生成目录不作为项目源码。

真实计划的原始字节另存为 `plan/real-plan.json` 并记录 SHA-256。离线核验逐项比对标题、目标、范围、基线命令、验收命令和探针描述。基线探针必须是冻结提交中的已审核断言，绑定 Git blob、源码哈希和完整 argv；外部 TypeScript loader 同时绑定路径和文件哈希。任意打印失败标记或直接抛错的脚本不能替代实际缺陷复现。最终冻结候选在独立基线副本中叠加后，须用同一探针获得成功，探针正文仍保持原样。

任务创建后、确认执行前先核对实际保存的计划，离线审核再核对一次。服务端范围策略会排序路径，因此范围按精确、区分大小写且无重复的路径成员比较；不将合法排序误判为内容变更。增加、删除或替换范围路径，以及改变标题、目标或验收命令仍拒绝。原始计划及收据中的范围顺序保持原样，命令顺序必须一致。

模拟模式使用本地协议夹具，验证同一持久化、评审、预览和应用链路。模拟测试、真实 Windows 进程测试与远程 Provider 调用分别报告，历史 Lite 收据不修改。所有新验收指定完整 `--expected-sha` 并保存独立目录；最终发布以对应提交的完整 CI 和真实使用收据为准。

`--expected-sha` 绑定构建、启动并执行任务的 AgentOS 提交。被迭代的项目默认使用同一提交，也可通过显式 `--project-sha <完整提交>` 固定到该仓库中另一个真实提交；这使运行器的新版本能够重复同一已有项目场景。新收据分别保存运行器与项目的 commit/tree，基线探针、任务范围、候选基线和叠加后复测都绑定项目提交，Provider 与运行器进程退出仍绑定运行器提交。验证使用不同项目提交的收据时必须再次提供相同的 `--project-sha`，不能由收据自行选择项目，也不能将历史验收改称为当前版本验收。
