## 5. Owner-Approved Data Model (DDL PROPOSED)

All DDL below is PROPOSED / SUBJECT TO Step 3 Schema Review. No SQL or migration files are created by this plan. Filenames follow the existing TS migration pattern and remain PROPOSED; Step 3 may adjust them.

### `workflow_definitions` — proposed Migration `007-workflow-definitions` (APPROVED direction — OD-3)

- Columns (proposal): `id` (`wfdef_<ulid>`), `workspace_id` NULL for built-ins, `name` TEXT NOT NULL, `version` INTEGER NOT NULL, `definition_json` TEXT NOT NULL, `definition_hash` TEXT NOT NULL, `enabled` INTEGER NOT NULL DEFAULT 1, `archived_at` TEXT NULL, `created_at` TEXT NOT NULL
- Unique constraints: `UNIQUE(name, version)`; built-ins seeded under a reserved namespace (exact key shape PROPOSED)
- Immutability: Definition content is never modified in place; a content change inserts a new version row
- Built-in seed strategy (PROPOSED): `legacy-pipeline-v1` (four ordered stage keys matching the current fixed Legacy pipeline) and `unbound-task-run-v1` (empty stages); seeded idempotently by the migration or by a guarded store bootstrap — decided in Step 3
- Resolution rules (APPROVED — OD-3): Legacy Pipeline resolves to `legacy-pipeline-v1`; a v2 Run without Workflow selection resolves to `unbound-task-run-v1`
- REJECTED FOR M2.5: "Workflow Snapshot only without definition persistence" (OD-3); normalized stage-definition/edge tables (M3-scale); Workflow CRUD API (OD-12)

### `run_snapshots` — proposed Migration `008-run-snapshots` (APPROVED direction — OD-2)

- Columns (proposal): `id` (`rsnap_<ulid>`), `run_id` UNIQUE FK → `runs(id)` ON DELETE CASCADE, `workspace_id` FK → `workspaces(id)`, `snapshot_json` TEXT NOT NULL, `snapshot_schema_version` INTEGER NOT NULL, `content_hash` TEXT NOT NULL, `captured_at` TEXT NOT NULL, `source_agent_version` INTEGER, `source_provider_version` INTEGER, `source_workflow_version` INTEGER
- One snapshot per Task Run enforced by `UNIQUE(run_id)`
- Insert/read-only repository; no generic update; optional DB trigger rejecting UPDATE/DELETE (decide in P1 review)
- Snapshot JSON contains the complete Workflow value copy; a Definition reference cannot replace the Snapshot (OD-3)
- Existing Runs may have no row; no backfill (OD-11)
- REJECTED FOR M2.5 (OD-2): JSON columns on `runs`; generic `entity_snapshots`; normalized agent/provider/workflow snapshot tables

### `run_stages` — proposed Migration `009-run-stages` (APPROVED direction — OD-4)

- Columns (proposal): `id` (`rstage_<ulid>`), `run_id` FK → `runs(id)` ON DELETE CASCADE, `workspace_id`, `workflow_stage_key` TEXT (open string, no fixed union), `name` TEXT, `sequence` INTEGER, `attempt` INTEGER NOT NULL DEFAULT 1, `status` TEXT NOT NULL with CHECK allowing only `pending` at creation, `run_snapshot_id` FK → `run_snapshots(id)` (PROPOSED — maps each Stage to the same Run Snapshot; exact FK shape decided in Step 3 Schema Review), `created_at`, `updated_at`, `version` INTEGER NOT NULL DEFAULT 1
- Indexes: `(run_id, sequence)`; `UNIQUE(run_id, workflow_stage_key, attempt)`
- Materialization (APPROVED — OD-4): Legacy built-in Workflow creates four initial Stages; unbound Workflow creates zero Stages; inserted in the same transaction as Run + Snapshot (OD-8)
- REJECTED FOR M2.5 (OD-4): reusing/extending Conversation `run_steps`; any Stage transition API; execution/output/event linkage

## 6. Snapshot Capture Architecture

Approved single capture boundary (OD-5), names verified against current code; new components marked PROPOSED:

```text
Route (`v2Tasks.ts` POST /tasks/:taskId/runs)
Legacy Bridge (`routes/tasks.ts`)
  → TaskRunService (existing transaction owner)
      → WorkflowDefinitionResolver (PROPOSED — OD-3): legacy-pipeline-v1 / unbound-task-run-v1
      → SnapshotService (PROPOSED): resolve Agent/Provider/Workflow inputs,
        apply secret allowlist (OD-9), build canonical snapshot JSON + content hash
      → RunRepository.insert                 (existing)
      → RunSnapshotRepository.insert         (PROPOSED — OD-2)
      → RunStageRepository.insertMany        (PROPOSED — OD-4)
  → single runInTransaction commit (OD-8)
```

Coverage (APPROVED — OD-5): v2 initial; v2 retry; review-fix; provider-comparison; manual; Legacy initial; Legacy retry. Routes never compose repositories directly; Legacy find-or-create returning an existing Run does not backfill; startup recovery and terminal reconciliation create no Snapshot; repository unit tests may insert directly, but no production route bypasses the Service.

## 7. Immutability Model

- No update after insert: snapshot repositories expose `insert` and `findByRunId` only (OD-2); workflow definitions are versioned immutable rows (OD-3).
- Optional DB trigger rejecting UPDATE/DELETE on snapshot tables (decide at P1 review; SQLite trigger precedent exists in ownership code).
- `content_hash` computed over canonical JSON (stable key ordering) for corruption detection on read.
- `snapshot_schema_version` integer starting at 1; readers must tolerate older versions explicitly.
- Existing Runs without snapshots remain valid (`snapshotAvailable=false` per OD-11); no synthesis from current config is ever allowed.

## 8. Stage Lifecycle Boundary

- M2.5 owns (APPROVED — OD-4): persistence of initial stages (identity, open `workflow_stage_key`, `sequence`, `attempt=1`, initial status `pending` only, timestamps) in the creation transaction.
- M3 owns: stage execution lifecycle, status transitions, event linkage, output contracts (all in the OD-12 denylist for M2.5).
- Allowed initial status: exactly `pending` (APPROVED — OD-4); M2.5 never pretends lifecycle exists.
- attempt/sequence: attempt starts at 1; same-run stage retry semantics belong to M3 (02 §27), not M2.5.

## 9. API Draft (APPROVED — OD-10; field structure PROPOSED for Step 3 freeze)

- `GET /api/workspaces/:workspaceId/v2/runs/:runId` — existing shape plus additive metadata only: `snapshotAvailable: boolean`, `snapshotSchemaVersion: number | null`
- `GET /api/workspaces/:workspaceId/v2/runs/:runId?include=snapshot,stages` — opt-in expansion; `include` may contain `snapshot`, `stages`, or both; full snapshot payload follows OD-9; `contentHash` may be returned as metadata
- Unknown `include` value: 400 or existing API parse policy — frozen in Step 3
- Pre-M2.5 Runs (APPROVED — OD-11): `snapshotAvailable=false`, `snapshotSchemaVersion=null`, `snapshot=null`, `stages=[]`; full snapshot/stages fields appear only when requested via `include`
- REJECTED FOR M2.5: `GET /v2/runs/:runId/details` (removed); any new `/snapshot`, `/stages`, or `/details` endpoint; conditional GET or new ETag mechanism (Run version behavior unchanged)
- Error contract: existing `{ error, code }` + stable codes from OD-7 (`AGENT_NOT_AVAILABLE`, `PROVIDER_CONFIG_NOT_AVAILABLE`, `WORKFLOW_NOT_AVAILABLE`, `RUN_SNAPSHOT_FAILED`); responses sanitized

## 10. Compatibility Plan

- Legacy Pipeline: capture inside the Bridge creation transaction only; Legacy URLs, SSE frames, and `TaskItem` JSON are byte-frozen (OD-11).
- v2 queued Run: creation gains snapshot+stages atomically; status flow unchanged.
- Conversation Run: untouched end to end (OD-1); no Conversation response changes (OD-11).
- Existing rows: no synthesis, no backfill (OD-11); pre-M2.5 response shape per §9.
- Existing clients: additive fields/parameters only; GET/LIST shapes otherwise unchanged; apps/web untouched.
- Workspace scope: all snapshot/stage reads scoped by `workspace_id` exactly like current v2 reads.
- Invalid explicit bindings: fail closed per OD-7; explicit unbound configuration is allowed; binding null and broken binding are distinguished.

## 11. Migration Strategy

- Actual next Migration ID: `007` (registry 001–006 confirmed in `default-registry.ts`). The old `v006/v007` SQL naming is expired and not used.
- Proposed split (APPROVED direction; filenames PROPOSED, Step 3 may adjust):
  - `007-workflow-definitions` — table + built-in seed strategy (`legacy-pipeline-v1`, `unbound-task-run-v1`)
  - `008-run-snapshots` — one-to-one snapshot table
  - `009-run-stages` — stage table with Run (and proposed Snapshot) FK
- No Migration is created by this plan; the split exists to keep rollback granularity clean (definitions → snapshots → stages dependency order).
- Rules: additive only; backup before apply (existing runner behavior); single migration transaction; `integrity_check` and `foreign_key_check` after apply; rollback verified on fresh and legacy DBs; no silent synthesis; no raw secrets in any DDL or seed data.

## 14. Security and Privacy

- Secret references only (`secretProfileId`, `environmentProfileId`) plus the OD-9 non-sensitive allowlist (`providerType`, `runtimeMode`, `model`, `executable`, `capabilities`, validated args template, non-sensitive policy metadata).
- Forbidden in snapshots and API responses: raw secrets, tokens, API keys, cookies, Authorization headers, private keys, resolved env values, full env objects, unreviewed free-text commands, absolute working directories outside the Workspace, hidden chain-of-thought.
- Allowlist-first classification; template placeholders preserved per approved syntax; dangerous literals rejected or redacted; unclassifiable input fails closed; `redactionApplied` markers permitted.
- Repository and API layers each repeat no-leak validation; no-leak tests are a P3/P4 Exit Gate.
