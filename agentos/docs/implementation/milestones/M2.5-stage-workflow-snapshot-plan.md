## 6. Frozen Migration 007 — `workflow_definitions`

Migration name frozen: `007-workflow-definitions`. DDL frozen for P1 planning:

```sql
CREATE TABLE workflow_definitions (
  id TEXT PRIMARY KEY,
  definition_key TEXT NOT NULL,
  version INTEGER NOT NULL CHECK (version >= 1),
  name TEXT NOT NULL,
  definition_json TEXT NOT NULL CHECK (json_valid(definition_json)),
  definition_hash TEXT NOT NULL CHECK (length(definition_hash) = 64),
  enabled INTEGER NOT NULL DEFAULT 1 CHECK (enabled IN (0,1)),
  archived_at TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE(definition_key, version),
  CHECK (archived_at IS NULL OR enabled = 0)

```

Hash constraint: SHA-256, lowercase hex, 64 chars; DDL checks length; Repository/P1 tests verify the full hex format.

No `workspace_id` column: M2.5 persists only global built-in Definitions; Workspace-owned Workflow CRUD is excluded by OD-12; future Workspace-scoped Workflows arrive via a new Migration with explicit scope — no ambiguous nullable scope is pre-built.

Definition content is never modified in place. The only metadata ever allowed to change: `enabled`, `archived_at`, `updated_at`.

Planned DB trigger `workflow_definitions_immutable_content` blocks changes to: `definition_key`, `version`, `name`, `definition_json`, `definition_hash`, `created_at`. It does NOT block: `enabled`, `archived_at`, `updated_at`. No DELETE-blocking trigger is planned. M2.5 exposes no Workflow Repository update API; metadata updates exist only for direct-SQL fixtures and future capability.

## 8. Frozen Canonical JSON and Hash

P1 adds pure utility `apps/server/src/snapshots/canonicalJson.ts` with tests `apps/server/src/snapshots/canonicalJson.test.ts`. Frozen algorithm:

- Object keys sorted recursively by Unicode code-point lexical order
- Array order preserved; string/boolean/null preserved; numbers must be finite
- `undefined`/function/symbol/bigint rejected; circular references rejected
- Output has no insignificant whitespace; never relies on original object insertion order
- SHA-256 computed over the UTF-8 bytes of the canonical JSON; output lowercase 64-char hex

Consumers: Migration 007 built-in definition hashes; P3 Run Snapshot content hash; P2 Repository integrity verification.

## 9. Frozen Migration 008 — `run_snapshots`

Migration name frozen: `008-run-snapshots`. Step 1 of the migration adds the supporting unique index (current `runs` has only `UNIQUE(id, task_id)`):

```sql
CREATE UNIQUE INDEX idx_runs_id_workspace
  ON runs(id, workspace_id);

CREATE TABLE run_snapshots (
  id TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL,
  run_id TEXT NOT NULL,
  workflow_definition_id TEXT NOT NULL,
  snapshot_schema_version INTEGER NOT NULL CHECK (snapshot_schema_version >= 1),
  snapshot_json TEXT NOT NULL CHECK (json_valid(snapshot_json)),
  content_hash TEXT NOT NULL CHECK (length(content_hash) = 64),
  redaction_applied INTEGER NOT NULL DEFAULT 0 CHECK (redaction_applied IN (0,1)),
  captured_at TEXT NOT NULL,
  UNIQUE(run_id),
  UNIQUE(id, run_id),
  FOREIGN KEY (run_id, workspace_id)
    REFERENCES runs(id, workspace_id) ON DELETE CASCADE,
  FOREIGN KEY (workflow_definition_id)
    REFERENCES workflow_definitions(id) ON DELETE RESTRICT
);
```

Deleted from the earlier proposal: `source_agent_version`, `source_provider_version`, `source_workflow_version`. Rationale: one Workflow may bind multiple Stages, Agents, and Providers; version information must live inside the Snapshot JSON per binding (§11).

Immutability: trigger `run_snapshots_reject_update` blocks UPDATE only. No DELETE trigger exists: deleting a Run must cascade `runs` → `run_snapshots` (ON DELETE CASCADE).

Repository surface: `insert`, `findByRunId`, `verifyHash`. No `update`, no `delete`, no `backfill`.

A pre-M2.5 Run without a snapshot row is a legal compatibility state. "Every new Run must have a Snapshot" is a `TaskRunService` production invariant, not a global DB NOT NULL constraint over historical `runs`.

## 10. Frozen Migration 009 — `run_stages`

Migration name frozen: `009-run-stages`. DDL frozen for P1 planning:

```sql
CREATE TABLE run_stages (
  id TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL,
  run_id TEXT NOT NULL,
  run_snapshot_id TEXT NOT NULL,
  workflow_stage_key TEXT NOT NULL,
  name TEXT NOT NULL,
  sequence INTEGER NOT NULL CHECK (sequence >= 1),
  attempt INTEGER NOT NULL DEFAULT 1 CHECK (attempt >= 1),
  status TEXT NOT NULL DEFAULT 'pending' CHECK (status = 'pending'),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  version INTEGER NOT NULL DEFAULT 1 CHECK (version >= 1),
  UNIQUE(run_id, sequence),
  UNIQUE(run_id, workflow_stage_key, attempt),
  UNIQUE(id, run_id),
  FOREIGN KEY (run_id, workspace_id)
    REFERENCES runs(id, workspace_id) ON DELETE CASCADE,
  FOREIGN KEY (run_snapshot_id, run_id)
    REFERENCES run_snapshots(id, run_id) ON DELETE CASCADE
);
```

The two composite FKs prove: the Stage's Workspace matches its Run's Workspace; the Stage's Snapshot belongs to the same Run — binding Run A's Stage to Run B's Snapshot is impossible at the DB level.

No RunStage UPDATE repository; no Stage transition; no Stage event; `run_steps` is not reused.

## 12. Capture/Execution Same-Resolution Rule (HIGH-1 closure)

`SnapshotService` does not merely return JSON. It produces a `ResolvedRunConfiguration` containing: the resolved Workflow Definition; the resolved Stage definitions; per-Stage resolved Agent Snapshot; per-Stage resolved Provider Snapshot; the canonical `RunSnapshotPayloadV1`; materializable RunStage drafts; and a Legacy execution projection (used only by the Legacy Pipeline).

The SAME `ResolvedRunConfiguration` drives all three consumers: (1) persisted Run Snapshot; (2) materialized initial RunStages; (3) Legacy Pipeline AgentRunner input. The Legacy AgentRunner class and its execution method remain unchanged.

Capture boundary coverage (OD-5, extended by Step 3): v2 initial; v2 retry; v2 resume-fallback; review-fix; provider-comparison; manual; Legacy initial; Legacy retry — every newly created Task-domain Run captures through the single boundary (`TaskRunService` transaction → `SnapshotService` → Run/Snapshot/Initial Stage repositories). Routes never compose repositories directly; startup recovery and terminal reconciliation create no Snapshot; pre-M2.5 existing Runs are not backfilled; repository unit tests may insert directly, but no production route bypasses the Service.

P3 permits one minimal internal modification to `apps/server/src/routes/tasks.ts` with a single purpose: accept the immutable Legacy execution projection returned by `TaskRunService` and pass it into the existing Runner factory — the Bridge no longer re-resolves Agent/Provider from mutable Workspace configuration after snapshot capture. P3 still forbids: changing Legacy URLs; changing SSE events; changing TaskItem JSON; changing AgentRunner internals; changing CLIExecutor; changing Provider Adapter execution; changing execution order.

Required consistency tests: snapshot Agent/Provider bindings exactly equal the bindings the Runner actually receives; mutating Workspace/Provider config after capture does not affect the already-created Runner projection; a later Retry builds a new projection from the latest configuration; the parent Snapshot is never modified.

## 15. Frozen Snapshot Transaction Flow

Order inside the `TaskRunService` transaction:

1. Validate Task and active-Run guards
2. Resolve Workflow Definition
3. Resolve/validate Agent and Provider bindings
4. Build `ResolvedRunConfiguration`
5. Insert Run
6. Finalize RunSnapshot payload with Run ID/root lineage
7. Insert RunSnapshot
8. Insert initial RunStages
9. Return Run plus immutable execution projection
10. Commit
11. Provider Process/AgentRunner may start only after the transaction returns successfully

Rules: Repository/JSON/hash operations only inside the transaction; no child process; no network; no CLI discovery; no Secret value reads; any failure rolls back everything; no compensation; no partial stages; no Run without Snapshot.

## 16. Frozen Error Mapping

v2 HTTP mapping: `AGENT_NOT_AVAILABLE` → 409; `PROVIDER_CONFIG_NOT_AVAILABLE` → 409; `WORKFLOW_NOT_AVAILABLE` → 409; `RUN_SNAPSHOT_FAILED` → 500. The external message for `RUN_SNAPSHOT_FAILED` is exactly `Run snapshot creation failed`. Never exposed: SQLite errors, paths, stacks, commands, args, secrets, hash inputs.

Legacy surface: Snapshot/binding capture errors add no new Legacy domain error shape; the Bridge returns the existing sanitized failure — HTTP 500 with body `{ "error": "Bridge persistence failed" }`. Full v2 snapshot error details are never returned on Legacy surfaces. Internal logs may record sanitized diagnostic codes, never secrets.

## 17. Frozen API Response Shape

Existing default response `GET /api/workspaces/:workspaceId/v2/runs/:runId`:

```json
{
  "run": { "...": "existing Run shape, unchanged" },
  "snapshotAvailable": true,
  "snapshotSchemaVersion": 1
}
```

Metadata lives at the response top level. The shared `Run` row shape is not modified to carry snapshot metadata. Without `include`: no `snapshot`, no `stages`, no `contentHash`, and no extra null/empty placeholders.

`include=snapshot`:

```json
{
  "run": { "...": "existing Run shape, unchanged" },
  "snapshotAvailable": true,
  "snapshotSchemaVersion": 1,
  "snapshot": "RunSnapshotPayloadV1 | null"
}
```

`include=stages`:

```json
{
  "run": { "...": "existing Run shape, unchanged" },
  "snapshotAvailable": true,
  "snapshotSchemaVersion": 1,
  "stages": ["RunStage"]
}
```

`include=snapshot,stages`: returns both `snapshot` and `stages` together.

Pre-M2.5 Runs: `snapshotAvailable=false`; `snapshotSchemaVersion=null`; `include=snapshot` → `snapshot=null`; `include=stages` → `stages=[]`. `contentHash` is returned only as snapshot metadata under `include=snapshot`; it is not exposed in the default response.

## 18. Frozen include Parse Policy

`include` is a single query string; case-sensitive; comma-separated; allowed tokens only `snapshot` and `stages`; each token trimmed; token order irrelevant; duplicate tokens allowed and deduplicated; repeated query-array form rejected; empty token rejected; unknown token rejected; bare `include=` rejected. Failures throw `V2ValidationError` → HTTP 400 with code `VALIDATION_FAILED`.

Examples: `include=snapshot` PASS; `include=stages` PASS; `include=snapshot,stages` PASS; `include=stages,snapshot` PASS; `include=snapshot,snapshot` PASS (deduplicated); `include=snapshot,` FAIL 400; `include=unknown` FAIL 400; `include[]=snapshot` FAIL 400.

## 20. Migration Strategy and Rollback Terminology (corrected)

Current `MigrationRunner` has NO down migration. Three distinct concepts:

A. Apply Failure Rollback — a failure inside a Migration's `BEGIN IMMEDIATE` transaction rolls back DDL, Seed, and the Migration record together; must be tested per migration.
B. Code/PR Rollback — reverting an unmerged implementation commit; does not touch any production DB.
C. Applied Schema Downgrade — NOT provided by M2.5; no "drop 009→008→007" claim; applied additive tables are managed by later Migrations; the runner does not support down.

Removed wording: "drop tables in reverse order"; "registry revert as runtime rollback"; "rollback 009 → 008 → 007".

Migration tests instead assert: 007 failure atomic rollback; 008 failure atomic rollback; 009 failure atomic rollback; no partial seed; no migration record on failure; retry after a corrected migration succeeds.

Other rules unchanged: additive only; backup before apply (existing runner behavior); single migration transaction; `integrity_check` and `foreign_key_check` after apply; no silent synthesis; no raw secrets in DDL or seed data. The old `v006/v007` SQL naming remains expired.
