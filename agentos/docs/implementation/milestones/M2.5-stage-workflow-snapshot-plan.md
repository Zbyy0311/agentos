## 5. Proposed Data Model Options

All options below are PROPOSED / SUBJECT TO OD-2, OD-3, OD-4. No SQL files are created by this plan.

### Option S1 — `run_snapshots` one-to-one table (recommended under OD-2-B)

- Tables: `run_snapshots`
- Columns (proposal): `id` (`rsnap_<ulid>`), `run_id` UNIQUE FK → `runs(id)` ON DELETE CASCADE, `workspace_id` FK → `workspaces(id)`, `snapshot_json` TEXT NOT NULL, `snapshot_schema_version` INTEGER NOT NULL, `content_hash` TEXT NOT NULL, `captured_at` TEXT NOT NULL, `source_agent_version` INTEGER, `source_provider_version` INTEGER, `source_workflow_version` INTEGER
- IDs: application-generated (matches 10 §3.6)
- FK: single FK to `runs`; workspace column duplicated for scoped queries (same pattern as `runs`)
- Unique constraints: `UNIQUE(run_id)` enforces one snapshot per Run
- Version: snapshot itself immutable; `snapshot_schema_version` governs payload evolution
- Immutable enforcement: repository exposes insert/read only; no generic update; optional DB trigger to reject UPDATE/DELETE (decide in P1 review)
- JSON validation: canonical serialization at capture; `content_hash` over canonical JSON (10 §92 pattern)
- Compatibility: pre-M2.5 Runs simply have no row (OD-11)
- Migration rollback: drop table (additive, no data migration)
- Query patterns: by `run_id` (details endpoint), by `workspace_id` + `captured_at` (future Inspector lists)

### Option S2 — JSON columns on `runs`

- Columns on `runs`: `snapshot_json`, `snapshot_schema_version`, `content_hash`
- Pros: no join. Cons: bloats hot Run row; weaker immutability story; couples schema evolution to the Run table. Not recommended.

### Option S3 — normalized snapshot tables (agent/provider/workflow)

- Separate `agent_snapshots`, `provider_config_snapshots`, `workflow_snapshots` with Run/Stage references (10 §93 pattern)
- Pros: dedup across Runs; stage-level references. Cons: 3× tables/joins for one read pattern; higher migration and review cost. Deferred unless Stage-level snapshot identity proves necessary (OD-4 review).

### Option W1 — Workflow Snapshot only (recommended under OD-3-C)

- No `workflow_definitions` table this round; the snapshot captures an immutable JSON rendering of the built-in pipeline definition (stage keys, order, agent bindings, retry policy, execution mode, definition version constant).
- Compatibility: zero CRUD surface; future Workflow Definition tables can adopt the same JSON shape.

### Option W2 — `workflow_definitions` single table (acceptable under OD-3-B)

- `workflow_definitions` (`id`, `workspace_id NULL` for built-ins, `name`, `version`, `definition_json`, `enabled`, `archived_at`, timestamps); updates insert new versions (immutable rows); Run references `definition_id` + captured version.
- Deferred unless Owner wants durable definitions now.

### Option ST1 — `run_stages` table (recommended under OD-4-B)

- Columns (proposal): `id` (`rstage_<ulid>`), `run_id` FK → `runs(id)` ON DELETE CASCADE, `workspace_id`, `workflow_stage_key` TEXT (open string, no union), `name` TEXT, `sequence` INTEGER, `attempt` INTEGER NOT NULL DEFAULT 1, `status` TEXT CHECK (minimal initial set, e.g. `pending` only at creation — lifecycle frozen in P1), `agent_snapshot_id`/`provider_snapshot_id` NULL (only if S3 adopted; otherwise omit), `started_at`, `completed_at`, `created_at`, `updated_at`, `version` INTEGER NOT NULL DEFAULT 1
- Indexes: `(run_id, sequence)`, `(run_id, workflow_stage_key, attempt)` unique, `(status)` optional
- Materialization: initial stages inserted in the same transaction as Run + Snapshot (OD-8)

## 6. Snapshot Capture Architecture

Candidate chain (names verified against current code; new components marked PROPOSED):

```text
Route (`v2Tasks.ts` POST /tasks/:taskId/runs)
Legacy Bridge (`routes/tasks.ts`)
  → TaskRunService (existing transaction owner)
      → SnapshotService (PROPOSED): resolve Agent/Provider/Workflow inputs,
        apply secret exclusion (OD-9), build canonical snapshot JSON + hash
      → RunRepository.insert           (existing)
      → RunSnapshotRepository.insert   (PROPOSED — OD-2)
      → RunStageRepository.insertMany  (PROPOSED — OD-4)
  → single runInTransaction commit (OD-8)
```

Capture inputs available today: `agent_profiles` (via `SqliteStore` join), `provider_configurations` (via `ProviderConfigurationRepository`), built-in pipeline definition (code). Inputs that do not exist today: canonical Workflow Definition (OD-3).

## 7. Immutability Model

- No update after insert: snapshot repositories expose `insert` and `findByRunId` only.
- Optional DB trigger rejecting UPDATE/DELETE on snapshot tables (decide at P1 review; SQLite trigger precedent exists in ownership tests).
- `content_hash` computed over canonical JSON (stable key ordering) for corruption detection on read.
- `snapshot_schema_version` integer starting at 1; readers must tolerate older versions explicitly.
- Existing Runs without snapshots remain valid (null/absent per OD-11); no synthesis from current config is ever allowed.

## 8. Stage Lifecycle Boundary

- M2.5 owns: persistence of initial stages (identity, key, sequence, attempt=1, initial status, timestamps) in the creation transaction.
- M3 owns: stage execution lifecycle, status transitions, event linkage, output contracts.
- Allowed initial statuses: frozen at P1 review; recommendation is exactly one (`pending`) so M2.5 never pretends lifecycle exists.
- attempt/sequence: attempt starts at 1; same-run stage retry semantics belong to M3 (02 §27), not M2.5.

## 9. API Draft

All endpoints PROPOSED / SUBJECT TO OD-10:

- `GET /v2/runs/:runId` — existing shape plus optional additive metadata: `snapshot: { present: boolean, schemaVersion?: number }` (no payload inline)
- `GET /v2/runs/:runId/details` — `{ run, snapshot: RunSnapshot | null, stages: RunStage[] }` (snapshot null for pre-M2.5 Runs per OD-11)
- Error contract: existing `{ error, code }` + new stable codes from OD-7 (`AGENT_NOT_AVAILABLE`, `PROVIDER_CONFIG_NOT_AVAILABLE`, `WORKFLOW_NOT_AVAILABLE`, `RUN_SNAPSHOT_FAILED`)
- Secret rule: snapshot payloads never contain secret values (OD-9); redaction covered by contract tests

## 10. Compatibility Plan

- Legacy Pipeline: capture inside the Bridge creation transaction only; Legacy URLs, SSE frames, and `TaskItem` JSON are byte-frozen.
- v2 queued Run: creation gains snapshot+stages atomically; status flow unchanged.
- Conversation Run: untouched end to end.
- Existing rows: snapshot absent/null; no backfill (OD-11/OD-12).
- Existing clients: additive fields only; GET/LIST shapes otherwise unchanged.
- Workspace scope: all snapshot/stage reads scoped by `workspace_id` exactly like current v2 reads.
- Archived configuration: behavior per OD-7; archived state is recordable, never silently resolved.

## 11. Migration Strategy

- Actual next Migration ID: `007` (registry 001–006 confirmed in `default-registry.ts`). The old `v006/v007` SQL naming is expired; new migration files follow the existing TS pattern (e.g. `007-<name>.ts`) after owner approval of contents.
- Rules: additive only; backup before apply (existing runner behavior); single migration transaction; `integrity_check` and `foreign_key_check` after apply; rollback verified on fresh and legacy DBs; no silent synthesis; no raw secrets in any DDL or seed data.
- Two candidate compositions (decide after OD-2/OD-3/OD-4):
  - M1 (minimal): `run_snapshots` + `run_stages` in one migration.
  - M2 (split): `007` snapshots, `008` stages — cleaner rollback granularity, one extra registry entry.

- Wrong Run Domain (writing snapshots to `agent_runs`) — mitigated by OD-1 + Drift Register.
- Stale old-plan assumptions (v006/v007, `run_steps` reuse) — mitigated by audit §12.
- Snapshot circular references — store value copies, not FK projections (M2 plan risk table).
- Large JSON payloads — canonicalization + size monitoring; normalized option S3 deferred.
- Immutable schema evolution — `snapshot_schema_version` discipline from day one.
- Partial transaction states — single-transaction rule (OD-8).
- Retry semantics confusion — explicit OD-6 decision + API copy later.
- Archived provider behavior — explicit OD-7 decision.
- Dual API confusion (v2 vs Conversation) — boundary section + frozen surfaces.
- Future M3 integration mismatch — stage model keeps lifecycle minimal and open-keyed.
