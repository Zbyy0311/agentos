## OD-1 — M2.6 Domain Scope

- Question: which aggregates does M2.6 cover?
- Option A: Task-domain v2 only
- Option B: Task-domain + Approval
- Option C: all mutable aggregates
- Current Evidence: Approval is in-memory (`ApprovalRegistry.ts`); Provider already has a complete version contract; Conversation is a separate frozen domain.
- Compatibility Impact: A/B leave Legacy/Conversation untouched; C would break the frozen-domain invariant.
- Security Impact: larger scope enlarges the no-leak review surface for stored results.
- Recommended Decision: **A** (Approval deferred to OD-17 as an explicit separate decision).
- Owner Status: PENDING OWNER DECISION

## OD-2 — Idempotent Operations

- Question: which operations accept idempotency keys?
- Candidates: Create Task, Create Run, Cancel Run, Accept Run, Cancel Task, Reopen Task, Resolve Approval, Grant/Revoke, Legacy Bridge.
- Current Evidence: Create Task duplicates on retry; Create Run replays as 409 `RUN_ACTIVE_EXISTS`; transitions replay as 409s; Legacy contract is frozen.
- Compatibility Impact: keys must be optional; existing callers unchanged.
- Security Impact: each included operation stores a replayable result — expands OD-13 review.
- Recommended Decision: include Create Task, Create Run, Cancel Run, Accept Run, Cancel Task, Reopen Task; exclude Resolve Approval / Grant/Revoke (pending OD-17) and Legacy Bridge (excluded by OD-3).
- Owner Status: PENDING OWNER DECISION

- Option A: fully excluded

- Current Evidence: Legacy URL/SSE/TaskItem JSON contract is frozen since M2.4/M2.5; Bridge already has explicit retry reconciliation.
- Compatibility Impact: any change risks breaking Legacy clients.
- Security Impact: none if excluded.
- Recommended Decision: **A — fully excluded**.
- Owner Status: PENDING OWNER DECISION

## OD-4 — Idempotency Input

- Question: how do clients supply the key?
- Option A: `Idempotency-Key` header only
- Option B: header + body
- Option C: body only
- Current Evidence: no parsing exists; v2 boundary uses explicit query/body validation already.
- Compatibility Impact: header-only is the industry convention and keeps bodies domain-pure.
- Security Impact: header keys must be validated before logging/storage (OD-19).
- Recommended Decision: **A — header only**.
- Owner Status: PENDING OWNER DECISION

## OD-5 — Key Validation

- Question: what is a legal key?
- Decisions needed: trim, min/max length, character policy, empty behavior, duplicate header behavior, header array behavior, user-credential-shaped content.
- Current Evidence: `parseV2RunInclude` shows the existing strict-parser pattern (reject empty/array/unknown).
- Compatibility Impact: strict rules must be documented; lenient normalization invites cross-caller collisions.
- Security Impact: reject empty, arrays, duplicates; forbid credential-shaped keys from being echoed or logged raw.
- Recommended Decision: trim; length 8–128; printable ASCII `[A-Za-z0-9._-]`; empty/duplicate/array → 400 `VALIDATION_FAILED`; keys never logged raw.
- Owner Status: PENDING OWNER DECISION

## OD-6 — Uniqueness Scope

- Question: what makes a key unique?
- Option A: key + operation
- Option B: workspace + key + operation
- Option C: owner + key + operation
- Current Evidence: all v2 aggregates are workspace-scoped; cross-workspace access returns 404 today.
- Compatibility Impact: B prevents cross-workspace replay/collision; A allows cross-workspace key clashes.
- Security Impact: B is required to prevent cross-workspace result disclosure.
- Recommended Decision: **B — workspace + key + operation**.
- Owner Status: PENDING OWNER DECISION

- Current Evidence: routes may evolve; stored records must remain interpretable.
- Compatibility Impact: vocabulary must be versioned/frozen once shipped.
- Security Impact: none.
- Recommended Decision: frozen keys `task.create`, `run.create`, `run.cancel`, `task.accept`, `task.cancel`, `task.reopen` (v1 suffix only if a breaking change ever ships).
- Owner Status: PENDING OWNER DECISION

## OD-8 — Request Fingerprint

- Question: how to detect same-key/different-request?
- Decisions: canonical JSON, SHA-256, participating fields, default normalization, header participation, workspace/path params participation.
- Current Evidence: M2.5 shipped `canonicalJson.ts` + SHA-256 hashing with frozen tests.
- Compatibility Impact: fingerprint inputs must be frozen; changing them invalidates stored records.
- Security Impact: hash only — never store raw request bodies (OD-19).
- Recommended Decision: canonical JSON + SHA-256 over { operation, workspaceId, path params, domain body fields with explicit defaults }; headers excluded.
- Owner Status: PENDING OWNER DECISION

## OD-9 — Same Key, Different Request

- Question: stable error for key reuse with a different fingerprint.
- Option A: `IDEMPOTENCY_KEY_REUSED`
- Option B: `IDEMPOTENCY_CONFLICT`
- Current Evidence: `V2_ERROR_STATUS` already maps domain codes to HTTP status; 409 is the established conflict status.
- Compatibility Impact: new code must be additive to the existing v2 error contract.
- Security Impact: message must not echo request content or fingerprints.
- Recommended Decision: `IDEMPOTENCY_KEY_REUSED` at HTTP 409 with safe message "Idempotency key was already used with a different request".
- Owner Status: PENDING OWNER DECISION

## OD-10 — Replay Response

- Question: what does a replay return?
- Decisions: original HTTP status retained, original body replayed in full, `Idempotency-Replayed: true` header, record ID exposure.
- Current Evidence: clients need deterministic results after network retries (Create Run currently loses the original Run reference).
- Compatibility Impact: replay must be byte-stable with the original response shape.
- Security Impact: do not expose internal record IDs; replayed bodies pass the same no-leak review as live responses.
- Recommended Decision: original status + original body replayed exactly; add `Idempotency-Replayed: true`; never expose record ID.
- Owner Status: PENDING OWNER DECISION

## OD-11 — Atomicity

- Question: must Idempotency Record + Domain Mutation commit in one `runInTransaction`?
- Analysis: lookup must precede the Active Run guard for `run.create` (else replay returns `RUN_ACTIVE_EXISTS`) and must precede state guards for cancel/accept/reopen (else replay returns transition conflicts).
- Current Evidence: `TaskRunService` already owns per-operation transactions; `Transaction.ts` is `BEGIN IMMEDIATE`.
- Compatibility Impact: none.
- Security Impact: partial commits would create orphaned claims or lost results.
- Recommended Decision: **yes — single transaction**: claim/lookup → guard → mutation → result store, atomically.
- Owner Status: PENDING OWNER DECISION

## OD-12 — Failure Semantics

- Question: which outcomes are cached, and what happens on rollback / concurrent same-key arrival?
- Decisions: validation failure cached? domain conflict cached? internal failure cached? claim retained after rollback? concurrent same-key wait/read behavior.
- Current Evidence: `RUN_ACTIVE_EXISTS` etc. are domain conflicts; unknown errors sanitize to 500 `INTERNAL_ERROR`.
- Compatibility Impact: caching failures changes what a retry sees.
- Security Impact: never cache internal failures (they may contain unsafe context); corrupted claims fail closed.
- Recommended Decision: cache validation failures and domain conflicts with their frozen responses; do not cache internal failures; rollback removes the claim; concurrent same-key requests serialize on the unique key and then replay the committed result.
- Owner Status: PENDING OWNER DECISION

## OD-13 — Result Storage

- Question: what is stored for replay?
- Option A: full `response_json`
- Option B: resource ID only, re-read on replay
- Option C: typed result envelope
- Analysis: A gives perfect fidelity but risks DTO drift and stale data; B always reflects current state but breaks replay fidelity (e.g. Task fields changed since); C freezes shape with an explicit schema and allows allowlisting.
- Current Evidence: M2.5 established explicit DTO allowlists as the no-leak pattern.
- Compatibility Impact: stored shape must be versioned (`resultSchemaVersion`).
- Security Impact: A risks storing fields later classified as sensitive; C supports allowlist enforcement.
- Recommended Decision: **C — typed result envelope** with schema version and explicit field allowlist per operation.
- Owner Status: PENDING OWNER DECISION

## OD-14 — Expiration and Retention

- Question: record lifetime.
- Option A: no `expiresAt`
- Option B: nullable `expiresAt`, no cleanup in M2.6
- Option C: fixed TTL with M2.6 cleanup
- Current Evidence: historical draft both included `expiresAt` and excluded expiration/cleanup — explicit conflict.
- Compatibility Impact: unbounded growth is acceptable for a local single-node app in the near term; TTL changes replay guarantees.
- Security Impact: retention of results extends the sensitivity window; cleanup is a background-job expansion.
- Recommended Decision: **B — nullable `expiresAt` column, no cleanup in M2.6**; retention policy deferred to a later milestone.
- Owner Status: PENDING OWNER DECISION

## OD-15 — Optimistic Concurrency API

- Question: does the v2 Task-domain API expose version control?
- Option A: no API change; internal guards only
- Option B: optional `expectedVersion`
- Option C: required `expectedVersion`
- Option D: HTTP `If-Match`
- Analysis: Cancel Run / Accept / Cancel Task / Reopen are natural read-modify-write operations where stale clients silently succeed today (first-writer-wins without detection). Provider API already proves the optional-body-field pattern; required would break existing callers.
- Compatibility Impact: B is additive; C breaks all current v2 callers; D requires header machinery inconsistent with the body-based v2 contract.
- Security Impact: none beyond existing error sanitization.
- Recommended Decision: **B — optional `expectedVersion`** on Accept/Cancel/Reopen/Cancel Run; absent preserves current behavior.
- Owner Status: PENDING OWNER DECISION

## OD-16 — Version Conflict Response

- Question: frozen conflict contract.
- Decisions: HTTP status, error code, safe message, return `currentVersion`?, leak internal entity info?
- Current Evidence: `VERSION_CONFLICT` already maps to 409 in the v2 boundary; Provider API returns `Version conflict: expected X, current Y`.
- Compatibility Impact: reusing the existing code keeps one contract.
- Security Impact: returning `currentVersion` leaks only an integer already visible via GET; entity internals must stay out.
- Recommended Decision: HTTP 409, code `VERSION_CONFLICT`, message "Version conflict"; include `currentVersion` integer, no other entity fields.
- Owner Status: PENDING OWNER DECISION

## OD-17 — Approval Boundary

- Question: does M2.6 touch Approval at all?
- Option A: defer Approval idempotency entirely
- Option B: persist the Approval aggregate first, then idempotency
- Option C: same-decision replay using the current in-memory Registry only
- Current Evidence: Registry is process-memory; restart loses everything; no transaction integration.
- Compatibility Impact: B is a new aggregate + migration; C gives no restart durability.
- Security Impact: persisted approvals enlarge the security review surface.
- Recommended Decision: **A — defer**; revisit as a separate milestone after Task-domain idempotency ships. No Approval persistence may be implemented without an explicit decision.
- Owner Status: PENDING OWNER DECISION

## OD-18 — Migration 010

- Question: schema for `idempotency_records`.
- Decisions: table name, columns, composite unique key, request hash, result schema, FK, workspace delete behavior, immutability, update/delete policy, index, ID prefix, rollback/backup policy.
- Current Evidence: M2.5 established the additive-migration + checksum-frozen pattern (007–009); registry tail is 009.
- Compatibility Impact: additive only; pre-M2.6 DBs must migrate cleanly.
- Security Impact: no raw request bodies; result envelope allowlist enforced at write.
- Recommended Decision: table `idempotency_records`; columns `id (idem_ prefix), workspace_id, operation, idempotency_key, request_hash CHAR(64), result_schema_version, result_json, http_status, created_at, expires_at NULL`; `UNIQUE(workspace_id, operation, idempotency_key)`; FK to workspaces with cascade delete; records immutable (no UPDATE API; UPDATE rejected by trigger like M2.5 snapshots); index on `(workspace_id, created_at)`; non-destructive migration, checksum-frozen, no backup requirement.
- Owner Status: PENDING OWNER DECISION

## OD-19 — Security and No-leak

- Question: no-leak rules for keys, results, and errors.
- Decisions: key written to logs?, `result_json` allowlist, error sanitization, raw request body prohibition, corrupted record fail-closed, cross-workspace isolation.
- Current Evidence: M2.5 shipped repository + API dual no-leak gates and safe error mapping.
- Compatibility Impact: none.
- Security Impact: this is the primary security boundary of M2.6.
- Recommended Decision: keys never logged raw (hash only if referenced); `result_json` limited to the typed envelope allowlist; error messages sanitized via the existing v2 boundary; raw request bodies never stored; corrupted/tampered records fail closed with `IDEMPOTENCY_RECORD_INVALID`; workspace isolation enforced by composite scoping and tested cross-workspace.
- Owner Status: PENDING OWNER DECISION
