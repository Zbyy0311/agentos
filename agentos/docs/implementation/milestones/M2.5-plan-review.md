## 4. Findings

### HIGH-1 — Snapshot and Legacy Execution Resolution Could Diverge

- Evidence: the Step 2 plan had `SnapshotService` "return JSON" while the Legacy Bridge resolves Agent/Provider independently — the Legacy AgentRunner resolves from `workspace.agents` / `AGENT_CONFIGS` (`packages/agent-core/src/runner.ts`), so a snapshot captured at T and a Runner configured at T+ε could bind different configurations.
- Impact: the persisted historical Snapshot could describe bindings other than the ones actually executed — the exact historical-fidelity failure M2.5 exists to prevent.
- Resolution: plan §12 freezes the same-resolution rule: `SnapshotService` produces a single `ResolvedRunConfiguration` (resolved Workflow Definition, Stage definitions, per-Stage Agent/Provider snapshots, canonical `RunSnapshotPayloadV1`, materializable RunStage drafts, Legacy execution projection) that drives (1) the persisted Snapshot, (2) the materialized initial RunStages, and (3) the Legacy AgentRunner input. P3 permits one minimal internal wiring change in `apps/server/src/routes/tasks.ts` to pass the immutable projection into the existing Runner factory; Legacy URL/SSE/TaskItem JSON, AgentRunner internals, CLIExecutor, Provider Adapter, and execution order are untouched. Binding-equality and post-capture-mutation consistency tests are required (plan §22 Service matrix).
- Status: RESOLVED
- Affected Package: P3

### MEDIUM-1 — `resume-fallback` Missing from Capture Matrix

- Evidence: `V2RunReason` includes `resume-fallback` (`packages/shared/src/types/index.ts`; DB CHECK in `006-runs-table.ts`), but the Step 2 capture path list and test matrix omitted it.
- Impact: a whole Run-reason class could have been created without a snapshot, breaking the OD-5 all-paths invariant.
- Resolution: plan §13 freezes that all six v2 reasons (`initial`, `retry`, `resume-fallback`, `review-fix`, `provider-comparison`, `manual`) resolve to `unbound-task-run-v1`; §22 Service matrix includes `v2 resume-fallback unbound` explicitly.
- Status: RESOLVED
- Affected Package: P3

### MEDIUM-2 — Snapshot Workspace Consistency Not Enforced

- Evidence: current `runs` has `UNIQUE(id, task_id)` but no `UNIQUE(id, workspace_id)` (`006-runs-table.ts`), so the Step 2 draft could not anchor a workspace-consistent snapshot FK.
- Impact: a snapshot row could reference a Run from another workspace, breaking workspace isolation at the DB level.
- Resolution: plan §9 freezes Migration 008 step 1 `CREATE UNIQUE INDEX idx_runs_id_workspace ON runs(id, workspace_id)` and the composite FK `(run_id, workspace_id) → runs(id, workspace_id) ON DELETE CASCADE`. §22 Migration 008 matrix includes `workspace mismatch rejected`.
- Status: RESOLVED
- Affected Package: P1

### MEDIUM-3 — Stage/Snapshot Same-Run Association Not Enforced

- Evidence: the Step 2 draft required "a Stage's snapshot binding must map to the same Run Snapshot" without a DB mechanism.
- Impact: Run A's Stage could be bound to Run B's Snapshot, corrupting history.
- Resolution: plan §10 freezes `UNIQUE(id, run_id)` on `run_snapshots` (008) and the composite FK `(run_snapshot_id, run_id) → run_snapshots(id, run_id) ON DELETE CASCADE` on `run_stages` (009), making cross-Run binding impossible at the DB level. §22 Migration 009 matrix includes `Snapshot from another Run rejected`.
- Status: RESOLVED
- Affected Package: P1

### MEDIUM-4 — Singular Source Version Columns Cannot Model Multi-stage Bindings

- Evidence: the Step 2 draft carried `source_agent_version`, `source_provider_version`, `source_workflow_version` columns on `run_snapshots`; a Workflow can bind multiple Stages, Agents, and Providers (Legacy pipeline binds four stages).
- Impact: single columns cannot represent per-stage binding versions; data model would silently lose fidelity.
- Resolution: plan §9 deletes the three columns; version information lives per-binding inside the Snapshot JSON (`WorkflowStageSnapshotV1.agent`/`provider` carry `version`, plan §11).
- Status: RESOLVED
- Affected Package: P1, P3

### MEDIUM-5 — Proposed ID Prefixes Do Not Match Identity Registry

- Evidence: the Step 2 draft used `wfdef_<ulid>`, `rsnap_<ulid>`, `rstage_<ulid>`; the Identity Registry (`apps/server/src/store/Identity.ts`) defines kinds `workflow` and `stage` but no `snapshot`.
- Impact: IDs would bypass the canonical generator/validator (`createEntityId`, `isValidEntityId`) and fragment the ID convention.
- Resolution: plan §5 freezes `workflow_<ulid>` (existing kind `workflow`), `stage_<ulid>` (existing kind `stage`), and `snapshot_<ulid>` (P1 adds `snapshot: 'snapshot'` to `ENTITY_ID_PREFIXES`); the three ad-hoc prefixes are REJECTED; P1 candidate files include `Identity.ts` and `Identity.test.ts`.
- Status: RESOLVED
- Affected Package: P1

### MEDIUM-6 — DELETE Immutability Trigger Conflicts with Cascade

- Evidence: the Step 2 draft floated a trigger rejecting UPDATE/DELETE on snapshot tables while `runs → run_snapshots` must cascade on Run delete (`006-runs-table.ts` already cascades workspace→runs).
- Impact: a DELETE-blocking trigger would break Run cascade deletion and trap orphan data.
- Resolution: plan §9 freezes `run_snapshots_reject_update` (UPDATE only) and explicitly plans NO DELETE trigger; §22 Migration 008 matrix includes `Run cascade delete works`; §22 Migration 009 matrix includes `Snapshot delete cascade does not block Run delete`.
- Status: RESOLVED
- Affected Package: P1

### MEDIUM-7 — Workflow Key, Version, Seed and Hash Ambiguous

- Evidence: the Step 2 draft named built-ins `legacy-pipeline-v1`/`unbound-task-run-v1` without key/version/ID/seed/hash definitions and left seeding ("migration or guarded store bootstrap") undecided; `MigrationRunner` provides single-transaction apply with checksums and records.
- Impact: ambiguous identity and seeding would make seeded rows non-deterministic and hashes unverifiable.
- Resolution: plan §6/§7/§8 freeze `definition_key` (`legacy-pipeline`, `unbound-task-run`), `version=1`, `name` (`legacy-pipeline-v1`, `unbound-task-run-v1`), exact IDs (`workflow_00000000000000000000000001` / `…0002`), migration-only seeding with plain INSERT (conflict rolls back; no `INSERT OR IGNORE`), exact Definition JSON V1 content and stage order, and SHA-256 over canonical JSON (64-char lowercase hex; DDL length check, full hex verified in tests).
- Status: RESOLVED
- Affected Package: P1

### MEDIUM-8 — API Response and Include Parsing Not Frozen

- Evidence: the Step 2 draft left "unknown include → 400 or existing parse policy — frozen in Step 3" open; current GET returns `{ run }` (`v2Runs.ts`) and `V2ValidationError` maps to HTTP 400 `VALIDATION_FAILED` (`v2Tasks.ts`).
- Impact: API ambiguity would leak into P4 implementation and client contracts.
- Resolution: plan §16/§17/§18 freeze: top-level `snapshotAvailable`/`snapshotSchemaVersion` metadata on the existing GET (shared `Run` row shape unchanged); `include=snapshot|stages` expansion shapes; pre-M2.5 null/empty semantics; `contentHash` only under `include=snapshot`; strict include parse policy (single string, case-sensitive, comma-separated, trim, dedupe, array form/empty token/unknown token/bare `include=` rejected) with `V2ValidationError` → 400 `VALIDATION_FAILED`; error mapping 409/409/409/500 with sanitized messages and Legacy `500 {"error":"Bridge persistence failed"}`.
- Status: RESOLVED
- Affected Package: P4

### MEDIUM-9 — Migration Rollback Terminology Incorrect

- Evidence: the Step 2 draft said "drop new tables in reverse order; registry revert" and "rollback (009 → 008 → 007)"; `MigrationRunner` has no down migration (forward-only `BEGIN IMMEDIATE` apply with records).
- Impact: promised a runtime capability that does not exist; rollback expectations would be untestable.
- Resolution: plan §20 distinguishes Apply Failure Rollback (in-transaction atomicity, tested), Code/PR Rollback (revert unmerged commits), and Applied Schema Downgrade (not provided); the three incorrect wordings are removed; migration tests now assert per-migration failure atomic rollback, no partial seed, no record on failure, and retry-after-fix success.
- Status: RESOLVED
- Affected Package: P1, documentation

### LOW-1 — Legacy Existing-Run Statement Inaccurate

- Evidence: the Step 2 documents said "Legacy find-or-create returning an existing Run does not backfill"; in fact `createLegacyRunForBridge` find-or-creates the canonical **Task** and always inserts a NEW Run when none is active (`TaskRunService.ts`), with recovery/reconciliation creating no Runs.
- Impact: misdescribed a production path and risked baking future idempotency behavior into current facts.
- Resolution: plan §14 records the corrected Legacy creation fact; the inaccurate sentence is removed; pre-M2.5 Runs remain un-backfilled by rule, not by a "returned existing Run" path.
- Status: RESOLVED
- Affected Package: documentation, P3

### LOW-2 — Package Dependency Wording Uses "Merged"

- Evidence: the Step 2 plan wrote package dependencies as "P1 merged" etc.; nothing merges between planning packages before review checkpoints.
- Impact: overstated integration state in a planning document.
- Resolution: plan §21 now writes dependencies as "P1 approved commit present" (and analogously for P2/P3).
- Status: RESOLVED
- Affected Package: documentation
