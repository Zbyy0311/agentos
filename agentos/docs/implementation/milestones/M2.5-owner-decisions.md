## OD-1 — Canonical Snapshot Aggregate Owner

Status: APPROVED
Decision owner: Product/Architecture Owner
Question: Do M2.5 snapshots belong only to Task-domain `runs`, or must Conversation `agent_runs` be covered too?
Current facts: Task-domain `runs` (migration 006) and Conversation `agent_runs` (baseline 001) are separate domains with no shared FK; M2.4 explicitly kept them unmerged; all M2.5-relevant Run creation paths (v2 API, Legacy Bridge, retry) write to `runs`.
Options (decision history):
A. Task-domain `runs` only
B. Conversation `agent_runs` only
C. Both domains in M2.5
D. Independent cross-domain snapshot layer
Recommended option (Step 1 proposal — decision history): A
Rationale (Step 1 proposal — decision history): M2.5's target is historical fidelity for Task Runs; covering Conversation Runs would double scope, entangle the frozen Conversation surface, and implicitly merge two Run domains that M2.4 deliberately separated. Conversation Run snapshots can be planned separately later.
Compatibility impact: Conversation API and `run_steps` remain untouched; zero Legacy/Conversation regression risk.
Migration impact: additive changes confined to Task-domain tables.
API impact: snapshot exposure only on v2 Task Run endpoints (per OD-10).
Test impact: Conversation suites act as unchanged regression witnesses.
Risks: users may expect Conversation runs to show snapshots; must be documented as out of scope.
Decision required before: any schema or repository work (P1/P2).
Owner decision: APPROVED — M2.5 snapshots are owned only by Task-domain `runs`. Conversation `agent_runs` is not in M2.5; Conversation `run_steps` is not modified; Conversation routes/services/stores are not modified; the two Run domains are not unified; a Conversation Run Snapshot will be planned separately later.
Decision date: 2026-07-26

## OD-2 — Snapshot Persistence Model

Status: APPROVED
Decision owner: Architecture Owner
Question: How are run snapshots persisted?
Current facts: no snapshot storage exists; Runtime Specification offers a generic `entity_snapshots` table with `content_hash` (10 §92) and recommends Run/Stage store snapshot IDs (10 §93); current repository style is typed tables with explicit FKs and optimistic versions.
Options (decision history):
A. JSON columns added to `runs`
B. Single one-to-one `run_snapshots` table (Run FK, snapshot JSON + schema version + content hash)
C. Multiple normalized snapshot tables (agent/provider/workflow snapshot tables)
D. Hybrid (generic `entity_snapshots` + `runs` snapshot ID columns)
Recommended option (Step 1 proposal — decision history): B
Rationale (Step 1 proposal — decision history): a one-to-one `run_snapshots` table matches current typed-repository style, keeps `runs` narrow, enforces one snapshot per Run via unique FK, supports immutability by exposing insert/read-only repository methods, is additive and reversible, and keeps future PostgreSQL migration straightforward. Option D adds indirection without a current consumer; option A bloats the hot `runs` row; option C multiplies joins for a single read pattern.
Compatibility impact: existing `runs` rows untouched (snapshot absent); queries opt-in.
Migration impact: one additive table + indexes; no backfill.
API impact: snapshot fetched by `run_id` when needed.
Test impact: focused repository tests (insert/read, one-per-run, no update path).
Risks: snapshot JSON size growth; needs schema versioning discipline (see plan §Snapshot Versioning).
Decision required before: P1 schema drafting.
Owner decision: APPROVED — one-to-one `run_snapshots` table. The table has an independent Snapshot ID; one snapshot per Task Run enforced by a unique `run_id`; snapshot JSON; snapshot schema version; content hash; captured timestamp. The repository is insert/read-only with no generic update. Existing Runs may have no row; there is no backfill. REJECTED FOR M2.5: JSON columns on `runs`; a generic `entity_snapshots` table; normalized agent/provider/workflow snapshot tables. DDL remains PROPOSED pending Step 3 Plan Review; no Migration is created by this decision.
Decision date: 2026-07-26

## OD-3 — Workflow Definition Persistence

Status: APPROVED
Decision owner: Architecture Owner
Question: Does M2.5 introduce a canonical `workflow_definitions` persistence, and is it versioned/immutable? Does a Run reference definition id+version, or only store a JSON snapshot?
Current facts: no workflow persistence exists (only unused `workspaces.default_workflow_definition_id`); Legacy pipeline is a fixed four-stage code union; Runtime Specification treats Workflow Definition as a configurable, versioned template requiring a snapshot at Run creation (01 §16, §16.5).
Options (decision history):
W1. `workflow_definitions` + stage definitions + edges (normalized)
W2. `workflow_definitions` + immutable definition JSON (single table, versioned rows)
W3. No definition persistence this round; store only a Workflow Snapshot derived from the built-in pipeline definition
Recommended option (Step 1 proposal — decision history): W3, with W2 as the acceptable next step
Rationale (Step 1 proposal — decision history): there is no Workflow authoring surface today; the only executable truth is the built-in pipeline.
Owner decision: APPROVED — W2: minimal immutable/versioned `workflow_definitions` persistence. M2.5 establishes `workflow_definitions` with an immutable JSON row/version model. At least two built-in Definitions are planned: `legacy-pipeline-v1` and `unbound-task-run-v1`. Rules: the Legacy Pipeline resolves to `legacy-pipeline-v1`; a v2 Run without Workflow selection resolves to `unbound-task-run-v1`; the unbound definition's stages are empty; Definition content is never modified in place — a content change creates a new version; the Run Snapshot stores the complete Workflow value copy; a Definition reference cannot replace the Snapshot; this round adds no Workflow CRUD API, no Workflow UI, does not activate `workspaces.default_workflow_definition_id`, and does not implement Workflow execution. The earlier plan preference W1 is superseded by W2 APPROVED; "Workflow Snapshot only without definition persistence" (W3) is REJECTED FOR M2.5.
Compatibility impact: none on Legacy or v2 reads; definitions and snapshots are additive.
Migration impact: one additive table (+ built-in seed strategy) proposed as Migration 007; DDL remains PROPOSED pending Step 3 Plan Review.
API impact: none this round (no Workflow CRUD API).
Test impact: built-in existence, immutable version, duplicate key/version rejection, new-version allowance, disabled/archived lookup, definition JSON hash.
Risks: minimal model must not drift into CRUD; enforced by OD-12 denylist.

## OD-4 — Canonical Task Run Stage Model

Status: APPROVED
Decision owner: Architecture Owner
Question: How are Task-domain stages persisted?
Current facts: `run_steps` is FK-bound to `agent_runs` and driven by Conversation event projection (`RunStepService` + `persistRunStepMutation`); Task-domain `runs` has no stage persistence; Runtime Specification requires open stage keys (no fixed union) and per-stage Agent/Provider snapshots.
Options (decision history):
A. Reuse/extend Conversation `run_steps`
B. New Task-domain `run_stages` table
C. No stage persistence in M2.5 (snapshots only)
Recommended option (Step 1 proposal — decision history): B
Rationale (Step 1 proposal — decision history): option A requires a cross-domain FK and merges Conversation event semantics into the Task domain — the exact contamination M2.4 removed. A dedicated `run_stages` gives clean ownership and matches the spec's Run Aggregate ("Create Run + Initial Stages", 10 §96).
Compatibility impact: `run_steps` and Conversation behavior unchanged.
Migration impact: one additive table + indexes proposed as Migration 009; DDL remains PROPOSED pending Step 3 Schema Review.
API impact: stages exposed only via the include-based expansion per OD-10.
Test impact: materialization counts, ordering, attempt, pending-only status, Run/Snapshot association; no Conversation regression expected.
Risks: two stage-shaped models exist until Conversation migrates (documented boundary); initial statuses must stay minimal to avoid pretending lifecycle exists.
Decision required before: P1 schema drafting.
Owner decision: APPROVED — dedicated Task-domain `run_stages`. `run_steps` is not reused; the FK points only to Task-domain `runs`; `workflow_stage_key` is an open string; `sequence` determines order; `attempt` starts at 1; the only allowed initial status is `pending`; the Legacy built-in Workflow materializes four initial Stages; the unbound Workflow materializes zero Stages; Stage materialization commits in the same transaction as Run and Snapshot; M2.5 has no Stage transition API and no execution/output/event linkage; a Stage's snapshot binding must map to the same Run Snapshot; the concrete FK design remains PROPOSED pending Step 3 Schema Review.
Decision date: 2026-07-26

## OD-5 — Snapshot Capture Paths

Status: APPROVED
Decision owner: Architecture Owner
Question: Must every Task-domain Run creation path go through a single Snapshot Service at the same capture boundary?
Current facts: Task-domain Runs are created only via `TaskRunService.createRun` (v2) and `TaskRunService.createLegacyRunForBridge` (Legacy initial/retry); startup recovery and terminal reconciliation create no Runs; Conversation Runs are out of scope (OD-1).
Options (decision history): per-path capture/no-capture for `v2_api` initial, `v2_api` retry, `review-fix`, `provider-comparison`, `manual`, `legacy_pipeline` initial, `legacy_pipeline` retry.
Recommended option (Step 1 proposal — decision history): capture on ALL Task-domain creation paths through one SnapshotService invoked inside `TaskRunService` (single capture boundary)
Rationale (Step 1 proposal — decision history): a single boundary inside the existing transaction owner guarantees no path can create a Run without a snapshot; excluding Legacy would make most real executions historically unreliable; recovery/reconciliation create no Runs and therefore capture nothing.
Compatibility impact: Legacy URL/SSE/JSON contracts unchanged; capture is internal.
Migration impact: none beyond OD-2/OD-3/OD-4 storage.
API impact: uniform snapshot availability for new Runs.
Test impact: one matrix cell per creation path.
Risks: capture failure must abort creation (see OD-8) — this changes failure modes of Run creation; error codes must be stable.
Decision required before: P3 service integration.
Owner decision: APPROVED — all newly created Task-domain Runs capture through one boundary. Covered paths: v2 initial; v2 retry; review-fix; provider-comparison; manual; Legacy initial; Legacy retry. The single boundary is: `TaskRunService` transaction → `SnapshotService` → Run/Snapshot/Initial Stage repositories. Routes do not compose repositories directly; an existing Legacy find-or-create that returns an existing Run does not backfill; startup recovery creates no Snapshot; terminal reconciliation creates no Snapshot; repository unit tests may insert directly, but no production route may bypass the Service.
Decision date: 2026-07-26

## OD-7 — Missing, Archived or Disabled Configuration

Status: APPROVED
Decision owner: Architecture Owner
Question: What happens when the Agent, Provider Configuration, or Workflow (or its version) is missing, archived, or disabled at capture time?
Current facts: provider configs support `enabled` and `archived_at` with version-guarded updates; agent profiles have `enabled`; archived providers are excluded from default listings; no current Run creation reads Agent/Provider at all, so there is no existing failure behavior to preserve.
Options (decision history):
A. Fail closed (stable error codes per case)
B. Capture archived/disabled config as historical fact and proceed
C. Legacy-compatibility exception (allow null snapshot sections)
Recommended option (Step 1 proposal — decision history): A with precise codes, plus B-style recording of the archived/disabled state when the config exists
Rationale (Step 1 proposal — decision history): silently running with a missing/disabled config undermines historical fidelity and reproducibility.
Compatibility impact: new failure modes on Run creation; Legacy JSON contract must remain stable for unrelated errors.
Migration impact: none.
API impact: new stable error codes documented in the v2 contract.
Test impact: matrix cells for each missing/archived/disabled combination.
Risks: failing previously-"working" creations that never read configs; must be communicated as a deliberate hardening change.
Decision required before: P3 service integration.
Owner decision: APPROVED — fail closed for invalid explicit bindings; explicit unbound configuration is allowed. Stable error codes: `AGENT_NOT_AVAILABLE`, `PROVIDER_CONFIG_NOT_AVAILABLE`, `WORKFLOW_NOT_AVAILABLE`, `RUN_SNAPSHOT_FAILED`. Matrix: explicit Agent missing/disabled → `AGENT_NOT_AVAILABLE`; explicit Provider missing/disabled/archived → `PROVIDER_CONFIG_NOT_AVAILABLE`; Workflow definition/version missing/disabled/archived → `WORKFLOW_NOT_AVAILABLE`; a valid unbound Workflow with no Agent/Provider binding → allowed; binding null and broken binding must be distinguished; no partial snapshot; no Legacy null-section exception; error responses must be sanitized; Snapshot failure must roll back Run and Stage. No additional error codes may be invented unless separately approved in Plan Review.
Decision date: 2026-07-26

## OD-8 — Snapshot Transaction Boundary

Status: APPROVED
Decision owner: Architecture Owner
Question: Must Run INSERT + Snapshot INSERT + initial RunStage INSERT commit atomically in one `TaskRunService.runInTransaction()`?
Current facts: `TaskRunService` already owns single-handle short transactions for Run creation; Runtime Specification puts "Create Run + Initial Stages" in the Run Aggregate transaction (10 §96) and requires that on snapshot failure no provider process starts (02 §7.4); a half-created Run without snapshot is explicitly unacceptable.
Options (decision history):
A. Single transaction for Run + Snapshot + initial Stages
B. Staged writes with compensation
C. Separate snapshot transaction after Run commit
Recommended option (Step 1 proposal — decision history): A
Rationale (Step 1 proposal — decision history): only a single transaction guarantees the "no Run without snapshot" invariant with SQLite; compensation adds failure modes without benefit at this scale; a separate transaction can orphan Runs.
Compatibility impact: creation latency grows slightly; failure becomes all-or-nothing.
Migration impact: none.
API impact: creation errors surface as one stable failure (`RUN_SNAPSHOT_FAILED`, OD-7).
Test impact: atomic rollback tests for each capture failure point.
Risks: transaction scope creep if stage materialization becomes heavy — keep initial stage writes minimal.
Decision required before: P3 service integration.
Owner decision: APPROVED — Run, Snapshot and Initial Stages commit atomically. One SQLite transaction; `TaskRunService` is the transaction owner; Snapshot resolution and security checks complete before commit; any failure rolls back everything; no compensation; no after-Run snapshot transaction; no Run without Snapshot. A pre-M2.5 existing Run is a compatibility exception (OD-11), not a created half-state.
Decision date: 2026-07-26

## OD-9 — Secret Handling

Status: APPROVED — the exclusion rules remain a HARD SECURITY CONSTRAINT, not negotiable
Decision owner: Security/Architecture Owner
Question: Precisely which secret-adjacent references may appear in snapshots and API responses?
Current facts: main DB stores only `secret_profile_id` / `environment_profile_id` references; spec forbids secret plaintext, tokens, cookies, keys in snapshots (01 §30.2) and secret values in main DB tables (10 §119); CLI args/templates may embed secrets and need scanning; absolute paths (custom working directory) may be sensitive.
Options (decision history):
A. Allow `secretProfileId`/`environmentProfileId` references; exclude everything else secret-adjacent
B. Exclude even references (null them)
C. Allow references plus a curated non-sensitive metadata allowlist
Recommended option (Step 1 proposal — decision history): A, with mandatory args/env scanning and redaction before persistence
Rationale (Step 1 proposal — decision history): references preserve interpretability without exposing values.
Compatibility impact: none on existing APIs (additive).
Migration impact: none.
API impact: snapshot payloads must never contain secret values; redaction verified by contract tests.
Test impact: no-leak assertions across capture, repository, and API layers.
Risks: args templates with embedded secrets are the most likely leak vector; scanning must be allowlist-first with pattern checks.
Decision required before: P2/P3 implementation.
Owner decision: APPROVED — secret references plus a strict non-sensitive allowlist. Allowed: `secretProfileId`; `environmentProfileId`; `providerType`; `runtimeMode`; `model`; `executable`; `capabilities`; structurally validated args template; non-sensitive policy metadata. Forbidden: raw secret; token; API key; cookie; Authorization header; private key; resolved env values; the full env object; unreviewed free-text commands; absolute working directories outside the Workspace; hidden chain-of-thought. Rules: allowlist-first, not reliance on a single-string denylist; template placeholders are preserved per approved syntax; dangerous literals are rejected or redacted; anything that cannot be safely classified fails closed; non-sensitive markers such as `redactionApplied` may be recorded; Repository and API layers must each repeat no-leak validation; no-leak tests are a P3/P4 Exit Gate.
Decision date: 2026-07-26

## OD-10 — API Contract

Status: APPROVED
Decision owner: Architecture Owner
Question: How are snapshots and stages exposed?
Current facts: v2 Run detail currently returns only the Run row; GET/LIST responses are consumed by existing clients; Legacy and Conversation surfaces are frozen; spec expects Inspector-grade snapshot reads eventually (13 §7) but M2.5 has no UI scope.
Options (decision history):
A. Inline snapshot in Run detail
B. Dedicated `GET /v2/runs/:runId/snapshot` (+ optional `/stages`)
C. Summary fields inline + dedicated endpoint for full snapshot
D. Summary metadata inline + opt-in expansion on the existing Run GET endpoint
Recommended option (Step 1 proposal — decision history): C
Rationale (Step 1 proposal — decision history): keeps payloads small and backward compatible while giving consumers a stable read path.
Compatibility impact: additive fields/parameters only; no existing field changes.
Migration impact: none.
API impact: `include` parameter on the existing v2 Run GET; absent-vs-null semantics for legacy Runs (with OD-11).
Test impact: response-shape, isolation, redaction, unknown-include, and absent-snapshot contract tests.
Risks: include-parsing policy must be frozen in Step 3 to avoid drift.
Decision required before: P4 API work.
Owner decision: APPROVED — summary metadata plus opt-in expansion on the existing Run GET endpoint (option D). Final API draft: `GET /api/workspaces/:workspaceId/v2/runs/:runId` gains only additive metadata by default: `snapshotAvailable`, `snapshotSchemaVersion`. Full reads use `GET /api/workspaces/:workspaceId/v2/runs/:runId?include=snapshot,stages`. REJECTED FOR M2.5: `GET /v2/runs/:runId/details` (removed from the Architecture Plan) and any new `/snapshot`, `/stages`, or `/details` endpoint. Rules: the `include` parameter may contain `snapshot`, `stages`; an unknown include value returns 400 or follows the existing API parse policy — this must be frozen in Step 3; Snapshot payload follows OD-9; Workspace isolation is preserved; `contentHash` may be returned as metadata; this round implements no conditional GET and no new ETag mechanism; the Run's existing version behavior is unchanged.
Decision date: 2026-07-26

## OD-11 — Legacy and Existing Run Compatibility

Status: APPROVED
Decision owner: Architecture Owner
Question: How do Runs created before M2.5 (no snapshot) behave, and what must never change?
Current facts: all existing Runs lack snapshots; Legacy URL/SSE/JSON and Conversation surfaces are frozen by M2.4; apps/web consumes current shapes; no backfill is in scope (OD-12).
Options (decision history):
A. Return `null`/absent snapshot for pre-M2.5 Runs; never synthesize
B. Synthesize snapshots from current config on read (prohibited recommendation)
C. Bulk backfill (out of scope)
Recommended option (Step 1 proposal — decision history): A
Rationale (Step 1 proposal — decision history): synthesizing from current config would falsify history — the exact failure M2.5 exists to prevent.
Compatibility impact: Legacy URLs, SSE frames, TaskItem JSON, Conversation `agent_runs`, and apps/web shapes must remain byte-compatible; snapshot fields appear only on v2 surfaces per OD-10.
Migration impact: none.
API impact: documented null/empty semantics for pre-M2.5 Runs.
Test impact: old-row fixture tests proving null behavior and Legacy byte-compatibility.
Risks: clients assuming snapshot always present; mitigated by explicit contract documentation.
Decision required before: P4 API work.
Owner decision: APPROVED — no synthesis and no backfill. Pre-M2.5 Run responses: `snapshotAvailable = false`; `snapshotSchemaVersion = null`; `snapshot = null`; `stages = []`. The full snapshot/stages fields appear only when requested via `include`; the exact default field structure is frozen in Step 3. Never allowed: synthesizing a historical Snapshot from current configuration; automatic backfill; bulk backfill; modifying Legacy URL/SSE/JSON; modifying Conversation responses; modifying apps/web.
Decision date: 2026-07-26
