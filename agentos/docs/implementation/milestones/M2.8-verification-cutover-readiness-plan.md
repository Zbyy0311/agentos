## 1. Objective

Establish an evidence-based path from the current mixed Workspace and Legacy Task state to an owner-approved, reversible cutover plan. The plan covers verification, authority decisions, parity, quarantine, API/Web contracts, recovery, rehearsal, and release gates.

The current task delivers only:

- Current-State Audit
- Owner Decision Register
- Implementation Plan Draft

The current task does not deliver:

- production code changes
- test changes
- schema or migration changes
- Migration 012
- real data migration
- Production Restore
- Legacy JSON deletion
- API/Web cutover
- PR creation

## 2. Success criteria for a future approved cutover

A future cutover may be considered ready only when all of the following are evidenced and owner-approved:

1. Every affected domain has one named authoritative write and read policy.
2. Workspace JSON and Legacy Task JSON have explicit read, write, retention, quarantine, and retirement decisions.
3. Canonical Task mapping is idempotent and does not fabricate historical Run or Execution records.
4. API, Web, SSE, cancel, resume, reconnect, and recovery behavior have contract parity evidence.
5. Locks, backups, restore or an explicitly approved compensating recovery gate are exercised.
6. Active runtime behavior and mixed-version behavior are documented and tested.
7. Release Gate and No-Go criteria have owner signatures and attached outputs.
8. Any Migration 012 has a demonstrated schema gap and approved scope.

## 3. Guiding invariants

- SQLite and JSON must never be treated as equal authorities without an explicit decision.
- A source record must be classified before it is applied.
- Invalid, duplicate, tombstone, conflict, and changed-source records must not be silently overwritten.
- Every apply operation must be idempotent and bound to source bytes, source hash, workspace scope, and canonical database.
- A Legacy TaskItem must not receive a synthetic historical execution unless its evidence and semantics are explicitly approved.
- Task-domain runs use runs with run_snapshots and run_stages and remain bound to canonical task_id.
- Conversation AgentRun/Execution uses agent_runs, run_steps, executions, execution_events, agent_events, and run_event_sequences.
- runs != agent_runs; the two aggregates must remain isolated during M2.8 API/Web Cutover.
- Any data-model unification is a separate Owner Decision and milestone, not an incidental cutover change.
- A backup is not a restore proof until restoration is exercised and verified.
- Read-only evidence gathering must not modify production data, source JSON, stash state, retained M2.7 branches, or unrelated files.
- No phase can silently expand into physical deletion, API removal, or runtime unification.

### Production, test, and document changes

- Tests: comparator, malformed input, duplicate, tombstone, conflict, and unchanged-source cases

- Documents: parity field matrix, thresholds, quarantine policy, and operator output format

### Interfaces

Define a read-only comparison interface with:

- source key and source byte hash
- workspace scope
- canonical database identity
- field-level comparison result
- classification
- mismatch reason
- redacted metrics
- run ID and timestamp

### Data invariants

- comparison cannot mutate source JSON or canonical rows
- equal counts are insufficient for parity
- a mismatch is observable and does not become an implicit overwrite
- source hash changes invalidate the previous comparison result

### Transaction boundary

Read-only comparison must use a read transaction or consistent snapshot for SQLite and exact source bytes for JSON. It must not acquire a write transaction.

### Failure behavior

Malformed JSON, symlinked source, changed bytes, invalid provider binding, duplicate identity, tombstone, conflict, and database mismatch produce explicit non-success classifications.

### Idempotency

Repeating the comparison for identical source bytes and database state produces the same classification and comparison hash.

### Security and no-leak rules

Metrics must omit credentials, executable secrets, full payloads, and full local paths where an opaque identifier is sufficient.

### Planned test matrix

- field equality and missing-field cases
- duplicate and tombstone cases
- changed-source rerun
- provider binding mismatch
- malformed JSON and symlink rejection
- database path mismatch
- no-write assertion
- latency and bounded-memory check

These tests are planned only; they were not run in this task.

### Exit gate

Owner-approved parity fields, thresholds, classifications, and no-write evidence exist for representative data.

### Rollback

Disable instrumentation and remove comparison outputs. No product data should require rollback because P1 is read-only.

### Risk tier

Medium, because instrumentation can expose sensitive data or create false parity confidence.

### Scope expansion stop condition

Any comparison code that writes canonical rows, updates authority, or repairs mismatches must stop and become a separately approved phase.

- Tests: list/create/run/recovery/bridge/SSE/idempotency and active-run cases
- Migrations: no new migration unless a proven mapping or retention schema gap exists
- Documents: Legacy Task conversion and retirement runbook

### Interfaces

Define the mapping contract for the Task-domain aggregate:

- Legacy TaskItem ID to canonical Task ID
- workspace identity
- status and priority mapping
- legacyTaskId uniqueness
- canonical Task-domain Run in runs, with run_snapshots and run_stages
- RunRepository and TaskRunService ownership
- bridge Run origin legacy_pipeline
- terminal synchronization
- compatibility evidence reference

ConversationService, agent_runs, run_steps, executions, execution_events, agent_events, and run_event_sequences remain outside this Task-domain mapping. A Legacy Task bridge Run is not a Conversation AgentRun.

### Data invariants

- one stable Legacy TaskItem maps to at most one canonical Task
- a bridge execution creates at most one intended Run for its idempotency key
- terminal state cannot move backward
- historical Runs are not synthesized from incomplete TaskItem fields
- JSON recovery and canonical recovery cannot both claim the same active work

### Transaction boundary

Task mapping, Run creation, Snapshot/Stage creation, and mapping evidence must commit in one SQLite transaction where the contract requires atomicity. JSON state transition and canonical bridge compensation must have an explicit failure policy.

### Failure behavior

If canonical creation succeeds but JSON transition fails, or the inverse occurs, the system must expose a recoverable reconciliation state and not silently claim success.

### Idempotency

Repeated run requests with the same task and idempotency key must not create duplicate canonical Runs. Repeated imports of identical task bytes must produce no-op/equal results.

### Security and no-leak rules

Task payloads, command arguments, and file paths must be redacted in parity output and logs.

### Planned test matrix

- empty, malformed, duplicate, and changed tasks JSON
- mapping by legacyTaskId
- create/list/run state transitions
- bridge retry and compensation
- Legacy Task recovery
- canonical Run recovery
- active run during cutover
- SSE terminal event and reconnect behavior
- no synthetic historical execution

These tests are planned only; they were not run in this task.

### Exit gate

Owner approves Legacy Task read/write retirement, mapping and history policy, recovery behavior, and retention of compatibility evidence.

### Rollback

Keep source tasks JSON and compatibility rows, revert the feature flag, and stop new canonical conversion. Do not delete Legacy Task files.

### Risk tier

High, because task state and execution state are user-visible and operational.

### Scope expansion stop condition

Any bulk conversion, task history synthesis, or physical tasks.json deletion requires a separate owner decision and release gate.

## 10. P5 — Controlled rehearsal and rollback

### Goal

Exercise the approved cutover sequence against an isolated representative copy, including failure paths, active Task-domain and Conversation runtime operations, backup, restore, quarantine, and rollback. The two run families are inventoried and verified separately.

### Exact files and file categories

- approved migration and compatibility services
- LegacyBackupVerifier and approved restore tooling
- migration/repository fixtures
- operator runbook and rehearsal report
- no production data path

### Production, test, and document changes

- Production: none during isolated rehearsal
- Tests: full approved matrix plus fault injection
- Migrations: only approved migrations against isolated copy
- Documents: step-by-step operator transcript, timings, hashes, and rollback result

### Interfaces

The rehearsal interface includes:

- preflight and lock acquisition
- source hash and database identity
- backup manifest
- dry-run classification
- apply result
- quarantine result
- post-apply parity
- restore result
- operator decision

### Data invariants

- original source bytes remain immutable
- isolated database identity is explicit
- every applied record has an evidence row
- restore returns to a verified known state
- no active run is lost or falsely terminal

### Transaction boundary

Acquire server ownership, then the database-wide migration lock. Backup before apply. Apply each approved scope transactionally. Release in reverse order. Restore in an isolated database before any production consideration.

### Failure behavior

Any lock, backup, integrity, parity, restore, or active-run failure produces No-Go for the rehearsal and preserves source bytes and evidence for diagnosis.

### Idempotency

Rerunning the dry-run on unchanged inputs is a no-op. Rerunning apply after a recorded terminal success is rejected or returns equal. A changed source requires new evidence.

### Security and no-leak rules

Rehearsal logs are sanitized and access-controlled. Backup locations, credentials, and command payloads are not copied into public milestone documents.

### Planned test matrix

- clean representative copy
- malformed and changed JSON
- duplicate, conflict, and tombstone records
- lock contention and lease expiry
- backup verification
- restore integrity and foreign-key checks
- active Legacy Task and bridge Run
- interrupted recovery
- API/Web smoke against the resulting copy
- rollback to pre-apply copy

These tests are planned only; they were not run in this task.

### Exit gate

Rehearsal passes the approved thresholds, restore is exercised, quarantine is reviewed, active-run behavior is accepted, and the owner signs the report.

### Rollback

Restore the isolated copy to the verified pre-apply state. For production, rollback remains unavailable until the same evidence exists for the production topology.

### Risk tier

Critical in production; medium in an isolated copy.

### Scope expansion stop condition

Do not run against production or delete source files if restore evidence, owner approval, or No-Go criteria are missing.
