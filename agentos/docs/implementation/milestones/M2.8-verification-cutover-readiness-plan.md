## 1. M2.8 goal and boundary

Goal:

Verify the entire M2 implementation against acceptance criteria, prove rollback and cutover readiness, and close the M2 milestone without performing Production Cutover.

M2.8 is not an M3 Cutover implementation phase. Completing M2 does not require:

- deleting or physically retiring Legacy JSON
- removing the Legacy API
- switching the Web default route to v2
- unifying Task-domain runs and Conversation agent_runs

Completing M2 does require:

- complete M2 acceptance verification
- read-only parity and reader/writer inventory
- real-copy migration and isolated Restore Rehearsal
- backward-compatibility and runtime evidence
- a formal Cutover Plan and Owner-signed Formal Gate

The current closure task changes only the Owner Decision Register and this Plan. The Current-State Audit remains unchanged and is the pre-closure evidence baseline.

- SQLite is the sole production Workspace writer.
- Legacy TaskItem continues to read from and write to tasks.json in M2.8.
- v2 Task/Run uses SQLite while remaining a separate API contract.
- Task-domain runs use runs, run_snapshots, and run_stages and remain bound to canonical task_id.
- Conversation AgentRun/Execution uses agent_runs, run_steps, executions, execution_events, agent_events, and run_event_sequences.
- runs != agent_runs.
- Task-domain Run and Conversation AgentRun remain independent Aggregates.
- API/Web compatibility work must not merge the two runtime families.
- A Legacy Task bridge Run is not a Conversation AgentRun.
- No new Dual-write is introduced.
- No destructive SQLite migration or Legacy JSON deletion occurs in M2.8.
- Every migration/rehearsal input is classified before apply.
- Conflict, duplicate, tombstone, malformed, and changed-source records are quarantined or rejected explicitly.
- Original real database and JSON source hashes remain unchanged during copy-only verification.

- Migration: fresh DB migrations 001–011 and upgrade from representative v1 copy
- Documents: source hashes, case manifest, results, failure transcript, and cleanup evidence

### Interfaces

P3 must exercise:

- MigrationRunner and Migration Registry 001–011
- WorkspaceCompatibilityMigrationService
- LegacyTaskItemImportService
- LegacyBackupVerifier
- LegacyMigrationExecutionLock and server ownership
- isolated Restore Rehearsal workflow

### Data invariants

- all source records are preserved or explicitly quarantined
- repeat execution is no-op/equal for unchanged input
- malformed, conflict, duplicate, and tombstone records are not silently applied
- verified SQLite Backup and exact-byte JSON Backup are created before apply/rehearsal
- original real DB and JSON hashes remain unchanged
- integrity_check=ok
- foreign_key_check=0

### Transaction boundary

Acquire server ownership before the database-wide migration lock. Back up before apply. Apply each approved scope transactionally. Release locks in reverse order. Restore only into an isolated database.

### Failure behavior

Any lock, backup, hash, integrity, foreign-key, source-preservation, quarantine, or restore failure is No-Go. The source copy remains preserved for diagnosis.

### Idempotency

Rerun of unchanged input returns no-op/equal. A changed source hash requires a fresh classification. A terminal successful migration cannot be applied again as a new success without an explicit new source revision.

### Security/no-leak

The real copy is sanitized and access-controlled. Backup paths, credentials, raw payloads, and full local paths are omitted from public reports.

### Test matrix

- fresh DB migrations 001–011
- upgrade from representative v1 copy
- all source records preserved
- repeat/no-op behavior
- malformed/conflict/quarantine
- verified SQLite Backup
- exact-byte JSON Backup
- isolated Restore Rehearsal
- integrity_check=ok
- foreign_key_check=0
- original real DB and JSON hashes unchanged
- active and interrupted Run recovery in a quiescent rehearsal

### Exit gate

The real-copy rehearsal passes preservation, no-op, backup, restore, integrity, foreign-key, hash, and quarantine gates. Restore failure is No-Go and cannot be waived by backup-only evidence.

### Rollback

Restore the isolated copy to its verified pre-rehearsal state. Production rollback remains a future M3 operation and is not performed by P3.

### Risk tier

Critical in production; high in an isolated copy.

### Scope expansion stop condition

Do not use production data, delete Legacy JSON, run a destructive migration, or treat an untested backup as restore evidence.
