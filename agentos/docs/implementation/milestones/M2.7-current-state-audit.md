## 2. Current Architecture Facts

1. `WorkspaceManager` is SQLite-first for `list`, `get`, `create`, `importExisting`, `touch`, and `remove`, but `SqliteStore.loadWorkspaces()` still performs a filtered JSON fallback.
2. Workspace JSON is still read on every `loadWorkspaces()` and by boot-time legacy workspace migration. Malformed JSON is silently converted to an empty list by `JsonFileStore`.
3. Workspace writes through the production `SqliteStore` go to SQLite. `JsonFileStore` still exposes JSON writes, and `SqliteStore.saveWorkspaces()` does not write `workspaces.json`.
4. Workspace deletion removes SQLite aggregate rows and inserts `_workspace_tombstones`; the JSON file is not deleted. `loadWorkspaces()` and `assertWorkspaceExists()` prevent a tombstoned JSON workspace from being re-imported or accepted.
5. `SqliteStore` constructs `DatabaseSync`, runs `MigrationRunner` for registry 001–010, then runs event-sequence migration, legacy execution migration, and legacy workspace/agent migration during construction.
6. `migrateLegacyWorkspaceAggregates()` is rerunnable by workspace ID, agent ID, provider binding, tombstone, and canonical-path checks. It has no explicit completion marker and reruns on every construction while JSON remains present.
7. `migrateLegacyExecutionRuns()` selects `executions WHERE run_id IS NULL`, creates `legacy-run-${execution.id}` Conversation `agent_runs`, and updates `executions.run_id`; after success, the predicate makes repeated runs no-ops. It is not a Task-domain Run migration.
8. Legacy `TaskItem` read/write remains fully JSON-backed through `JsonFileStore`; `SqliteStore.loadTasks/saveTasks/saveTask` delegate directly to it.
9. v2 Task and Run reads/writes are SQLite-backed through `TaskRepository` and `RunRepository` and exposed by workspace-scoped v2 routes.
10. The Legacy Task Pipeline Bridge reads and writes JSON TaskItem state while `TaskRunService.createLegacyRunForBridge()` creates a canonical Task/Run/Snapshot/Stage projection for each new execution.
11. `legacy_task_id` is optional on canonical `tasks`, unique per workspace, and is used by the Bridge to find-or-create the canonical Task. No bulk JSON-task migration exists.
12. Legacy Task `outputs` are not copied into canonical Task/Run/Artifact records by existing boot migration. New Bridge executions retain JSON outputs and create a new canonical Run; historical output-to-Run mapping is unresolved.
13. Conversation `agent_runs`/`executions` and Task-domain `runs` are separate aggregates and tables. They must remain separate in M2.7.
14. Partial migration and dual-read are real: Workspace/Agent/Provider migration exists, Workspace JSON fallback exists, Legacy Task JSON remains canonical for that surface, and the Bridge performs per-execution canonical projection.
15. Workspace deletion plus restart does not resurrect a JSON workspace when the tombstone remains in SQLite; this is a tested invariant. A future migration must preserve it.
16. Malformed `workspaces.json` or `tasks.json` is silently ignored by `JsonFileStore` and returns `[]`; callers cannot distinguish missing, malformed, or empty data.
17. Canonical root paths are normalized by `toCanonicalRootPath()` and unique in SQLite. A legacy workspace whose path conflicts with an existing SQLite workspace is skipped with a warning; there is no durable conflict record.
18. `MigrationRunner` fails closed on schema incompatibility, checksum mismatch, lock failure, migration failure, integrity failure, or foreign-key failure. It does not authorize JSON fallback after a migration error.
19. Server startup constructs `SqliteStore` before recovery and routes; startup therefore depends on successful SQLite migration/adoption, while Workspace and Legacy Task compatibility still depends on JSON reads.
20. `apps/web/src/lib/useTask.ts` directly consumes Legacy `/api/workspaces/:workspaceId/tasks` and `TaskItem` JSON shape. Legacy API removal or shape replacement is outside this audit’s authority.
