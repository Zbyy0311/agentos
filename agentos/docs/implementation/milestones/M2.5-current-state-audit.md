## 13. Confirmed Facts

1. Migration Registry is 001–006; the last migration is `006 runs-table`; `default-registry.ts` lists exactly six migrations.
2. Task-domain `runs` exists with composite FKs, 8-state status CHECK, reason/origin CHECKs, and a partial unique index enforcing one active Run per Task.
3. `agent_runs` and `run_steps` belong to the Conversation Domain; `run_steps.run_id` references `agent_runs(id)`.
4. v2 `POST /tasks/:taskId/runs` creates only a durable queued Run via `TaskRunService.createRun` inside `runInTransaction`.
5. Legacy Bridge find-or-creates the Task and creates `initial`/`retry` Runs with parent lineage inside one transaction.
6. Retry lineage is `parentRunId` + inherited `rootRunId`; historical Runs are never mutated by retry (new row only).
7. No snapshot of any kind is created on any Run creation path today.
8. No Workflow Definition persistence exists; the Legacy four-stage pipeline is a fixed `AgentStage` union in code.
9. `provider_configurations.secret_profile_id` is a reference column; no raw secret values are stored in the main database schema.
10. There is no dedicated `AgentProfileRepository`; agent profiles are read through `SqliteStore` with a JOIN to `provider_configurations`.
11. `TaskRunService` is the single transaction owner for Task/Run cross-aggregate mutations.
12. Baseline Attempt 3 passed with Server 478/477/0/1, Agent Core 123/123, Root Build PASS, no residual processes or listeners.
13. `run_stages` does not exist in schema or code; Task-domain Runs have no stage persistence of any kind.
14. No snapshot/stage read API exists on any v2 or Legacy surface.
15. `packages/shared` contains no `WorkflowDefinition`, Task-domain `RunStage`, `AgentSnapshot`, `ProviderConfigurationSnapshot`, or `RunSnapshot` runtime types.
16. No secret-scan/redaction utility dedicated to snapshot persistence exists.
