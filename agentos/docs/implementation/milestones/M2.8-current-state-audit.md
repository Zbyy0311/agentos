## 5. Legacy JSON inventory

### 5.1 Confirmed production Legacy JSON path

apps/server/src/store/JsonFileStore.ts is the active production Legacy JSON store.

- workspace/workspaces.json is loaded and saved by JsonFileStore.
- workspace/<workspaceId>/.agentos/tasks.json is loaded and saved by JsonFileStore.
- writes use a temporary file followed by rename and cleanup.
- malformed or unreadable JSON is converted to an empty collection by the legacy loader.
- the loader does not provide a durable migration completion marker by itself.

The exact JSON file names are therefore not sufficient to establish a safe cutover. Read fallback, write authority, tombstones, adoption markers, backup records, and failure recovery must be considered together.

### 5.2 Current SQLite-first Workspace behavior

apps/server/src/store/SqliteStore.ts constructs JsonFileStore, opens .agentos/agentos.sqlite, runs the registered migrations, and then performs legacy execution/workspace adoption helpers.

Workspace reads:

- loadWorkspaces reads SQLite workspace rows first.
- JSON records are considered for IDs not found in SQLite and not present in _workspace_tombstones.
- an adopted or explicitly deleted workspace can therefore affect whether an old JSON record is visible.

Workspace writes:

- saveWorkspaces writes Workspace, Agent, and Provider rows in a SQLite transaction.
- saveWorkspaces does not write the workspace JSON file.

This is a dual-read transition state, not proof that workspace JSON is already retired.

### 5.3 Current Legacy Task behavior

SqliteStore.loadTasks, saveTasks, and saveTask delegate directly to JsonFileStore. The Legacy Task routes use those methods for list, create, run-state updates, SSE-facing state, and recovery. taskRecovery.ts also loads and saves Legacy Task JSON during startup recovery.

TaskRunService.createLegacyRunForBridge creates canonical Task/Run/Snapshot/Stage records for a Legacy Task execution, but this bridge operation does not itself import every existing Legacy TaskItem into the canonical task table. The current design is therefore per-execution bridging, not a completed bulk task cutover.

## 6. Migration and adoption mechanisms

### 6.1 Registered migrations

apps/server/src/migrations/default-registry.ts registers migrations 001 through 011. MigrationRunner applies pending migrations in a transaction with integrity and foreign-key checks.

Migration 011 creates:

- legacy_data_migrations
- legacy_task_items
- related indexes and immutability triggers

The registered Migration 011 source keys are workspaces.json and tasks.json. The schema is an evidence and compatibility foundation; it is not itself proof that all Legacy JSON has been imported or that the JSON files may be deleted.

### 6.2 Workspace compatibility migration service

WorkspaceCompatibilityMigrationService is an explicit, dry-run-capable service for workspace/workspaces.json.

Observed safeguards include:

- strict source path resolution
- symlink rejection
- canonical database path assertion
- two-layer lease acquisition
- byte and SHA-256 capture
- parse and classification before writes
- dry-run mode with no writes
- backup before apply
- cleanup and lease release in finally

Classifications include invalid, duplicate, tombstone, conflict, adoptable, equal, and compatible-missing cases. These classifications need an owner-approved disposition matrix before any production cutover.

### 6.3 Legacy Task item import service

LegacyTaskItemImportService is a separate explicit service for workspace/<workspaceId>/.agentos/tasks.json.

Observed safeguards include:

- strict workspace source resolution
- explicit tasks import kind
- two-layer lock
- backup before apply
- compatibility-row writes only

LegacyTaskItemRepository describes append-only compatibility storage and records accepted snapshots. This still leaves open the canonical Task conversion policy, historical execution policy, and physical JSON retirement policy.

### 6.4 Locking and backup

LegacyMigrationExecutionLock serializes database-wide migration activity and has a fixed acquisition order: server ownership first, then the database lock; release occurs in reverse order.

LegacyBackupVerifier creates and verifies a consistent SQLite backup and exact-byte JSON backups. It checks database binding, integrity, foreign keys, tables, and row counts without modifying source files. The service is backup-and-verify only. No Production Restore API or exercised restore workflow was found in the audited implementation.

The presence of locks and backups lowers operational risk but does not satisfy the release gate by itself.

## 7. API, SSE, and Web boundaries

### 7.1 Server routes

apps/server/src/index.ts mounts both Legacy and v2 route families:

- Legacy workspaces and Legacy Task routes under /api/workspaces and /api/workspaces/:workspaceId/tasks
- v2 task and run routes under /api/workspaces/:workspaceId/v2
- conversation, agent, stream, and related routes

The route families are simultaneously active. Route registration does not identify one family as the sole authority.

Legacy task routes:

- list and create Legacy TaskItems through JsonFileStore
- update running state through JSON
- create a canonical bridge Run for an execution
- expose Legacy task state and SSE behavior

v2 routes:

- use TaskRunService and canonical repositories
- return a uniform error envelope through respondV2
- use version, status, priority, and idempotency controls

Conversation routes:

- create and stream messages through ConversationService
- persist AgentRun/Execution records separately from Legacy TaskItem state
- provide reconnect, cursor, cancel, and resume behavior for conversation streams

### 7.2 SSE behavior

apps/server/src/routes/sse.ts emits event and JSON data frames and sends periodic heartbeat comments. Conversation streams use event IDs/cursors and reconnect behavior. Legacy task SSE and conversation SSE are therefore related transport surfaces but not automatically interchangeable contracts.

Before any API/Web switch, the owner must decide whether event names, payloads, cursor semantics, reconnect behavior, cancel behavior, and error envelopes are preserved, versioned, or migrated together.

### 7.3 Web consumers

The Web application currently consumes:

- workspace APIs
- Legacy Task API under /api/workspaces/:workspaceId/tasks
- conversation messages and streaming
- run and execution data
- agent and presence data

The workspace page contains reconnect, resume, cancel, and stream event handling. There is no evidence in the audited Web code that a global switch to v2 task routes has already been completed. Web cutover therefore remains a contract migration, not a route aliasing exercise.
