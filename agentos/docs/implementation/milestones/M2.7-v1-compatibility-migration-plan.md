## 2. Objective

Define a reversible, repeatable compatibility and data-migration boundary for Workspace/Agent/Provider legacy JSON and Legacy TaskItem JSON while preserving the existing architectural distinctions:

- Task-domain Task ≠ Conversation AgentRun.
- Task-domain Run ≠ Conversation AgentRun or Process.
- Legacy TaskItem JSON ≠ canonical Task/Run storage.
- Migration metadata ≠ schema Migration 011 by assumption.
- M2.7 migration ≠ M2.8 final cutover readiness.

## 3. Non-goals

- No M2.7 production code, test, or Migration implementation in this planning branch.
- No automatic JSON deletion, rename, or fallback policy.
- No assumption that Migration 011 is necessary.
- No historical Task-domain Run/Artifact/Snapshot/Stage synthesis without Owner approval.
- No Legacy API, SSE, Web TaskItem shape, Task Pipeline Bridge, Conversation `agent_runs`, or Agent Core refactor.
- No migration of `agent-memory`, attachments, artifacts, logs, worktrees, leases, Prompt, Message, Secret, or provider runtime evidence.
- No M2.8 cutover or verification implementation.

## 4. Architecture Invariants

1. SQLite canonical tables and Legacy JSON sources remain separate until an approved policy closes the boundary.
2. Conversation `agent_runs` and Task-domain `runs` remain distinct aggregates and are never merged by compatibility code.
3. Existing M2.6 Migration 010 and idempotency invariants remain unchanged.
4. Workspace tombstones always participate in any Workspace migration/read policy.
5. Canonical root normalization and Workspace scoping remain authoritative.
6. A migration may not silently convert malformed JSON to an empty successful migration.
7. A committed data migration must be resumable or restoreable from a verified backup.
8. Any inferred or synthetic historical record must be explicitly marked and Owner-approved; default direction is no synthesis.
9. Legacy URLs, SSE, TaskItem JSON, Web consumers, and Bridge behavior remain compatible unless a later Owner decision says otherwise.
10. Logs and reports contain only counts, entity types, safe IDs, hashes, and stable error codes.

## 5. Current-State Findings

- Workspace boot adoption is partially implemented and reruns without a data-migration completion marker.
- Workspace reads are SQLite-first plus filtered JSON fallback.
- Legacy TaskItem reads/writes are still JSON-only.
- The Bridge maps new Legacy executions to canonical Task/Run/Snapshot/Stage but does not bulk-migrate old TaskItem history.
- Existing execution migration creates Conversation `agent_runs`, not Task-domain `runs`.
- Main’s real SQLite copy is a valid old schema at `_schema_migrations` 001–002; current code would apply later schema migrations during construction.
- Malformed JSON is silently ignored by the current `JsonFileStore`.
- Canonical-root conflicts are skipped with a warning and no durable conflict record.

Evidence and scenario details are in `M2.7-current-state-audit.md`; decisions are in `M2.7-owner-decisions.md`.

## 8. Migration Strategy Alternatives

| Strategy | Description | Benefit | Risk | Current Planning Position |
|---|---|---|---|---|
| A | Boot-time automatic JSON-to-SQLite migration | Simple user experience | Constructor side effects, silent failures, difficult rollback | Not assumed |
| B | Explicit operator migration with verified backups | Controlled and auditable | Requires command/UX and operational process | Recommended candidate |
| C | Mixed safe adoption + explicit data migration | Preserves current boot compatibility while isolating risky writes | More states to document | Recommended candidate |
| D | Read-only compatibility forever | Lowest migration risk | Permanent dual-read/write complexity | Not preferred |

Migration 011 is not assumed. A dedicated data registry, sidecar manifest, or existing metadata mechanism must be chosen by OD-23/OD-24 before implementation.
