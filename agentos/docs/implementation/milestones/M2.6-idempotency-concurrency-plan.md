## 4. Architecture

- `TaskRunService` continues to own every operation transaction (OD-11).
- `IdempotencyService` is transactionless: it never calls `BEGIN`, `COMMIT`, `ROLLBACK`, or `runInTransaction`; it receives the same `TransactionDatabase` handle used by the Task/Run repositories.
- In-transaction order: lookup/replay → version/domain guard → mutation → result allowlist → immutable record insert → commit.
- No key → exactly today's code path.
- Replay lookup precedes `RUN_ACTIVE_EXISTS`, `RUN_NOT_CANCELLABLE`, `TASK_NO_ACCEPTANCE_WINDOW`, `INVALID_TASK_TRANSITION`, and `VERSION_CONFLICT` guards.
- No HTTP retry is added anywhere.

## 5. Exact Domain Boundaries

In scope: `task.create`, `run.create`, `run.cancel`, `task.accept`, `task.cancel`, `task.reopen` on workspace-scoped v2 routes. Out of scope: Legacy Bridge, `routes/tasks.ts`, Conversation/`agent_runs`, Approval, Provider (reference pattern only), Web, Agent Core, M2.7/M2.8.

## 6. Transaction Ownership

`IdempotencyRepository` shares the operation's `TransactionDatabase` handle inside `TaskRunService.runInTransaction`. Record insert and domain mutation commit or roll back together. Failed operations (any non-2xx) leave no record (OD-12).

## 7. Data Flow

1. Route calls `parseIdempotencyKey(req)` (OD-5: `req.rawHeaders` duplicate detection, trim-normalize, validate) and parses the optional `expectedVersion` body field (OD-15 validation).
2. Service computes `key_hash = SHA-256 UTF-8(normalizedKey)` and `request_hash` (canonical JSON + SHA-256 over operation, workspace, path params, normalized input, expectedVersion null-or-integer).
3. Inside the transaction: `findVerifiedByScope(workspaceId, operation, keyHash)` — the repository performs the full 12-step integrity verification internally (§11 P1.2); a malformed record fails closed with `IDEMPOTENCY_RECORD_INVALID`.
4. Hit + same `request_hash` → replay original status and `envelope.body`, set `Idempotency-Replayed: true`.
5. Hit + well-formed different `request_hash` → throw `IdempotencyKeyReusedError` → 409 `IDEMPOTENCY_KEY_REUSED`.
6. Miss → domain/version guards → mutation → build allowlisted typed envelope V1 → `insertCompleted` with `result_hash` → commit.

## 8. Error Contract

| Condition | HTTP | Code | Message |
|---|---|---|---|
| Bad key shape / duplicate header / comma-joined / array / empty | 400 | `VALIDATION_FAILED` | existing validation message style; the message never contains the key or header value |
| Key reused with different request (well-formed stored `request_hash`, mismatch) | 409 | `IDEMPOTENCY_KEY_REUSED` | "Idempotency key was already used with a different request" |
| Stale `expectedVersion` | 409 | `VERSION_CONFLICT` | "Version conflict" (no `currentVersion`, no entity metadata) |
| Malformed stored record (shape/hash/JSON/envelope verification failure, including malformed stored `request_hash`) | 500 | `IDEMPOTENCY_RECORD_INVALID` | "Idempotency record is invalid" (fixed safe message; no internal detail) |
| All existing domain codes | unchanged | unchanged | unchanged |

P3 adds the v2 error mapping for `IDEMPOTENCY_KEY_REUSED` and `IDEMPOTENCY_RECORD_INVALID` to `V2_ERROR_STATUS`; this remediation round changes no code.

## 9. Security Contract

Dual-layer no-leak (OD-19): repository validates exact stored shape and hashes on read; API never echoes raw keys, request bodies, fingerprints, or internal errors. Only `key_hash`, `request_hash`, `result_hash` persist. Tamper/corruption fails closed with `IDEMPOTENCY_RECORD_INVALID`. Cross-workspace records are unreachable by construction (composite scope) and by test.

Request-hash verifiability boundary (OD-19 freeze): raw requests are not retained, so a well-formed but non-matching stored `request_hash` is indistinguishable from legitimate key reuse with a different request and is answered with 409 `IDEMPOTENCY_KEY_REUSED`. Only malformed stored hashes (non-string, wrong length, non-lowercase-hex) fail closed as 500 `IDEMPOTENCY_RECORD_INVALID`. Plain SHA-256 is not represented as a defense against an attacker with database write access; M2.6 adds no `record_hash`, HMAC, or secret key.

## 10. Compatibility Contract

No key → behavior, status codes, and response shapes identical to today. Legacy URL/SSE/TaskItem JSON unchanged. Conversation unchanged. Web unchanged. Provider required-`expectedVersion` contract unchanged. Pre-M2.6 databases migrate additively. No M2.7 behavior introduced.

#### P1.2 — Repository Integrity Contract

The optional external-verify pattern (`findByScope` + public `verifyIntegrity`) is cancelled. Frozen public API:

```ts
findVerifiedByScope(
  workspaceId: string,
  operation: IdempotencyOperation,
  keyHash: string,
): IdempotencyRecord | undefined;

insertCompleted(input: InsertCompletedIdempotencyRecord): IdempotencyRecord;
```

`findVerifiedByScope` internal read order (every step mandatory, in order):

1. Workspace + Operation + Key Hash scope lookup;
2. Exact row shape;
3. ID prefix (`idem_`);
4. Operation vocabulary (six frozen keys);
5. Hash shapes (`key_hash`/`request_hash`/`result_hash`: string, length 64, lowercase hex);
6. `result_schema_version` (= 1);
7. HTTP status (2xx);
8. JSON parse of `result_json`;
9. Exact envelope shape (typed envelope V1 allowlist);
10. Envelope operation equals row operation;
11. Canonical `result_hash` recomputation match;
12. Deep-detached domain record returned.

Any step failure throws `IDEMPOTENCY_RECORD_INVALID`; a caller can never obtain an unverified record. Internal `private verifyRow(...)` / `parseEnvelope(...)` helpers are allowed but must not be exposed as skippable public API.

Forbidden on the repository: `update`, `delete`, list-all, raw-key lookup. Final public API is exactly `findVerifiedByScope` + `insertCompleted`. P1 does not touch `TaskRunService` or any route.

### P2 — Idempotency Service

Create:

- `apps/server/src/services/IdempotencyService.ts`
- `apps/server/src/services/IdempotencyService.test.ts`

Frozen P2 API (transactionless; receives repository + fingerprint inputs from the caller's transaction; no `unknown` remains):

```ts
prepare(input: {
  operation: IdempotencyOperation;
  workspaceId: string;
  normalizedKey: string | undefined;
  fingerprintInput: FingerprintInput;
}): PreparedIdempotency | undefined;

resolve(prepared: PreparedIdempotency): IdempotencyResolution;

type IdempotencyResolution =
  | { kind: 'miss' }
  | {
      kind: 'replay';
      httpStatus: 200 | 201;
      envelope: IdempotencyResultEnvelopeV1;
    };

storeSuccess(input: {
  prepared: PreparedIdempotency;
  httpStatus: 200 | 201;
  envelope: IdempotencyResultEnvelopeV1;
}): IdempotencyRecord;
```

Frozen requirements: a different well-formed request does NOT return `kind: 'conflict'` — `resolve` throws `IdempotencyKeyReusedError` (mapped to 409 `IDEMPOTENCY_KEY_REUSED` in P3). `normalizedKey` exists only for the duration of the `prepare` call; `PreparedIdempotency` never exposes the raw or normalized key and carries only `key_hash`, operation, workspace, and `request_hash`. `storeSuccess` rejects non-2xx statuses and rejects an envelope whose operation does not match the prepared operation. `IdempotencyService` never begins, commits, rolls back, or calls `runInTransaction`.

Requirements: exact request hash; exact result hash; same-request replay; different-request conflict; corrupted result fail closed; success-only persistence; no raw key exposure. P2 does not touch routes or `TaskRunService`.

#### P3.1 — TaskRunService Integration Seam (frozen)

`TaskRunServiceDeps` does NOT gain a required idempotency accessor (that would expand every Legacy/test callsite). Instead:

- `TaskRunServiceOptions` gains an optional `idempotencyService?: IdempotencyService` (alongside the existing optional `resolver`).
- New server-internal result type:

```ts
interface V2MutationExecutionResult<TBody> {
  httpStatus: 200 | 201;
  body: TBody;
  replayed: boolean;
}
```

- Six additive v2-only methods return `V2MutationExecutionResult<...>`:

```ts
createTaskForV2(...)
createRunForV2(...)
cancelQueuedRunForV2(...)
acceptRunForV2(...)
cancelTaskForV2(...)
reopenTaskForV2(...)
```

- Existing methods keep their exact current signatures and return types — `createTask(...)`, `createRun(...)`, `cancelQueuedRun(...)`, `acceptRun(...)`, `cancelTask(...)`, `reopenTask(...)` — and all existing direct callers are unchanged.
- New private in-transaction helpers share the guard/mutation logic between existing methods and the `*ForV2` methods, avoiding nested transactions and logic duplication.
- The route store surface uses an independent intersection type:

```ts
TaskRunServiceDeps & { idempotencyRepository(): IdempotencyRepository }
```

Only v2 routes and their test fixtures require the new accessor; Legacy, Recovery, Bridge, and old lifecycle fixtures are never forced to inject an idempotency repository.

#### P3.2 — Route Result Contract (frozen)

v2 route flow: (1) `parseIdempotencyKey(req)`; (2) parse `expectedVersion`; (3) call the matching `*ForV2` method; (4) when `result.replayed === true`, set header `Idempotency-Replayed: true`; (5) respond with `res.status(result.httpStatus).json(result.body)`.

Frozen rules: `Idempotency-Replayed: false` is never set; first-result statuses are `task.create`/`run.create` → 201, the other four operations → 200; replay preserves the first-result status; without a key the body/status semantics are exactly today's behavior; both live and replay bodies come from the typed envelope (`envelope.body`), never from divergent DTO shapes.

### P4 — Optional Optimistic Concurrency API

Scope: `run.cancel`, `task.accept`, `task.cancel`, `task.reopen` only. Frozen rules: `expectedVersion` optional; positive safe integer when present; absent preserves current behavior; checked inside the transaction; `VERSION_CONFLICT` fixed safe response without `currentVersion`; `expectedVersion` participates in the fingerprint; same-key successful replay returns before the version guard.
