## 1. Executive Summary

M2.4 的目标是在数据模型层把 Task（长期工作意图）与 Run（一次执行尝试）分离，这是 domain-gap-analysis 中唯一 CRITICAL 级且尚未处理的领域冲突（Q1: Task == Run）。

当前系统存在两条执行路径：

1. **Legacy Pipeline 路径**（`POST /api/workspaces/:workspaceId/tasks/:taskId/run`）：TaskItem 存储在 `workspace/{id}/.agentos/tasks.json`，执行结果（`outputs: TaskLog[]`）、执行状态（`running`/`reviewing`）直接写在 Task 上，浏览器断开 SSE 会取消执行。没有独立 Run 实体。
2. **Conversation 路径**（`ConversationService`）：已有 SQLite `agent_runs` 表，但它绑定 Conversation + Message，缺少 `taskId`、`parentRunId`、`rootRunId`、结构化错误字段，且 `updateRun` 不使用 version 乐观并发。

M2.4 的交付物（冻结范围）：

- 新增 canonical `tasks` 表（Migration 005）与 canonical `runs` 表（Migration 006）；
- 新增 `TaskRepository` / `RunRepository`（version 乐观并发、状态机守卫）；
- 新增 v2 Task/Run REST API（工作区隔离、稳定错误码）；
- Legacy Pipeline Bridge：旧 `/tasks/:taskId/run` 路由内部 find-or-create v2 Task 并持久化 durable Run；Legacy URL、挂载点、请求响应、SSE payload 和 JSON 数据契约不变，`tasks.ts` 内部只追加计划冻结的 Bridge 持久化逻辑；
- 不修改 `agent_runs`、`executions`、`run_steps`、ConversationService、RunStepService、agent-core、Web。

M2.4 明确不做：tasks.json 全量迁移（M2.7）、Snapshot（M2.5）、Idempotency-Key 与 API 级乐观并发（M2.6）、事件发布管线（M3）、执行引擎解耦（M3）。

## 4. Architecture Invariants

以下来自 Runtime Specification 的不变量直接约束 M2.4 设计：

1. Task ≠ Run（01 §2, §47.2；02 §61.1；10 §173.2）。
2. Retry 必须创建新 Run，不得重置或覆盖历史 Run（01 §47.5；02 §61.3）。
3. 浏览器断线不得取消 Run、不得作为执行生命边界（01 §47.12；02 §61.4；03 §79.6）。
4. Run completed ≠ Task done；Task done 需要接受（acceptance）（02 §5.6, §61.13；03 §79.22）。
5. 所有可变 Aggregate 使用 version 乐观并发（02 §45；10 §173.14）。
6. Workspace 是所有项目对象的主边界；Task 必须属于 Workspace（01 §5.3, §13.4；10 §173.1）。
7. ID 应用层生成、带前缀、创建后不变（01 §3.3；10 §6）。
8. Runtime Event append-only；同一 Run 内 sequence 唯一递增（01 §47.4；03 §79.4）。M2.4 为 v2 Run 预留 `next_event_sequence`，但事件发布管线属于 M3，M2.4 不写 v2 runtime event（见 §14 明确排除项与 §42 风险 R-7）。
9. v1 固定四阶段只能作为 Workflow Template 存在（02 §61.25）。M2.4 不改造四阶段执行本身，只在数据层记录其 Run。
10. 渐进迁移：现有可用功能通过兼容层逐步迁移，不一次性破坏（00 §11.11；02 Part XXVII）。

### 5.1 Legacy TaskItem

- **TypeScript 类型**（`packages/shared/src/types/index.ts`）：

```ts

export interface TaskItem {
  id: string;                      // randomUUID().slice(0, 8)，8 字符，无前缀
  workspaceId: string;
  title: string;
  status: TaskStatus;
  currentAgent: AgentStage | null; // AgentStage 是固定联合类型

  reviewBlocked?: boolean;

  updatedAt: string;

export interface TaskLog {
  stage: AgentStage;               // 'codex_manager' | 'kimi_worker' | 'opencode_reviewer' | 'codex_final_review'
```

### 5.3 Existing Pipeline Task Execution

`POST /api/workspaces/:workspaceId/tasks/:taskId/run`（`routes/tasks.ts`）完整生命周期：

1. 校验 workspace（404）、加载 TaskItem（404）。
2. `claimTaskRun(task)`：若 `status === 'running'` 返回 409 `Task is already running`；否则置 `running`。
3. 重置：`outputs = []`、`error = undefined`、`reviewDecision = 'unknown'`、`reviewBlocked = false`，写 JSON。
4. 开启 SSE（`text/event-stream`），发送 `status(running)`；启动心跳。
5. 依次执行四个固定 stage（`codex_manager` → `kimi_worker` → `opencode_reviewer` → `codex_final_review`）：
   - `runStage()`：stage 开始 → 写 `currentAgent` + JSON + SSE `stage(running)`；stage 完成 → push log 到 `outputs` + JSON + SSE `stage(completed, log)`；
   - worker evidence 缺失时置 `reviewBlocked = true` 并发 SSE `status(reviewing)`；
   - `applyFinalReviewDecision()` 写最终 `status/reviewDecision/reviewBlocked`；
   - `thinking` 事件实时转发 AgentRunner 输出。
6. 终态：成功 → SSE `status` + `done`；异常 → `applyStageFailure()`（status `failed`）或取消分支（status `cancelled`，error=`任务的实时连接已关闭，执行已取消。`）。
7. **Browser close / AbortController**：`res.on('close', ...)` → `abortController.abort()`。**浏览器断开 SSE 即取消整个 Pipeline**——这直接违反 spec 不变量「浏览器断线不得取消 Run」（01 §47.12）。证据：`tasks.ts` 末尾 `res.on('close')` 处理器。
8. **cancellation**：只由浏览器断连触发；没有显式 cancel API。
9. **failure**：stage 抛错 → `applyStageFailure()`，任务 status `failed`，错误文本进 `task.error`。
10. **final review**：见 §5.1 reviewDecision/reviewBlocked。
11. **JSON 写入次数**：单次成功执行至少 10 次整文件原子重写（claim、reset、4×stage 开始、4×stage 完成、reviewBlocked、final decision，另有 `onActivity` 高频追加写）。每次都是 `loadTasks → 全量改写 → rename`。

## 11. Recommended Decisions

### Decision 1 — Task Status Vocabulary

- **Spec A**（01-Core-Concepts §13.3/§13.5 + 02-Runtime-Lifecycle §5.5）：Task `open | in_progress | blocked | done | cancelled`；priority `low | normal | high | critical`；Run `queued | starting | running | waiting_approval | paused | completed | failed | cancelled`（8 态）。
- **Spec B**（10-Data-Model §26/§28 + 11-API-Specification §67-69）：Task `draft | ready | running | review | completed | cancelled | archived`；priority `low | normal | high | urgent`；Run 13 态（含 `created/validating/planning/preparing/cancelling/recovery_required`）；生命周期命令 `ready/cancel/reopen/archive/restore`。
- **Current Implementation**：legacy `pending | running | reviewing | completed | failed | cancelled`；`agent_runs` 6 态无 CHECK。
- **Options**：
  - A：采用 01/02 词汇表。理由：01 自我声明为核心概念语义最高权威（「后续文档与代码不得随意改变本文件中核心概念的语义」），02 与 01 一致；2 对 2 平手中 01+02 是概念层、10+11 是数据/API 层；`done` 与 acceptance 语义在 02 §5.5 有完整状态机可直接落地；spec 11 的 `ready/archive` 命令未来可作为扩展状态加入（CHECK 可通过新 Migration 放宽）。
  - B：采用 10/11 词汇表。理由：API 层已按 B 写死命令集；但 `running/review` 作为 Task 状态重新混淆意图与执行，正是 M2.4 要消除的核心冲突。
  - C：保留 legacy 词汇表。拒绝——它正是领域冲突本体。
- **Recommended Decision**：**A 系**。v2 Task：`open | in_progress | blocked | done | cancelled`；priority：`low | normal | high | critical`；v2 Run：01 的 8 态（M2.4 实际只用 `queued/running/completed/failed/cancelled` 子集，但 CHECK 一次到位，避免后续 ALTER 重建表）。
- **Compatibility Impact**：legacy TaskStatus 不变；映射见 §6。`agent_runs` 状态不变。
- **Migration Impact**：005/006 的 CHECK 按 A 系落盘；若 Owner 改判 B 系，005/006 的 CHECK 与 §24/§25 状态机需同步改写（计划返工，成本中等）。
- **API Impact**：v2 请求/响应与错误码按 A 系；B 系的 `ready/archive/restore` 命令不提供。
- **Test Requirement**：T01-T15（schema/FK）、T50-T67（TaskRunService）、T68-T92（v2 API）、T111-T121（acceptance window、终态归并与取消清理）。
- **Owner Decision Recorded**：OD-1 已于 2026-07-23 批准并完成状态关系澄清。
- **Owner Decision（2026-07-23）：APPROVED WITH CLARIFICATION。** 采用 A 系词汇表（Task `open | in_progress | blocked | done | cancelled`；Priority `low | normal | high | critical`；Run 8 态 `queued | starting | running | waiting_approval | paused | completed | failed | cancelled`），并附带以下强制状态关系澄清（已并入 §24/§25）：
  1. 创建 `queued` Run **不会**把 Task 改为 `in_progress`；
  2. Task 只在 Run 实际进入 `running` 时才进入 `in_progress`；
  3. `queued` Run 被取消后，Task 保持或恢复 `open`；
  4. `completed` Run 不自动使 Task `done`；
  5. acceptance 后 Task 才进入 `done`。

### Decision 2 — Run Table Strategy

- **Spec A**（10-Data-Model §29）：canonical `runs` 表（task_id NOT NULL、parent_run_id、root_run_id、next_event_sequence 等）。
- **Spec B**（m2-migration-plan M2.4 草稿）：「Run — enhanced from AgentRun: add taskId, parentRunId, rootRunId, errorCode, errorMessage, reason, version」。
- **Current Implementation**：`agent_runs`：`conversation_id`/`source_message_id` 均 NOT NULL + FK；被 `executions`、`run_steps`、`run_cli_invocations`、`run_file_changes`、`run_decisions`、`runtime_artifacts`、`run_memory_usage`、`memory_candidates`、`preference_applications`、`preference_evidence` 等 10+ 表 FK 引用。
- **Options**：
  - A. **新建 canonical `runs` 表**：`task_id NOT NULL`；无 conversation/message 列；`agent_runs` 原样保留为 Conversation 执行事实源。
  - B. 扩展 `agent_runs`：加 `task_id` 等列；但 Task 型 Run 没有 Conversation/Message，必须放宽两个 NOT NULL——SQLite 不支持 ALTER COLUMN，需禁 FK、重建表、拷贝数据、重建全部索引，并级联处理 10+ FK 依赖表；或用占位 Conversation/Message 伪造（违反「不得伪造」原则）。
  - C. 先扩展 `agent_runs`，M2.7/M3 再迁移成 `runs`：同 B 的重建成本，且多一次未来数据迁移。
  - D. 其他：无更优。
- **Recommended Decision**：**A**。理由：spec 10 §29 已定义 canonical `runs`；避免在 M2.4 做高风险表重建；Conversation Run 与 Task Run 边界清晰（双表事实源风险见下，用归属边界控制）。
- **双表事实源风险评估与对策**：`agent_runs`（Conversation 执行）与 `runs`（Task 执行）并存形成两个 Run 事实源。控制措施：① 写入归属互斥——ConversationService 只写 `agent_runs`，v2 API/Bridge 只写 `runs`；② 查询分离——现有 `GET /runs`（conversation 维度）读 `agent_runs`，v2 API 读 `runs`，不交叉；③ 文档化统一时点——M3 Conversation Runtime 重构时决策是否统一两者，超出 M2.4。
- **Migration Impact**：纯 CREATE TABLE（006），零数据迁移。
- **API Impact**：v2 Run API 只读写 `runs`。
- **Test Requirement**：T01-T15（schema/FK）、T16-T29（TaskRepository）、T30-T49（RunRepository）、T50-T67（Service）、T68-T92（API）、T93-T105（Bridge）、T106-T108（persistence）、T109-T121（state closure）。
- **Owner Decision Recorded**：OD-2 已于 2026-07-23 批准；总计划中的旧 B/C 草稿必须按本修订同步。
- **Owner Decision（2026-07-23）：APPROVED。** 新建 `tasks` 与 `runs` 表；完全不修改 `agent_runs`、`executions`、`run_steps`、ConversationService、RunStepService。补充约束（已并入 §7 与 §14）：
  1. `runs` 是 M2.4 的 canonical **Task Run** 表；
  2. `agent_runs` 暂时是 **Conversation Run** 表；
  3. 两者写入归属互斥；
  4. M3 Conversation Runtime 决定最终统一方式；
  5. **不得声称 M2.4 已经形成全系统唯一 Run 事实源**。

### Decision 5 — Legacy TaskItem Identity

- **明确结论**：
  - Legacy 8 字符 ID **不直接成为** v2 Task ID（无前缀、熵过低、违反 01 §3.3）。

### Decision 6 — Legacy Pipeline Bridge

Legacy URL、挂载点、请求响应、SSE payload 和 JSON 数据契约不变；`tasks.ts` 内部只允许追加计划冻结的 Bridge 持久化逻辑。精确顺序冻结为：

1. 读取 Legacy `TaskItem`。
2. `claimTaskRun` 只做内存状态检查，不写 SQLite。
3. 调用 `TaskRunService.createLegacyRunForBridge` 的单一 SQLite 事务：find-or-create v2 Task，并创建 `queued` v2 Run；Task 仍为 `open`。
4. Legacy JSON reset + `saveTask(running)`。
5. JSON 写入成功后，调用 `TaskRunService.startRunForBridge`：Run `queued→running`，Task `open→in_progress`。
6. 执行既有四阶段 Pipeline，保持所有 JSON 写入点与 SSE payload 不变。
7. Legacy 终态 JSON 保存成功后，调用 `TaskRunService.completeRunForBridge`、`failRunForBridge` 或 `cancelRunForBridge`，在一个 SQLite 事务中写 Run 终态与 Task 状态。
8. Bridge 忠实记录 Legacy 断连造成的 `cancelled`，不声称修复断连取消这一已知 Runtime 违规。

重复 active Run 由内存 claim 与数据库唯一索引共同防守；唯一索引冲突转为 `RUN_ACTIVE_EXISTS`，不得遗留 active queued Run。

补偿契约：

- 第 4 步 JSON claim save 失败：`compensateLegacyClaimFailure` 在同一事务中先读取 Task、调用 `RunRepository.failQueuedBridgeClaim` 写 Run `failed` 与 `failure_code='BRIDGE_CLAIM_FAILED'`，再调用 `resolveTaskAfterRunTerminal(task, terminalRun)`。pending 存在时 Task 保持 `in_progress` 与原指针；无 pending 且无其他 active Run 时 Task 为 `open`；提交后显式抛出原始 JSON 错误。T98 是初始 claim、无 pending 的 Bridge 集成场景。普通 `transitionStatus(..., 'failed')` 不允许 queued Run 失败。
- 第 7 步终态 JSON save 失败：Service 原子写 Run `failed`、`failure_code='BRIDGE_TERMINAL_SAVE_FAILED'`，并通过 `resolveTaskAfterRunTerminal(task, terminalRun)` 决定 Task：pending 存在时保持 `in_progress` 与原指针，否则无 active Run 时回 `open`；不得吞掉原始 JSON 错误。
- 补偿本身失败：保留原始错误与补偿错误的结构化记录，使用 `BRIDGE_COMPENSATION_FAILED` 作为外层错误码并显式抛出；禁止静默吞掉 SQLite、JSON 或未知错误。

- **Owner Approval Required**：否。

### Decision 7 — Browser / SSE Disconnect

- **当前行为**：legacy SSE `res.on('close')` → `abortController.abort()` → Task `cancelled`（违反 01 §47.12 / 02 §61.4）。
- **M2.4 是否改变此行为**：**不改变**。行为修复超出「数据模型分离」范围，且需要后台执行引擎（M3 ProcessManager/RunEngine）支撑才有意义。
- **新 v2 Run API 是否脱离 HTTP 生命周期**：**是，天然脱离**。M2.4 的 v2 API 不提供 SSE 执行端点；Run 行在创建时即 durable；M2.4 内 v2 API 创建的 Run 不触发执行（执行语义见 OD-5 与 §14）。
- **Legacy SSE Path 是否暂时保留**：是，原样保留（含断连取消）。
- **行为变更是否超出范围**：是，故冻结并文档化为已知违规（§8、§42 R-4）。
- **对应测试和后续里程碑**：M2.4 测试锁定 Bridge 对断连取消的忠实记录，并验证 JSON/SQLite 补偿及专用 queued failure（T98-T103、T109-T110）；行为修复测试归 M3（02 §52 Scenario D）。
- **Owner Decision（2026-07-23）：APPROVED WITH REQUIRED REVISION。** v2 POST runs 只创建 durable `queued` Run，不触发 AgentRunner、后台执行或 recovery；新增 queued Run cancel API。Legacy 断连取消保持现状并由 Bridge 记录为 `cancelled`。

### Decision 8 — Task and Run State Independence

（完整状态机见 §24/§25，此处为裁决要点。）

- 创建 `queued` Run 不改变 Task 状态；仅 Run 实际 `queued→running` 时才把 Task `open→in_progress`。
- Run `completed` → **不自动** Task `done`；Task 保持 `in_progress` 直到 acceptance（02 §5.6）。
- Run `failed` 或 `cancelled` → 统一由 `resolveTaskAfterRunTerminal` 归并：若 `pending_result_run_id` 非空，Task 保持 `in_progress` 且保留指针、`acceptedRunId`、`completedAt`；否则仅在无其他 active Run 时回 `open`。
- 当前 M2.4 只允许每 Task 一个 active Run；全部 Run 终态、无 `pending_result_run_id` 且未 acceptance → `open`；pending 非空时保留 `in_progress` acceptance window。
- Retry：创建 queued Run 本身不推进 Task；已有 pending 时 Task 因既有 acceptance window 保持 `in_progress`，无 pending 时保持/回到 `open`；只有该新 Run 实际进入 `running` 才推进 `in_progress`。
- **User Acceptance**：v2 `POST /api/workspaces/:workspaceId/v2/tasks/:taskId/accept`（body: `runId`），要求当前 Task `in_progress`、`pending_result_run_id` 非空、该 Run `completed`、同 Task/Workspace 且无其他 active Run；任一 completed 候选（包括较早 Run）均可接受 → Task `done` + `accepted_run_id` + `completed_at`，并清 pending。
- **acceptedRunId/pendingResultRunId**：独立列，completed 时写 pending；accept 时写 accepted 并清 pending；`cancelTask` 对非 done Task 固定写 `acceptedRunId=null`、`pendingResultRunId=null`、`completedAt=null`；reopen 时全部清空。
- **cancelled Task 是否允许新 Run**：不允许（409 `TASK_CANCELLED`），须先 `reopen` → `open`（02 §5.5 cancelled → reopen → open）。
- **failed Run 是否改变 Task 的用户意图**：不改变。失败是执行事实；意图终结只能由用户 cancel 或 acceptance 产生。
- **Owner Approval Required**：否。

### Decision 9 — Retry Semantics

- Initial Run：`parentRunId = null`，`rootRunId = self id`（Repository insert 时计算并校验）。
- Retry：`parentRunId = source Run.id`，`rootRunId = source.rootRunId`。
- Review Fix：新 Run（`reason='review-fix'`），不修改旧 Run 任何字段。
- Provider Comparison：多个 sibling Run（各自 `parentRunId` 指向同一 source 或同为 initial，共享 `rootRunId`）。
- 历史 Run 不得因 Retry 被重置或覆盖：Repository 终态守卫——`completed/failed/cancelled` 后拒绝一切状态迁移（T41、T45、T48）。
- Legacy Bridge 重跑即 Retry（§11 D6 第 2 步）。
- **Owner Approval Required**：否。

### Decision 10 — M2.4 与后续包边界

见 §14 Explicit Out of Scope：M2.5 Snapshot 全部；M2.6 Idempotency-Key 与 API 级乐观并发；M2.7 tasks.json 全量迁移/JSON Cutover/旧执行历史批量生成 Run；M3+ Event Store 重构、ProcessManager、ProviderAdapter、Worktree Runtime、Conversation Runtime、Web UI。

- **Owner Approval Required**：否。

```sql
  FOREIGN KEY (task_id, workspace_id)
    REFERENCES tasks(id, workspace_id) ON DELETE CASCADE,
  FOREIGN KEY (parent_run_id, task_id)

  ON runs(workspace_id, task_id, created_at ASC, id ASC);
```

## 19. Migration Rollback and Checksum Strategy

- 遵循既有 MigrationRunner 契约（m2-migration-plan §5 决策）：单 Migration 单事务（`BEGIN IMMEDIATE`）；失败整体回滚且不写 `_schema_migrations`；checksum 不匹配为硬失败；每个 Migration 应用后跑 `PRAGMA integrity_check` 与 `PRAGMA foreign_key_check`。
- 005/006 均为非破坏性 CREATE，无数据迁移，无需 pre-migration backup（与 003/004 同级处理）；但 composite FK/self FK 的可行性必须在真实 `node:sqlite` 数据库中验证，不能以 schema parse 成功代替。
- 回滚策略：forward-only。提交后发现问题 → 备份恢复或新修复 Migration（如 `007-*`），不修改已发布的 005/006 文件（checksum 不变性）。如果真实 SQLite 证明 self FK 方案不可行，保持 Plan Pending，提出 Trigger 或替代 schema，不静默删约束。
- 无 `down()`。F1 必须在真实 `node:sqlite`、`PRAGMA foreign_keys=ON` 下证明：
  1. initial Run 的 `root_run_id=self` 可 INSERT；
  2. 跨 Workspace Task/Run 组合被 FK 拒绝；
  3. 跨 Task parent/root 被 FK 拒绝；
  4. 删除 Workspace 级联清理 tasks/runs；
  5. 删除 Task 级联清理 runs；
  6. `PRAGMA foreign_key_check` 通过。

| `transitionStatus(workspaceId, runId, expectedVersion, to, extra?: { failureCode?; failureMessage? })` | 通用状态迁移；`queued→running/cancelled`、`running→completed/failed/cancelled`；`running` 写 `started_at`；终态写 `completed_at`；`failed` 写 `failure_code/message`；`cancelled` 写 `cancellation_requested_at` | **任何通用 queued→failed（包括携带 `BRIDGE_CLAIM_FAILED`）→ `INVALID_RUN_TRANSITION`**；其他非法迁移/终态后迁移 → Error；version 冲突 → `VersionConflictError` |
| `failQueuedBridgeClaim(workspaceId, runId, expectedVersion, failureMessage)` | **仅 Bridge claim 补偿专用**：验证 `origin='legacy_pipeline'`、status `queued`，原子写 `failed`、`failure_code='BRIDGE_CLAIM_FAILED'`、message、`completed_at=now`、version+1 | origin/status/version 不符 → `INVALID_RUN_TRANSITION`；不暴露为 v2 HTTP API |
| `listByWorkspace(workspaceId, opts?: { status? })` | 管理/调试读 | — |

终态守卫：`completed/failed/cancelled` 的 `ALLOWED_TRANSITIONS` 为空数组（对齐 RunStepService 既有模式）。`queued→failed` 不属于通用 `ALLOWED_TRANSITIONS`，只能经 `failQueuedBridgeClaim`。

### 20.3 SqliteStore 接线

`SqliteStore.ts` 最小改动：构造时实例化两个 repository（复用同一 db handle），暴露 `taskRepository()` / `runRepository()` 访问器。**不改动**任何既有方法（含 `loadTasks/saveTask/saveTasks/createRun/updateRun`）。Service 通过同一 db handle 建立跨 Repository 原子事务。

## 21. Service Design

新增 `apps/server/src/services/TaskRunService.ts`，由它承担所有跨 Repository 组合事务、Task/Run 状态机、workspace/task/run 归属校验、active Run 检查、acceptance 与稳定 domain error。**GET/LIST 读取路由可以在 WorkspaceManager 校验后直接调用单一 TaskRepository/RunRepository；所有创建、更新、状态迁移、accept、cancel、reopen、Bridge 和跨 Aggregate 操作必须调用 Service。** Route 不得直接组合两个 Repository，也不得直接执行 versioned UPDATE。

Service 的公开职责固定为：

1. `createTask`
2. `createRun`
3. `createLegacyRunForBridge`
4. `cancelQueuedRun`
5. `startRunForBridge`
6. `completeRunForBridge`
7. `failRunForBridge`
8. `cancelRunForBridge`
9. `acceptRun`
10. `cancelTask`
11. `reopenTask`

### 21.1 统一终态归并（冻结内部规则）

`resolveTaskAfterRunTerminal(task, terminalRun)` 是 `TaskRunService` 的内部规则，只能在同一 SQLite 事务中、当前 Run 已经写为 terminal 后调用；它可在该事务内确认是否还有其他 active Run。以下五条路径必须调用它：`cancelQueuedRun`、`compensateLegacyClaimFailure`、`failRunForBridge`、`cancelRunForBridge`、终态 JSON 保存失败补偿。

1. 若 `task.pendingResultRunId` 非空，任何 `failed`/`cancelled` terminal Run 都不得覆盖 acceptance window：Task 保持 `in_progress`，pending 指针原样保留，`acceptedRunId` 与 `completedAt` 原样保留；Run 自身写为失败或取消终态。
2. 若 pending 为空且不存在其他 active Run，失败或取消的 terminal Run 使 Task 回到 `open`。
3. `completeRunForBridge` 写 Run `completed` 后应用本规则的 completed 结果：Task 保持 `in_progress`，并将 `pendingResultRunId` 写为当前 completed Run.id；不得自动 done。
4. 该规则绝不扫描历史 completed Run 来恢复 pending 指针。
5. `reopenTask` 清空 `acceptedRunId`、`pendingResultRunId`、`completedAt`；历史 Run 不得影响 reopen 后的 Task，只有新 Run 真正进入 `running` 才能重新进入 `in_progress`。

`compensateLegacyClaimFailure` 仅由 Legacy claim JSON save failure 路径调用，不存在对应 HTTP API。它在一个事务中严格执行：读取 Task → `RunRepository.failQueuedBridgeClaim(...)` → `resolveTaskAfterRunTerminal(task, terminalRun)` → commit；随后显式抛出原始 JSON 错误。它保证 Task 不遗留错误的 active 状态，并依据 pending acceptance window 决定 `in_progress` 或 `open`。每个组合操作使用同一个 SQLite 事务边界；Service 不调用 AgentRunner、不管理后台调度、不把 `agent_runs` 与 `runs` 合并。

`acceptRun` 不要求传入 Run 等于 `pending_result_run_id`：只要 acceptance window 有效，任何属于同一 Task/Workspace 的 completed 候选（包括较早 Run）都可以被接受。`TaskRunService.acceptRun` 在同一事务内完成 Task/Run 的跨 Aggregate 校验（Task 为 `in_progress`、pending 非空、候选 Run completed 且同 Task/Workspace、无 active Run），然后调用 `TaskRepository.accept(workspaceId, taskId, expectedVersion, acceptedRunId)`；Repository 不读取或验证 Run。

`cancelTask` 仅在无 active Run 时执行：Task 写为 `cancelled`，清 `pendingResultRunId`，不修改任何历史 Run；由于可取消目标不是 done，固定同时写 `acceptedRunId=null`、`completedAt=null`。`reopenTask` 一律清 `acceptedRunId`、`pendingResultRunId`、`completedAt` 后转为 `open`。

`createLegacyRunForBridge(input)` 是 Legacy Bridge 唯一的 find-or-create 入口，输入至少为：

```ts
type CreateLegacyRunForBridgeInput = {
  workspaceId: string;
  legacyTaskId: string;
  title: string;
  createdBy: string;
  objective: string;
};

type CreateLegacyRunForBridgeResult = {
  task: Task;
  run: Run;
  taskCreated: boolean;
};
```

它在单一 SQLite 事务中依次执行：`findByLegacyTaskId` → 未命中时 `insert Task` → `findLatestByTask` → 推导 `initial/retry` → `insert queued Run` → 返回 `{ task, run, taskCreated }`。唯一约束冲突映射为稳定 domain error；Route 不得手工组合两个 Repository。并发调用不得生成重复 Task 或两个 active Run。

Bridge 辅助函数（纯函数，便于单测）放在新文件 `routes/taskRunBridge.ts`。排序不在 helper 中完成，Bridge 必须先调用 `RunRepository.findLatestByTask(workspaceId, taskId)`：

```ts
resolveBridgeRunReason(latestRun?: Run): { reason: 'initial' } | { reason: 'retry'; parentRunId: string }
mapLegacyTerminalToRunUpdate(terminal: 'completed' | 'failed' | 'cancelled', error?: string): { to: V2RunStatus; failureCode?: string; failureMessage?: string }
```

## 24. Task State Machine

```
open
  ├── 创建 queued Run → open（不推进）
  ├── Run 实际 queued→running → in_progress
  └── user cancel（无活跃 Run） → cancelled（清 pending；非 done Task 的 acceptedRunId/completedAt 均为 null）

in_progress
  ├── Run completed → in_progress，并写 `pending_result_run_id=run.id`
  ├── 后续 retry failed → 若 `pending_result_run_id` 非空则仍 in_progress，否则无 active Run 时 → open
  ├── 后续 retry cancelled → 若 `pending_result_run_id` 非空则仍 in_progress，否则无 active Run 时 → open
  ├── acceptance（任一同 Task/Workspace 的 completed Run；Task 仍 in_progress、pending 非空、无 active Run） → done
  └── user cancel（无活跃 Run） → cancelled（清 pending；历史 Run 不变）

blocked
  ├── create Run → 409 `TASK_BLOCKED`
  └── M2.4 无 blocked 产生方；保留状态供后续里程碑

done
  ├── create Run → 409 `TASK_DONE`
  └── reopen → open（清 accepted_run_id / pending_result_run_id / completed_at）

cancelled
  ├── create Run → 409 `TASK_CANCELLED`
  └── reopen → open（清 accepted_run_id / pending_result_run_id / completed_at）
```

守卫：cancel 时存在活跃 Run → 409 `TASK_HAS_ACTIVE_RUN`；`cancelTask` 不读取或改写历史 Run，且必须清 pending；blocked/done/cancelled 创建 Run 分别返回 `TASK_BLOCKED`/`TASK_DONE`/`TASK_CANCELLED`；accept 的跨 Aggregate 校验仅由 Service 执行：当前 Task 为 `in_progress`、`pending_result_run_id` 非空、Run completed、同 Task/Workspace 且不存在其他 active Run，否则返回 `TASK_NO_ACCEPTANCE_WINDOW`、`RUN_NOT_COMPLETED`、404 或 `TASK_HAS_ACTIVE_RUN`。历史 completed Run 本身不可变，但 reopen 后不会重新设置 pending result。

## 25. Run State Machine

```
queued
  ├── Legacy Bridge JSON 成功后 → running
  └── v2 queued Run cancel API → cancelled（`cancelQueuedRun` 经统一归并释放 active slot）
  └── Legacy claim JSON save compensation → failed
      仅当 origin=`legacy_pipeline` 且 failure_code=`BRIDGE_CLAIM_FAILED`
      且只能由 `failQueuedBridgeClaim` 调用；通用 transitionStatus → INVALID_RUN_TRANSITION

running
  ├── pipeline 成功 → completed
  ├── pipeline 异常 → failed
  └── 断连取消 → cancelled

starting / waiting_approval / paused   （CHECK 预留，M2.4 无生产写入方）

completed / failed / cancelled         （终态，ALLOWED_TRANSITIONS = []）
```

守卫：终态后任何迁移 → Error（历史不可变，D9）；`failed` 必须携带 `failure_code`；`cancelled` 必须写 `cancellation_requested_at`。普通 `transitionStatus` 只允许 `running→failed`，不允许任意 queued Run → failed；v2 HTTP API 不提供 queued→failed。v2 cancel 对 running/starting/waiting_approval/paused 及所有终态均返回 409 `RUN_NOT_CANCELLABLE`；不得调用 ProcessManager。Legacy Bridge 的 running Run 不受此 v2 API 中止。

## 26. Retry / Parent / Root Rules

（即 §11 D9 冻结。）Repository `insert` 强制：

- `reason='initial'` → 禁止携带 `parentRunId`；`root_run_id = 自身 id`。
- `reason IN ('retry','resume-fallback','review-fix')` → 必须携带同 Task 的 `parentRunId`；`root_run_id = parent.root_run_id`。
- `reason='provider-comparison'` → `parentRunId` 可选；携带时同上，不携带时 `root_run_id = 自身 id`（独立比较树）。
- `reason='manual'` → 同 initial 规则。
- Bridge 自动推导：调用 `findLatestByTask(workspaceId, taskId)`；无历史 Run → `initial`；有 → `retry` + 返回 Run 为 parent（`resolveBridgeRunReason(latestRun)`，T108）。Retry 保留既有 `pending_result_run_id`；只有新 Run completed 才把 pending 指针替换为新 Run。

## 27. Cancellation Rules

- v2 Task cancel：仅无活跃 Run 时允许（409 `TASK_HAS_ACTIVE_RUN`）；只取消意图，不杀执行，写 Task `cancelled` 并清 `pendingResultRunId`，不修改历史 Run；对非 done 的可取消 Task，`acceptedRunId` 与 `completedAt` 固定为 null。reopen 再次清理 accepted/pending/completed 后回 `open`。
- v2 Run cancel：仅提供 `/api/workspaces/:workspaceId/v2/runs/:runId/cancel`；`cancelQueuedRun` 先将 queued Run 写为 cancelled，再调用 `resolveTaskAfterRunTerminal` 并释放 active slot：初始 queued、无 pending → Task `open`；retry queued、已有 pending → Task `in_progress` 且 pending 指针保留。running/starting/waiting_approval/paused/terminal → 409 `RUN_NOT_CANCELLABLE`。不触发 ProcessManager，也不允许中止 Legacy Bridge 的 running Run。
- Legacy 断连取消：行为不变（D7 冻结）；Bridge 忠实记录 v2 Run `cancelled`。
- 取消与完成竞态：Service 事务、repository version guard + 终态守卫保证只有一个胜者。

## 28. Transaction Boundaries

| 操作 | 事务内容 | 备注 |
|---|---|---|
| v2 Task 创建 | `TaskRunService.createTask` 单 INSERT | route 不直接调用 repository |
| v2 Run 创建（API） | `TaskRunService.createRun`：同一事务读 Task/active Run → INSERT Run | queued 创建后 Task 仍 `open`；活跃索引冲突回滚 |
| v2 queued Run cancel | `TaskRunService.cancelQueuedRun`：同一事务 queued→cancelled → `resolveTaskAfterRunTerminal` | 无 pending → `open`；有 pending → `in_progress` 且原指针保留；HTTP 响应与错误码不变 |
| Bridge claim + create | `TaskRunService.createLegacyRunForBridge`：同一事务 find-or-create Task + `findLatestByTask` + INSERT queued Run | JSON reset/save 在事务外；失败按 §23 补偿 |
| Bridge claim compensation | `TaskRunService.compensateLegacyClaimFailure`：同一事务读 Task → `RunRepository.failQueuedBridgeClaim` → `resolveTaskAfterRunTerminal` | 仅 `legacy_pipeline` + queued + `BRIDGE_CLAIM_FAILED`；pending 决定 `in_progress` 或 `open`；commit 后抛原 JSON 错误；普通 transition/API 拒绝 |
| Bridge start | `TaskRunService.startRunForBridge`：同一事务 Run queued→running + Task open→in_progress | JSON 成功后才执行；已有 pending 指针保留 |
| Bridge 终态同步 | `complete/fail/cancelRunForBridge`：同一事务写 Run 终态；completed 写/替换 pending_result_run_id，fail/cancel 必须调用 `resolveTaskAfterRunTerminal` | pending 决定 `in_progress` 或 `open`；不得扫描历史 completed Run |
| terminal JSON save failure compensation | 同一事务写 Run `failed` + `BRIDGE_TERMINAL_SAVE_FAILED` → `resolveTaskAfterRunTerminal` | pending 保持 Task `in_progress` 与指针；否则无 active Run 时 `open`；原 JSON 错误不得吞掉 |
| accept/cancel/reopen | `acceptRun` 在 Service 做跨 Aggregate 校验后调用纯 Task 的 Repository accept；cancel/reopen 按 §21/§27 清理指针 | route 只映射错误 |

不在 Provider/Pipeline 执行期间持有数据库事务（10 §173.37）：Bridge 只在执行前/终态后开短事务。

## 29. Workspace Isolation

- 所有 v2 查询 `(workspace_id, id)` 双条件；列表强制 `workspace_id`。
- 路由先 `workspaceManager.get(:workspaceId)` → 404 `WORKSPACE_NOT_FOUND`。
- 跨工作区访问 Task/Run → 404（与不存在无差别，不泄露）。
- `runs.workspace_id` 冗余列（与 tasks.workspace_id 一致写入），支持按工作区直接扫描与恢复。
- 测试：T10-T12 覆盖数据库级跨 Workspace/Task FK；T65、T73-T77 覆盖 Service/API 级跨工作区拒绝。

## 31. Version Behavior

- `tasks.version` / `runs.version`：`INTEGER NOT NULL DEFAULT 1`；每次 UPDATE 经 `assertVersionedMutation` 递增；并发写产生唯一胜者，败者 `VersionConflictError`。
- API 响应包含 `version` 字段（只读暴露）。
- M2.4 API **不接收** `expectedVersion`/`If-Match`（API 级乐观并发属 M2.6）；route 内部读取当前 version 后立即在同一事务内使用。
- 与 M2.3 provider API 的差异（那边已强制 expectedVersion）是有意边界：Task/Run 的并发写方在 M2.4 只有单进程 route/bridge，version guard 是内部一致性保障而非外部契约。

## 43.1 Queued Legacy Bridge Startup Recovery Addendum

The queued crash-window remediation uses the Owner-approved startup orphan reconciliation design. It is intentionally not part of normal Retry handling: a queued `legacy_pipeline` Run may still belong to another live request, while a server restart establishes that the previous process owned the queued handoff.

The startup sequence is `new SqliteStore` → one `TaskRunService` → `recoverInterruptedTaskRuntime` (Legacy JSON running-task recovery, then per-workspace queued orphan recovery) → existing Conversation `recoverInterruptedRuns` → route construction → `app.listen`. Recovery failures propagate and prevent startup from continuing.

`RunRepository.failQueuedBridgeRestart` is separate from `failQueuedBridgeClaim`. It accepts only `legacy_pipeline` + `queued`, writes `failed` with `BRIDGE_PRESTART_INTERRUPTED` under a version guard, and leaves generic queued-to-failed transitions and v2 queued Runs rejected. `TaskRunService.recoverInterruptedLegacyQueuedRuns` performs one transaction per workspace, preserves pending acceptance windows through `resolveTaskAfterRunTerminal`, and does not read Legacy JSON, create Runs, alter parent/root, or touch `agent_runs`.

R17-R24 cover Window A, Window B, idempotency, v2 isolation, pending acceptance, running Legacy isolation, fail-closed rollback, and multi-workspace evidence using real persistent JSON and real `node:sqlite`. Current evidence is 9/9 for the independent taskRecovery collection, 140/140 for the seven-file M2.4 targeted collection, 446/446 for the final Server suite, 123/123 Agent Core, Build PASS, and `git diff --check` PASS.
