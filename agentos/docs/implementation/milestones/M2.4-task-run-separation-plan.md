## 1. Executive Summary

M2.4 的目标是在数据模型层把 Task（长期工作意图）与 Run（一次执行尝试）分离，这是 domain-gap-analysis 中唯一 CRITICAL 级且尚未处理的领域冲突（Q1: Task == Run）。

当前系统存在两条执行路径：

1. **Legacy Pipeline 路径**（`POST /api/workspaces/:workspaceId/tasks/:taskId/run`）：TaskItem 存储在 `workspace/{id}/.agentos/tasks.json`，执行结果（`outputs: TaskLog[]`）、执行状态（`running`/`reviewing`）直接写在 Task 上，浏览器断开 SSE 会取消执行。没有独立 Run 实体。
2. **Conversation 路径**（`ConversationService`）：已有 SQLite `agent_runs` 表，但它绑定 Conversation + Message，缺少 `taskId`、`parentRunId`、`rootRunId`、结构化错误字段，且 `updateRun` 不使用 version 乐观并发。

M2.4 的交付物（冻结范围）：

- 新增 canonical `tasks` 表（Migration 005）与 canonical `runs` 表（Migration 006）；
- 新增 `TaskRepository` / `RunRepository`（version 乐观并发、状态机守卫）；
- 新增 v2 Task/Run REST API（工作区隔离、稳定错误码）；
- Legacy Pipeline Bridge：旧 `/tasks/:taskId/run` 路由内部 find-or-create v2 Task 并持久化 durable Run，同时完全保留 JSON TaskItem 写入与 SSE 响应形状；
- 不修改 `agent_runs`、`executions`、`run_steps`、ConversationService、RunStepService、agent-core、Web。

M2.4 明确不做：tasks.json 全量迁移（M2.7）、Snapshot（M2.5）、Idempotency-Key 与 API 级乐观并发（M2.6）、事件发布管线（M3）、执行引擎解耦（M3）。

## 4. Architecture Invariants

以下来自 Runtime Specification 的不变量直接约束 M2.4 设计：

1. Task ≠ Run（01 §2, §47.2；02 §61.1；10 §173.2）。
2. Retry 必须创建新 Run，不得重置或覆盖历史 Run（01 §47.5；02 §61.3）。
3. 浏览器断线不得取消 Run、不得作为执行生命边界（01 §47.12；02 §61.4；03 §79.6）。
4. Run completed ≠ Task done；Task done 需要接受（acceptance）（02 §5.6, §61.13；03 §79.22）。
5. 所有可变 Aggregate 使用 version 乐观并发（02 §45；10 §173.14）。
6. Workspace 是所有项目对象的主边界；Task 必须属于 Workspace（01 §5.3, §13.4；10 §173.1）。
7. ID 应用层生成、带前缀、创建后不变（01 §3.3；10 §6）。
8. Runtime Event append-only；同一 Run 内 sequence 唯一递增（01 §47.4；03 §79.4）。M2.4 为 v2 Run 预留 `next_event_sequence`，但事件发布管线属于 M3，M2.4 不写 v2 runtime event（见 §14 明确排除项与 §42 风险 R-7）。
9. v1 固定四阶段只能作为 Workflow Template 存在（02 §61.25）。M2.4 不改造四阶段执行本身，只在数据层记录其 Run。
10. 渐进迁移：现有可用功能通过兼容层逐步迁移，不一次性破坏（00 §11.11；02 Part XXVII）。

### 5.1 Legacy TaskItem

- **TypeScript 类型**（`packages/shared/src/types/index.ts`）：

```ts
export type TaskStatus = 'pending' | 'running' | 'reviewing' | 'completed' | 'failed' | 'cancelled';

export interface TaskItem {
  id: string;                      // randomUUID().slice(0, 8)，8 字符，无前缀
  workspaceId: string;
  title: string;
  status: TaskStatus;
  currentAgent: AgentStage | null; // AgentStage 是固定联合类型
  outputs: TaskLog[];              // 执行结果直接嵌在 Task 上（核心领域冲突）
  lastActivityAt?: string;
  error?: string;
  reviewDecision?: 'approve' | 'reject' | 'modify' | 'unknown';
  reviewBlocked?: boolean;
  createdAt: string;
  updatedAt: string;
}

export interface TaskLog {
  stage: AgentStage;               // 'codex_manager' | 'kimi_worker' | 'opencode_reviewer' | 'codex_final_review'
  agentName: string;
  stdout: string;
  stderr: string;
  exitCode: number | null;
  timestamp: string;
  duration: number;
  mode?: 'real' | 'mock';
}
```

- **Status 枚举**：`pending | running | reviewing | completed | failed | cancelled`。其中 `running`/`reviewing`/`failed` 是执行态，不是意图态（domain-gap-analysis Q1）。
- **JSON 文件位置**：`workspace/{workspaceId}/.agentos/tasks.json`，结构 `{ tasks: TaskItem[] }`（`JsonFileStore.tasksFile()`）。
- **load/save 方法**：
  - `Store` 接口（`apps/server/src/store/Store.ts`）：`loadTasks(workspaceId)`、`saveTasks(workspaceId, tasks)`、`saveTask(workspaceId, task)`。
  - `SqliteStore`（`SqliteStore.ts:439-448`）：三个方法**全部直接委托** `this.legacy`（JsonFileStore），SQLite 中没有任何 Task 表。
  - `JsonFileStore`：原子写（临时文件 + rename），`saveTask` 为单条 upsert。
- **API**（`apps/server/src/routes/tasks.ts`，挂载于 `index.ts:108` → `/api/workspaces/:workspaceId/tasks`）：
  - `GET /` — 列出全部 TaskItem；
  - `POST /` — 创建 TaskItem（id 为 8 字符随机串，status `pending`），并向 `{rootPath}/agent-memory/TASKS.md` 追加一行（best-effort）；
  - `POST /:taskId/run` — SSE 执行四阶段 Pipeline（详见 §5.3）；
  - `GET /:taskId/logs` — 读 `{rootPath}/.agentos/logs/{taskId}/*.log`；
  - `GET /:taskId/status` — 返回单个 TaskItem。
- **Web 使用点**：`apps/web/src/lib/useTask.ts` 调用 `GET/POST /api/workspaces/:id/tasks`。经 `rg` 全仓验证：**useTask 没有任何 importer，是孤儿 hook**；`apps/web` 中没有任何对 `/tasks/:taskId/run`（SSE）的调用。当前 Web 实际使用 Conversation Run 路径（`page.tsx` 调 `/conversations/.../runs/...`、`/api/workspaces/:id/runs...`）。
- **Pipeline 使用点**：`routes/tasks.ts` 的 `POST /:taskId/run` 是唯一执行入口；`AgentRunner`（`@agentos/agent-core`）执行四个固定阶段。
- **outputs**：每次 run 开始时被清空（`task.outputs = []`），随后逐 stage push `TaskLog`。
- **currentAgent**：stage 开始/结束时读写；终态置 `null`。
- **reviewDecision / reviewBlocked**：由 `taskPipeline.ts` 的 `applyFinalReviewDecision()` 依据 final review 与 worker evidence 写入。
- **error**：`applyStageFailure()` 写入错误 message。
- **lastActivityAt**：`touchTaskActivity()` 在 stage 切换、log 追加、`onActivity` 回调时刷新。

### 5.3 Existing Pipeline Task Execution

`POST /api/workspaces/:workspaceId/tasks/:taskId/run`（`routes/tasks.ts`）完整生命周期：

1. 校验 workspace（404）、加载 TaskItem（404）。
2. `claimTaskRun(task)`：若 `status === 'running'` 返回 409 `Task is already running`；否则置 `running`。
3. 重置：`outputs = []`、`error = undefined`、`reviewDecision = 'unknown'`、`reviewBlocked = false`，写 JSON。
4. 开启 SSE（`text/event-stream`），发送 `status(running)`；启动心跳。
5. 依次执行四个固定 stage（`codex_manager` → `kimi_worker` → `opencode_reviewer` → `codex_final_review`）：
   - `runStage()`：stage 开始 → 写 `currentAgent` + JSON + SSE `stage(running)`；stage 完成 → push log 到 `outputs` + JSON + SSE `stage(completed, log)`；
   - worker evidence 缺失时置 `reviewBlocked = true` 并发 SSE `status(reviewing)`；
   - `applyFinalReviewDecision()` 写最终 `status/reviewDecision/reviewBlocked`；
   - `thinking` 事件实时转发 AgentRunner 输出。
6. 终态：成功 → SSE `status` + `done`；异常 → `applyStageFailure()`（status `failed`）或取消分支（status `cancelled`，error=`任务的实时连接已关闭，执行已取消。`）。
7. **Browser close / AbortController**：`res.on('close', ...)` → `abortController.abort()`。**浏览器断开 SSE 即取消整个 Pipeline**——这直接违反 spec 不变量「浏览器断线不得取消 Run」（01 §47.12）。证据：`tasks.ts` 末尾 `res.on('close')` 处理器。
8. **cancellation**：只由浏览器断连触发；没有显式 cancel API。
9. **failure**：stage 抛错 → `applyStageFailure()`，任务 status `failed`，错误文本进 `task.error`。
10. **final review**：见 §5.1 reviewDecision/reviewBlocked。
11. **JSON 写入次数**：单次成功执行至少 10 次整文件原子重写（claim、reset、4×stage 开始、4×stage 完成、reviewBlocked、final decision，另有 `onActivity` 高频追加写）。每次都是 `loadTasks → 全量改写 → rename`。

## 6. Legacy TaskItem Model

（即 §5.1 的冻结结论。）

- Legacy TaskItem **继续存在且语义不变**：JSON 文件、字段、状态枚举、outputs、reviewDecision、reviewBlocked、error、lastActivityAt 全部保留。
- M2.4 对 Legacy 路径的唯一改变是**追加** v2 Task/Run 持久化（Bridge），不改变任何既有读写行为。
- Legacy `TaskStatus` 与 canonical v2 状态的映射（Compatibility Projection，只读映射，不回写 JSON）：

| Legacy TaskStatus | v2 Task Projection | 说明 |
|---|---|---|
| `pending` | `open` | 从未运行或已复位 |
| `running` | `in_progress` | 有活跃执行 |
| `reviewing` | `in_progress` | 仍是执行中状态 |
| `completed` | `in_progress`（未接受） | legacy 的 completed 是「执行完成」，不等于 v2 `done`；Bridge 不自动接受 |
| `failed` | `open` | 执行失败，意图未终结（02 §5.5: all active runs end without acceptance → open） |
| `cancelled` | `open` | legacy cancelled 是执行被取消，意图仍在；v2 `cancelled` 只由用户显式取消意图产生 |

> 注意：上表是文档化映射，M2.4 实际持久化 v2 Task 状态时由 Bridge 按 §24 状态机直接写入，不做反向 JSON 投影。

## 11. Recommended Decisions

### Decision 1 — Task Status Vocabulary

- **Spec A**（01-Core-Concepts §13.3/§13.5 + 02-Runtime-Lifecycle §5.5）：Task `open | in_progress | blocked | done | cancelled`；priority `low | normal | high | critical`；Run `queued | starting | running | waiting_approval | paused | completed | failed | cancelled`（8 态）。
- **Spec B**（10-Data-Model §26/§28 + 11-API-Specification §67-69）：Task `draft | ready | running | review | completed | cancelled | archived`；priority `low | normal | high | urgent`；Run 13 态（含 `created/validating/planning/preparing/cancelling/recovery_required`）；生命周期命令 `ready/cancel/reopen/archive/restore`。
- **Current Implementation**：legacy `pending | running | reviewing | completed | failed | cancelled`；`agent_runs` 6 态无 CHECK。
- **Options**：
  - A：采用 01/02 词汇表。理由：01 自我声明为核心概念语义最高权威（「后续文档与代码不得随意改变本文件中核心概念的语义」），02 与 01 一致；2 对 2 平手中 01+02 是概念层、10+11 是数据/API 层；`done` 与 acceptance 语义在 02 §5.5 有完整状态机可直接落地；spec 11 的 `ready/archive` 命令未来可作为扩展状态加入（CHECK 可通过新 Migration 放宽）。
  - B：采用 10/11 词汇表。理由：API 层已按 B 写死命令集；但 `running/review` 作为 Task 状态重新混淆意图与执行，正是 M2.4 要消除的核心冲突。
  - C：保留 legacy 词汇表。拒绝——它正是领域冲突本体。
- **Recommended Decision**：**A 系**。v2 Task：`open | in_progress | blocked | done | cancelled`；priority：`low | normal | high | critical`；v2 Run：01 的 8 态（M2.4 实际只用 `queued/running/completed/failed/cancelled` 子集，但 CHECK 一次到位，避免后续 ALTER 重建表）。
- **Compatibility Impact**：legacy TaskStatus 不变；映射见 §6。`agent_runs` 状态不变。
- **Migration Impact**：005/006 的 CHECK 按 A 系落盘；若 Owner 改判 B 系，005/006 的 CHECK 与 §24/§25 状态机需同步改写（计划返工，成本中等）。
- **API Impact**：v2 请求/响应与错误码按 A 系；B 系的 `ready/archive/restore` 命令不提供。
- **Test Requirement**：T02/T03（CHECK 拒绝非法值）、T11-T15（状态机）、T26-T36（API 状态行为）。
- **Owner Approval Required**：**是（OD-1）**。

### Decision 2 — Run Table Strategy

- **Spec A**（10-Data-Model §29）：canonical `runs` 表（task_id NOT NULL、parent_run_id、root_run_id、next_event_sequence 等）。
- **Spec B**（m2-migration-plan M2.4 草稿）：「Run — enhanced from AgentRun: add taskId, parentRunId, rootRunId, errorCode, errorMessage, reason, version」。
- **Current Implementation**：`agent_runs`：`conversation_id`/`source_message_id` 均 NOT NULL + FK；被 `executions`、`run_steps`、`run_cli_invocations`、`run_file_changes`、`run_decisions`、`runtime_artifacts`、`run_memory_usage`、`memory_candidates`、`preference_applications`、`preference_evidence` 等 10+ 表 FK 引用。
- **Options**：
  - A. **新建 canonical `runs` 表**：`task_id NOT NULL`；无 conversation/message 列；`agent_runs` 原样保留为 Conversation 执行事实源。
  - B. 扩展 `agent_runs`：加 `task_id` 等列；但 Task 型 Run 没有 Conversation/Message，必须放宽两个 NOT NULL——SQLite 不支持 ALTER COLUMN，需禁 FK、重建表、拷贝数据、重建全部索引，并级联处理 10+ FK 依赖表；或用占位 Conversation/Message 伪造（违反「不得伪造」原则）。
  - C. 先扩展 `agent_runs`，M2.7/M3 再迁移成 `runs`：同 B 的重建成本，且多一次未来数据迁移。
  - D. 其他：无更优。
- **Recommended Decision**：**A**。理由：spec 10 §29 已定义 canonical `runs`；避免在 M2.4 做高风险表重建；Conversation Run 与 Task Run 边界清晰（双表事实源风险见下，用归属边界控制）。
- **双表事实源风险评估与对策**：`agent_runs`（Conversation 执行）与 `runs`（Task 执行）并存形成两个 Run 事实源。控制措施：① 写入归属互斥——ConversationService 只写 `agent_runs`，v2 API/Bridge 只写 `runs`；② 查询分离——现有 `GET /runs`（conversation 维度）读 `agent_runs`，v2 API 读 `runs`，不交叉；③ 文档化统一时点——M3 Conversation Runtime 重构时决策是否把 `agent_runs` 并入 `runs`（10 §29 的 `runs.task_id NOT NULL` 意味着统一还需先解决 Conversation Run 的 Task 归属，超出 M2.4）。
- **Migration Impact**：纯 CREATE TABLE（006），零数据迁移。
- **API Impact**：v2 Run API 只读写 `runs`。
- **Test Requirement**：T01-T06（schema）、T16-T25（repository）、T29-T33（API）、T37-T42（bridge）。
- **Owner Approval Required**：**是（OD-2）**——与 m2-migration-plan M2.4 草稿字面不一致（草稿为 B/C 方向），需 Owner 确认按 spec 10 修正总计划。

### Decision 3 — Run Field Naming

- **Spec A**（01 §14.2）：`errorCode` / `errorMessage`。
- **Spec B**（10 §28/§29）：`failureCode` / `failureMessage`（DDL 列 `failure_code` / `failure_message`）。
- **Current Implementation**：`agent_runs.failure_reason`（自由文本）；legacy `TaskItem.error`（自由文本）。
- **Options**：A / B / 同时保留三个（明确拒绝——目标文件禁止三个无明确语义的错误表达并存）。
- **Recommended Decision**：**B**。理由：与现有 `failure_reason` 命名族连续，团队认知成本最低；spec 10 是数据模型权威文档；`failure_*` 语义上专指「Run 终止失败」，与 Event 层 `errorCode`（03 `run.failed` payload 用 `errorCode`）分层不冲突——Event payload 字段属于 03 的事件契约，M3 事件管线落地时再对齐。

- **Migration Impact**：006 列名 `failure_code` / `failure_message`。
- **API Impact**：v2 Run JSON：`failureCode?` / `failureMessage?`。
- **Test Requirement**：T22、T33、T39。
- **Owner Approval Required**：**是（OD-3）**——01 与 10 字面冲突，不得静默二选一。

### Decision 4 — API Topology

- **Spec A**（11-API-Specification §67-70）：集合 `GET/POST /api/workspaces/:workspaceId/tasks`；资源 `/api/tasks/:taskId`、`/api/tasks/:taskId/runs`、`/api/runs/:runId`（含 start/pause/resume/cancel/retry 等子命令，多数属 M3）。
- **Spec B / Current**：legacy 已占用 `GET/POST /api/workspaces/:workspaceId/tasks`、`POST .../tasks/:taskId/run`（单数 run，SSE）、`GET .../tasks/:taskId/status|logs`；现有 Run 查询为 `/api/workspaces/:workspaceId/runs?conversationId=` 与 `/api/workspaces/:workspaceId/runs/:runId`（读 agent_runs）。
- **Options**：
  - A1（推荐）：legacy 整体迁到 `/api/workspaces/:workspaceId/legacy/tasks/**`，v2 按 spec 11 占用 canonical 路径。依据：spec 11 §4.2 禁止 query 版本号；Web 端 legacy 唯一调用方 useTask 是孤儿 hook（rg 验证无 importer），实际破坏面为零；但对外部脚本/调用方仍是 URL 破坏。
  - A2：legacy 原地不动，v2 挂 `/api/workspaces/:workspaceId/v2/tasks...`。零破坏，但与 spec 11 canonical 路径不一致，未来还要再迁一次。
  - A3：混合——v2 只占未被占用的 `/api/tasks/:taskId/**`、`/api/runs/:runId/**`（全局解析 id 后做 workspace 校验），集合路径暂留 legacy。拓扑不一致，不推荐。
- **Recommended Decision**：**A1**，具体路由表见 §22。Workspace isolation：所有 v2 路由先解析 `:workspaceId`（不存在 → 404 `WORKSPACE_NOT_FOUND`），再按 `(workspace_id, id)` 双条件查询 Task/Run（跨工作区访问 → 404 `TASK_NOT_FOUND`/`RUN_NOT_FOUND`，不泄露存在性）。
- **路由注册位置**：新文件 `apps/server/src/routes/v2Tasks.ts`（`createV2TaskRoutes`），在 `index.ts` 挂载于 `/api/workspaces/:workspaceId`；legacy 挂载点在 A1 下改为 `/api/workspaces/:workspaceId/legacy/tasks`。
- **稳定错误码**：见 §30。
- **Compatibility Impact**：legacy URL 变更（A1）；`GET /api/workspaces/:id/runs...`（agent_runs 读路径）保持不变。
- **Migration Impact**：无。
- **API Impact**：v2 全套新端点；legacy 路径迁移（A1）。
- **Test Requirement**：T26-T36（含跨工作区 404）。
- **Owner Approval Required**：**是（OD-4）**——A1 是 URL 破坏决策；若 Owner 否掉，回落 A2（仅挂载点与测试基准 URL 变化，其余设计不变）。

### Decision 5 — Legacy TaskItem Identity

- **明确结论**：
  - Legacy 8 字符 ID **不直接成为** v2 Task ID（无前缀、熵过低、违反 01 §3.3）。
  - **不建独立映射表**；v2 `tasks.legacy_task_id` 列 + 部分唯一索引 `(workspace_id, legacy_task_id) WHERE legacy_task_id IS NOT NULL` 即映射。
  - 不使用 metadata JSON 记录 legacy ID（它是查询字段，按 10 §3.9/§171 必须是独立列）。
  - 重复启动防重：Bridge 每次执行先 `findByLegacyTaskId` find-or-create；并发重复由唯一索引兜底，冲突按 §23 事务顺序转为 409。
  - **M2.4 不导入现有 tasks.json**（目标文件预设；全量迁移属 M2.7 Exit Gate，本计划不主张纳入 M2.4）。后果：从未执行过的 legacy 任务在 v2 API 中不可见，直到它第一次经 Bridge 执行——视为目标文件既定决策。
- **Owner Approval Required**：否。

### Decision 6 — Legacy Pipeline Bridge

明确旧 `POST /workspaces/:workspaceId/tasks/:taskId/run`（A1 下为 `.../legacy/tasks/:taskId/run`）的 7 步行为：

1. **找到或创建 v2 Task**：加载 TaskItem（404 不变）→ `taskRepository.findByLegacyTaskId`，无则 `insert`（`legacy_task_id=taskId`，`title` 拷贝，`status='open'`，`created_by='legacy-pipeline'`）。
2. **创建 durable Run**：`runRepository.insert`（`origin='legacy_pipeline'`，`objective=task.title`）；reason：该 v2 Task 无任何历史 Run → `'initial'`；否则 → `'retry'`，`parentRunId=最近一次 Run`，`rootRunId=parent.rootRunId`。插入撞上部分唯一索引（已有活跃 Run）→ 409 `RUN_ACTIVE_EXISTS`，**不写 JSON**。
3. **执行旧 AgentRunner**：完全复用现有四阶段流程与 `runStage()`。
4. **Run 状态持久化**：创建即 `queued`；Pipeline 开始（首个 stage 前）→ `running`（写 `started_at`）；成功 → `completed`（写 `completed_at`）；`applyStageFailure` → `failed`（`failure_code='LEGACY_PIPELINE_FAILED'`，`failure_message=task.error`）；取消 → `cancelled`（`failure_code='LEGACY_PIPELINE_CANCELLED'`，写 `cancellation_requested_at` 与 `completed_at`）。
5. **保留 Legacy TaskItem.outputs**：JSON 写入路径逐字保留（§34）。
6. **保持现有 SSE 响应**：事件名与 payload 不变。
7. **防止重复 active Run**：三层——内存 `claimTaskRun`（409 不变）、SQLite 部分唯一索引（兜底，转 409）、Express 单进程同步执行（better-sqlite3 同步 API，天然串行）。

事务顺序（JSON 与 SQLite 无法同事务，按 Saga 排序）：① `claimTaskRun` 内存检查；② SQLite 事务（find-or-create Task + insert Run）；③ JSON `saveTask(running)`。③失败时 catch 内将 v2 Run 置 `failed`（`failure_code='BRIDGE_CLAIM_FAILED'`）补偿，见 §28。

- **Owner Approval Required**：否。

### Decision 7 — Browser / SSE Disconnect

- **当前行为**：legacy SSE `res.on('close')` → `abortController.abort()` → Task `cancelled`（违反 01 §47.12 / 02 §61.4）。
- **M2.4 是否改变此行为**：**不改变**。行为修复超出「数据模型分离」范围，且需要后台执行引擎（M3 ProcessManager/RunEngine）支撑才有意义。
- **新 v2 Run API 是否脱离 HTTP 生命周期**：**是，天然脱离**。M2.4 的 v2 API 不提供 SSE 执行端点；Run 行在创建时即 durable；M2.4 内 v2 API 创建的 Run 不触发执行（执行语义见 OD-5 与 §14）。
- **Legacy SSE Path 是否暂时保留**：是，原样保留（含断连取消）。
- **行为变更是否超出范围**：是，故冻结并文档化为已知违规（§8、§42 R-4）。
- **对应测试和后续里程碑**：M2.4 测试锁定「Bridge 把断连取消映射为 v2 Run `cancelled`」（T39），保证数据层忠实记录现状；行为修复测试归 M3（02 §52 Scenario D）。
- **Owner Approval Required**：**是（OD-5）**——确认「冻结违规 + v2 Run 在 M2.4 仅数据层 durable、v2 API 创建的执行语义（是否同步触发 Bridge 执行）」。

### Decision 8 — Task and Run State Independence

（完整状态机见 §24/§25，此处为裁决要点。）

- Run `queued/starting/running/waiting_approval/paused`（活跃）→ Task `in_progress`（从 `open` 首次激活时推进）。
- Run `completed` → **不自动** Task `done`；Task 保持 `in_progress` 直到 acceptance（02 §5.6）。
- Run `failed` → Task 回 `open`（无其他活跃 Run 且未接受时；02 §5.5）。
- Run `cancelled` → 同上回 `open`。
- 多 Run 并存（provider-comparison siblings）：任一活跃 → `in_progress`；全部终态无接受 → `open`。
- Retry：创建新 Run → Task 维持/回到 `in_progress`。
- **User Acceptance**：`POST /tasks/:taskId/accept`（body: `runId`），要求该 Run `completed` → Task `done` + `accepted_run_id` + `completed_at`。
- **acceptedRunId**：独立列，accept 时写入；reopen 时清空。
- **cancelled Task 是否允许新 Run**：不允许（409 `TASK_CANCELLED`），须先 `reopen` → `open`（02 §5.5 cancelled → reopen → open）。
- **failed Run 是否改变 Task 的用户意图**：不改变。失败是执行事实；意图终结只能由用户 cancel 或 acceptance 产生。
- **Owner Approval Required**：否。

### Decision 9 — Retry Semantics

- Initial Run：`parentRunId = null`，`rootRunId = self id`（Repository insert 时计算并校验）。
- Retry：`parentRunId = source Run.id`，`rootRunId = source.rootRunId`。
- Review Fix：新 Run（`reason='review-fix'`），不修改旧 Run 任何字段。
- Provider Comparison：多个 sibling Run（各自 `parentRunId` 指向同一 source 或同为 initial，共享 `rootRunId`）。
- 历史 Run 不得因 Retry 被重置或覆盖：Repository 终态守卫——`completed/failed/cancelled` 后拒绝一切状态迁移（T21/T25）。
- Legacy Bridge 重跑即 Retry（§11 D6 第 2 步）。
- **Owner Approval Required**：否。

- **Owner Approval Required**：否。

## 19. Migration Rollback and Checksum Strategy

- 遵循既有 MigrationRunner 契约（m2-migration-plan §5 决策）：单 Migration 单事务（`BEGIN IMMEDIATE`）；失败整体回滚且不写 `_schema_migrations`；checksum 不匹配为硬失败；每个 Migration 应用后跑 `PRAGMA integrity_check` 与 `PRAGMA foreign_key_check`。
- 005/006 均为非破坏性 CREATE，无数据迁移，无需 pre-migration backup（与 003/004 同级处理）。
- 回滚策略：forward-only。提交后发现问题 → 备份恢复或新修复 Migration（如 `007-*`），不修改已发布的 005/006 文件（checksum 不变性）。
- 无 `down()`；测试通过「fresh DB 应用 005/006 → PRAGMA 验证结构」覆盖正确性（T01-T06）。

## 24. Task State Machine

```
open
  ├── run 创建成功（queued/running） → in_progress
  ├── （M2.4 无 blocked 产生方；保留状态供 M2.6+）
  └── user cancel（无活跃 Run） → cancelled

in_progress
  ├── acceptance（completed Run） → done
  ├── 全部 Run 终态且无 acceptance → open
  └── user cancel（无活跃 Run） → cancelled

blocked
  ├── （M2.4 无进入/退出方，状态保留）
  └── user cancel → cancelled

done
  └── reopen → open（清 accepted_run_id / completed_at）

cancelled
  └── reopen → open
```

守卫：cancel 时存在活跃 Run → 409 `TASK_HAS_ACTIVE_RUN`；cancelled Task 创建 Run → 409 `TASK_CANCELLED`；accept 的 Run 非 completed → 409 `RUN_NOT_COMPLETED`。

## 25. Run State Machine

```
queued
  ├── bridge 执行开始 → running
  ├── （API 创建的 Run 在 M2.4 停留 queued；无调度器）
  └── user cancel → cancelled        （M2.4 仅 Bridge 路径实际发生）

running
  ├── pipeline 成功 → completed
  ├── pipeline 异常 → failed
  └── 断连取消 → cancelled

starting / waiting_approval / paused   （CHECK 预留，M2.4 无写入方）

completed / failed / cancelled         （终态，ALLOWED_TRANSITIONS = []）
```

守卫：终态后任何迁移 → Error（历史不可变，D9）；`failed` 必须携带 `failure_code`；`cancelled` 必须写 `cancellation_requested_at`。

## 26. Retry / Parent / Root Rules

（即 §11 D9 冻结。）Repository `insert` 强制：

- `reason='initial'` → 禁止携带 `parentRunId`；`root_run_id = 自身 id`。
- `reason IN ('retry','resume-fallback','review-fix')` → 必须携带同 Task 的 `parentRunId`；`root_run_id = parent.root_run_id`。
- `reason='provider-comparison'` → `parentRunId` 可选；携带时同上，不携带时 `root_run_id = 自身 id`（独立比较树）。
- `reason='manual'` → 同 initial 规则。
- Bridge 自动推导：Task 无历史 Run → `initial`；有 → `retry` + 最近 Run 为 parent（`resolveBridgeRunReason`，T38）。

## 27. Cancellation Rules

- v2 Task cancel：仅无活跃 Run 时允许（409 `TASK_HAS_ACTIVE_RUN`）；只取消意图，不杀执行。
- v2 Run cancel：M2.4 不提供 v2 Run cancel API（活跃 Run 只由 Bridge 产生，其取消仍走 legacy 断连路径）。`POST /api/runs/:runId/cancel` 属 M3（spec 11 §1825），列入 §14。
- Legacy 断连取消：行为不变（D7 冻结）；Bridge 忠实记录 v2 Run `cancelled`。
- 取消与完成竞态：repository version guard + 终态守卫保证只有一个胜者（T24）。

## 28. Transaction Boundaries

| 操作 | 事务内容 | 备注 |
|---|---|---|
| v2 Task 创建 | 单 INSERT | route 内单条，无需显式事务 |
| v2 Run 创建（API） | `inTransaction`：读 Task（校验状态）→ INSERT Run | 活跃索引冲突回滚 |
| Bridge claim + create | `inTransaction`：find-or-create Task + INSERT Run（+ Task `open→in_progress`） | 与 JSON 写按 §11 D6 Saga 排序；JSON 写失败 → catch 内 Run 置 `failed`（`BRIDGE_CLAIM_FAILED`）补偿 |
| Bridge 终态同步 | `inTransaction`：Run 终态 UPDATE + Task 状态 UPDATE（failed/cancelled → `open`） | 单 DB 操作组 |
| accept | `inTransaction`：读 Run（校验 completed + 同 Task）→ Task accept UPDATE | version guard |
| cancel/reopen | 单 UPDATE（version guard） | — |

不在 Provider/Pipeline 执行期间持有数据库事务（10 §173.37）：Bridge 只在执行前/终态后开短事务。

## 29. Workspace Isolation

- 所有 v2 查询 `(workspace_id, id)` 双条件；列表强制 `workspace_id`。
- 路由先 `workspaceManager.get(:workspaceId)` → 404 `WORKSPACE_NOT_FOUND`。
- 跨工作区访问 Task/Run → 404（与不存在无差别，不泄露）。
- `runs.workspace_id` 冗余列（与 tasks.workspace_id 一致写入），支持按工作区直接扫描与恢复。
- 测试：T28、T33、T36 覆盖跨工作区 404。

## 30. Error Code Contract

v2 路由错误体：`{ error: string, code: string }`（`error` 为人类可读，`code` 为稳定机器码；legacy 路由错误体不变）。

| code | HTTP | 触发 |
|---|---|---|
| `WORKSPACE_NOT_FOUND` | 404 | workspace 不存在 |
| `TASK_NOT_FOUND` | 404 | task 不存在或跨工作区 |
| `RUN_NOT_FOUND` | 404 | run 不存在或跨工作区 |
| `PARENT_RUN_NOT_FOUND` | 404 | parentRunId 不存在/跨 Task |
| `TASK_TITLE_REQUIRED` | 400 | 缺 title |
| `VALIDATION_FAILED` | 400 | priority/reason 枚举、parentRunId 与 reason 组合非法 |
| `TASK_ARCHIVED` | 409 | archived task 上的写操作 |
| `TASK_CANCELLED` | 409 | cancelled task 上创建 Run |
| `TASK_HAS_ACTIVE_RUN` | 409 | 有活跃 Run 时 cancel Task |
| `RUN_ACTIVE_EXISTS` | 409 | 活跃索引冲突（API 与 Bridge 共用） |
| `RUN_NOT_COMPLETED` | 409 | accept 未完成 Run |
| `INVALID_TASK_TRANSITION` | 409 | 非法 Task 状态迁移 |
| `INVALID_RUN_TRANSITION` | 409 | 非法 Run 状态迁移（含终态后迁移） |
| `VERSION_CONFLICT` | 409 | version guard 失败（M2.4 内部；API 不接收 expectedVersion） |
| `INTERNAL_ERROR` | 500 | 兜底（message sanitized，不泄露内部细节——对齐 M2.3 provider API 约定） |

## 31. Version Behavior

- `tasks.version` / `runs.version`：`INTEGER NOT NULL DEFAULT 1`；每次 UPDATE 经 `assertVersionedMutation` 递增；并发写产生唯一胜者，败者 `VersionConflictError`。
- API 响应包含 `version` 字段（只读暴露）。
- M2.4 API **不接收** `expectedVersion`/`If-Match`（API 级乐观并发属 M2.6）；route 内部读取当前 version 后立即在同一事务内使用。
- 与 M2.3 provider API 的差异（那边已强制 expectedVersion）是有意边界：Task/Run 的并发写方在 M2.4 只有单进程 route/bridge，version guard 是内部一致性保障而非外部契约。
