# M2.6 Owner Decisions — Idempotency and Optimistic Concurrency

Status: M2.6 OWNER DECISIONS APPROVED

Owner Decision Baseline: `ee516558f448bc961b49ebd073bd3c99b1d3baf8` (M2.6 current-state audit commit). Planning review findings BLOCKER 0 / HIGH 0 / MEDIUM 4 / LOW 1 are all closed by the frozen decisions below.

This file is frozen. It authorizes planning only; implementation begins only after independent plan review and separate Owner authorization per phase.

---

## OD-1 — M2.6 Domain Scope

Decision: **Task-domain v2 only.** Approval, Provider, Legacy, Conversation, and Web are excluded.
Owner Status: APPROVED

## OD-2 — Idempotent Operations

Decision: include exactly six operations — `task.create`, `run.create`, `run.cancel`, `task.accept`, `task.cancel`, `task.reopen`. Everything else is excluded.
Owner Status: APPROVED

## OD-3 — Legacy Compatibility

Decision: the Legacy Task/SSE Bridge is fully excluded from M2.6.
Owner Status: APPROVED

## OD-4 — Idempotency Input

Decision: `Idempotency-Key` HTTP header only. No body field.
Owner Status: APPROVED

## OD-5 — Key Validation

Decision: trim; length 8–128; pattern `^[A-Za-z0-9][A-Za-z0-9._:-]{7,127}$`; empty, array, duplicate header, or comma-joined values are rejected with 400 `VALIDATION_FAILED`. Raw keys are never logged and never persisted — only `key_hash` is stored.
Owner Status: APPROVED

## OD-6 — Uniqueness Scope

Decision: `workspace_id + operation + key_hash`. Cross-workspace collisions are impossible by construction.
Owner Status: APPROVED

## OD-7 — Operation Vocabulary

Decision: frozen operation keys `task.create`, `run.create`, `run.cancel`, `task.accept`, `task.cancel`, `task.reopen`. Route strings are never used as operation identifiers.
Owner Status: APPROVED

## OD-8 — Request Fingerprint

Decision: canonical JSON + SHA-256 over operation, workspace, path params, normalized domain input (including defaults), and `expectedVersion` as null-or-integer. The Idempotency-Key and all other headers are excluded. Raw request bodies are never stored.
Owner Status: APPROVED

## OD-9 — Same Key, Different Request

Decision: HTTP 409, code `IDEMPOTENCY_KEY_REUSED`, fixed safe message "Idempotency key was already used with a different request".
Owner Status: APPROVED

## OD-10 — Replay Response

Decision: original HTTP status plus JSON semantic deep equality (not byte identity); replay adds header `Idempotency-Replayed: true`; the internal record ID is never exposed.
Owner Status: APPROVED

## OD-11 — Atomicity

Decision: `TaskRunService` owns the single transaction per operation. The idempotency lookup/replay happens inside that transaction before every domain/version guard (`RUN_ACTIVE_EXISTS`, `RUN_NOT_CANCELLABLE`, `TASK_NO_ACCEPTANCE_WINDOW`, `INVALID_TASK_TRANSITION`, `VERSION_CONFLICT`). There is no placeholder claim. `IdempotencyService` never begins, commits, rolls back, or calls `runInTransaction` itself.
Owner Status: APPROVED

## OD-12 — Failure Semantics

Decision: success-only persistence — only 2xx outcomes are recorded. Validation, domain conflict, version conflict, internal, and security failures are never cached. Rollback leaves no record. Concurrent same-key requests are serialized by `BEGIN IMMEDIATE` and the composite unique key, then replay the committed result.
Owner Status: APPROVED

## OD-13 — Result Storage

Decision: server-internal typed result envelope V1; no new shared type; explicit per-operation field allowlist; `result_hash` is mandatory and verified on replay.
Owner Status: APPROVED

## OD-14 — Expiration and Retention

Decision: no `expires_at` column; no TTL, cleanup, or retention job in M2.6.
Owner Status: APPROVED

## OD-15 — Optimistic Concurrency API

Decision: optional `expectedVersion` on `run.cancel`, `task.accept`, `task.cancel`, `task.reopen` only. Absent preserves current behavior. Present must be a positive safe integer and is checked inside the transaction. `expectedVersion` participates in the request fingerprint.
Owner Status: APPROVED

## OD-16 — Version Conflict Response

Decision: HTTP 409, code `VERSION_CONFLICT`, fixed message "Version conflict". The response never returns `currentVersion` or any entity metadata.
Owner Status: APPROVED

## OD-17 — Approval Boundary

Decision: Approval is fully deferred. No Approval persistence, idempotency, or Registry change in M2.6.
Owner Status: APPROVED

## OD-18 — Migration 010 Exact Schema

Decision: table `idempotency_records` with exactly these columns:

| Column | Rule |
|---|---|
| `id` | `idem_<ulid>` primary key |
| `workspace_id` | FK to workspaces, cascade delete |
| `operation` | one of the six frozen operation keys |
| `key_hash` | SHA-256 of the raw key; raw key never stored |
| `request_hash` | SHA-256 canonical fingerprint (OD-8) |
| `result_schema_version` | integer ≥ 1 |
| `result_json` | typed envelope V1, allowlist-validated |
| `result_hash` | SHA-256 of canonical result envelope |
| `http_status` | original 2xx status |
| `created_at` | insert timestamp |

Constraints: `UNIQUE(workspace_id, operation, key_hash)`; UPDATE rejected by trigger; no DELETE API; no `expires_at`; no raw key column; no additional `created_at` index. Migration is additive, checksum-frozen, non-destructive, and requires no backup.
Owner Status: APPROVED

## OD-19 — Security and No-leak

Decision: dual-layer no-leak at Repository and API. Only `key_hash`, `request_hash`, and `result_hash` are persisted/inspectable; raw keys and raw request bodies are never stored or logged. Stored results are validated exactly on read and replay; corruption or tampering fails closed with 500 `IDEMPOTENCY_RECORD_INVALID` and a fixed safe message.
Owner Status: APPROVED

## OD-20 — M2.7 Boundary

Decision: M2.6 performs no M2.7 cutover, no JSON migration, no Legacy retirement, no Conversation or Web changes, and no historical backfill.
Owner Status: APPROVED
