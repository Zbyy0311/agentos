## OD-5 — Key Validation and Normalization

Decision: trim; length 8–128; pattern `^[A-Za-z0-9][A-Za-z0-9._:-]{7,127}$`; empty, array, duplicate header, or comma-joined values are rejected with 400 `VALIDATION_FAILED`. Raw keys are never logged and never persisted — only `key_hash` is stored.

Normalization freeze (plan-review remediation):

- `normalizedKey = headerValue.trim()`; length and regex validation apply to `normalizedKey` only.
- `key_hash = SHA-256 UTF-8(normalizedKey)`; the untrimmed header value is never hashed.
- Neither the raw header value nor `normalizedKey` may be logged or persisted.
- Exactly one `Idempotency-Key` header is accepted; duplicate detection counts header occurrences case-insensitively over `req.rawHeaders` and must not rely on Express-merged header values.

Frozen parser candidate signature:

```ts
export function parseIdempotencyKey(req: Request): string | undefined;
```

Parser rules: (1) count `Idempotency-Key` occurrences in `req.rawHeaders` case-insensitively; (2) 0 occurrences → `undefined`; (3) 1 occurrence → read, trim, validate; (4) 2 or more → 400 `VALIDATION_FAILED`; (5) array value → reject; (6) value containing a comma → reject; (7) empty after trim → reject; (8) the error message never contains the header value.

Planned tests: M26-T031 (duplicate raw header rejected), M26-T032 (single header with comma-joined value rejected), M26-T041 (case-insensitive duplicate header names still rejected), M26-T042 (trim-equivalent keys produce the same `key_hash`).
Owner Status: APPROVED

## OD-9 — Same Key, Different Request

Decision: HTTP 409, code `IDEMPOTENCY_KEY_REUSED`, fixed safe message "Idempotency key was already used with a different request".
Owner Status: APPROVED

## OD-10 — Replay Response

Decision: original HTTP status plus JSON semantic deep equality (not byte identity); replay adds header `Idempotency-Replayed: true`; the internal record ID is never exposed.
Owner Status: APPROVED

## OD-11 — Atomicity

Decision: `TaskRunService` owns the single transaction per operation. The idempotency lookup/replay happens inside that transaction before every domain/version guard (`RUN_ACTIVE_EXISTS`, `RUN_NOT_CANCELLABLE`, `TASK_NO_ACCEPTANCE_WINDOW`, `INVALID_TASK_TRANSITION`, `VERSION_CONFLICT`). There is no placeholder claim. `IdempotencyService` never begins, commits, rolls back, or calls `runInTransaction` itself.
Owner Status: APPROVED

## OD-12 — Failure Semantics

Decision: success-only persistence — only 2xx outcomes are recorded. Validation, domain conflict, version conflict, internal, and security failures are never cached. Rollback leaves no record. Concurrent same-key requests are serialized by `BEGIN IMMEDIATE` and the composite unique key, then replay the committed result.
Owner Status: APPROVED

## OD-13 — Result Storage

Decision: server-internal typed result envelope V1; no new shared type; explicit per-operation field allowlist; `result_hash` is mandatory and verified on replay.

Typed envelope freeze (plan-review remediation) — `unknown` is removed from all core interfaces. Server-internal types:

```ts
type IdempotencyOperation =
  | 'task.create'
  | 'run.create'
  | 'run.cancel'
  | 'task.accept'
  | 'task.cancel'
  | 'task.reopen';

interface IdempotencyEnvelopeBaseV1 {
  schemaVersion: 1;
  operation: IdempotencyOperation;
}

type TaskResultOperation =
  | 'task.create'
  | 'task.accept'
  | 'task.cancel'
  | 'task.reopen';

type RunResultOperation =
  | 'run.create'
  | 'run.cancel';

interface TaskResultEnvelopeV1 extends IdempotencyEnvelopeBaseV1 {
  operation: TaskResultOperation;
  body: { task: IdempotencyTaskDtoV1 };
}

interface RunResultEnvelopeV1 extends IdempotencyEnvelopeBaseV1 {
  operation: RunResultOperation;
  body: { run: IdempotencyRunDtoV1 };
}

type IdempotencyResultEnvelopeV1 = TaskResultEnvelopeV1 | RunResultEnvelopeV1;
```

Frozen Task DTO fields (`IdempotencyTaskDtoV1`): `id`, `workspaceId`, `legacyTaskId` (when present), `title`, `description` (when present), `status`, `priority`, `sourceConversationId` (when present), `sourceMessageId` (when present), `acceptedRunId` (when present), `pendingResultRunId` (when present), `createdBy`, `createdAt`, `updatedAt`, `completedAt` (when present), `archivedAt` (when present), `version`.

Frozen Run DTO fields (`IdempotencyRunDtoV1`): `id`, `workspaceId`, `taskId`, `parentRunId` (when present), `rootRunId`, `status`, `reason`, `origin`, `objective` (when present), `failureCode` (when present), `failureMessage` (when present), `cancellationRequestedAt` (when present), `nextEventSequence`, `startedAt` (when present), `completedAt` (when present), `createdBy`, `createdAt`, `updatedAt`, `version`.

Optional-field rules: `undefined` fields never enter the body; they are not coerced to `null`; no object spread is used; explicit builders `buildTaskResultEnvelopeV1(...)` and `buildRunResultEnvelopeV1(...)` are frozen; canonical-JSON input never contains `undefined`. Live responses and replay responses both serialize `envelope.body` — live never returns the raw Task/Run entity and replay never uses a second DTO shape.

## OD-18 — Migration 010 Exact Schema

Decision: table `idempotency_records` with exactly these columns:

| Column | Rule |
|---|---|
| `id` | `idem_<ulid>` primary key |
| `workspace_id` | FK to workspaces, cascade delete |
| `operation` | one of the six frozen operation keys |
| `key_hash` | SHA-256 of the raw key; raw key never stored |
| `request_hash` | SHA-256 canonical fingerprint (OD-8) |
| `result_schema_version` | integer ≥ 1 |
| `result_json` | typed envelope V1, allowlist-validated |
| `result_hash` | SHA-256 of canonical result envelope |
| `http_status` | original 2xx status |
| `created_at` | insert timestamp |

Constraints: `UNIQUE(workspace_id, operation, key_hash)`; UPDATE rejected by trigger; no DELETE API; no `expires_at`; no raw key column; no additional `created_at` index. Migration is additive, checksum-frozen, non-destructive, and requires no backup.

Exact candidate DDL freeze (plan-review remediation) — the full statement text, not only the field list:

```sql
CREATE TABLE idempotency_records (
  id TEXT PRIMARY KEY
    CHECK (
      length(id) = 31
      AND substr(id, 1, 5) = 'idem_'
    ),

  workspace_id TEXT NOT NULL,

  operation TEXT NOT NULL
    CHECK (
      operation IN (
        'task.create',
        'run.create',
        'run.cancel',
        'task.accept',
        'task.cancel',
        'task.reopen'
      )
    ),

  key_hash TEXT NOT NULL
    CHECK (
      length(key_hash) = 64
      AND key_hash NOT GLOB '*[^0-9a-f]*'
    ),

  request_hash TEXT NOT NULL
    CHECK (
      length(request_hash) = 64
      AND request_hash NOT GLOB '*[^0-9a-f]*'
    ),

  result_schema_version INTEGER NOT NULL
    CHECK (result_schema_version = 1),

  result_json TEXT NOT NULL
    CHECK (json_valid(result_json)),

  result_hash TEXT NOT NULL
    CHECK (
      length(result_hash) = 64
      AND result_hash NOT GLOB '*[^0-9a-f]*'
    ),

  http_status INTEGER NOT NULL
    CHECK (http_status BETWEEN 200 AND 299),

  created_at TEXT NOT NULL,

  UNIQUE(workspace_id, operation, key_hash),

  FOREIGN KEY (workspace_id)
    REFERENCES workspaces(id)
    ON DELETE CASCADE
);
```

UPDATE trigger freeze: `idempotency_records_reject_update` with the fixed SQLite abort message `IDEMPOTENCY_RECORD_IMMUTABLE`. There is no DELETE trigger; the workspace cascade is retained.

Migration export freeze: `M26_010_DDL_STATEMENTS`, `migration010Checksum`, `migration010`. The checksum covers the full table + trigger DDL.
Owner Status: APPROVED

## OD-19 — Security and No-leak

Decision: dual-layer no-leak at Repository and API. Only `key_hash`, `request_hash`, and `result_hash` are persisted/inspectable; raw keys and raw request bodies are never stored or logged. Stored results are validated exactly on read and replay; corruption or tampering fails closed with 500 `IDEMPOTENCY_RECORD_INVALID` and a fixed safe message.

Request-hash verifiability boundary freeze (plan-review remediation): the system does not retain raw requests, so it cannot distinguish "a well-formed stored `request_hash` was modified" from "the same key was reused for a different request". Frozen semantics:

- A. Stored `request_hash` is malformed — not a string, length is not 64, or contains non-lowercase-hex characters → HTTP 500, code `IDEMPOTENCY_RECORD_INVALID`, message "Idempotency record is invalid" (fails closed).
- B. Stored `request_hash` is well-formed but differs from the freshly computed request fingerprint → HTTP 409, code `IDEMPOTENCY_KEY_REUSED`, message "Idempotency key was already used with a different request".

Plain SHA-256 is not claimed to identify an attacker who already has database write access. No `record_hash`, HMAC, or secret key is added; those are not part of M2.6. `result_hash` verifies only the canonical result envelope. Planned tests: M26-T035 (malformed stored `request_hash` fails closed as `IDEMPOTENCY_RECORD_INVALID`), M26-T043 (valid-format mismatched `request_hash` returns `IDEMPOTENCY_KEY_REUSED`).
Owner Status: APPROVED
