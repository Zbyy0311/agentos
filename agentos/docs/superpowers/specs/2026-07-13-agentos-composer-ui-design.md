# AgentOS 对话 Composer 与整体 UI 设计

## 目标

将 AgentOS 对话输入区调整为接近 Codex 的交互：模型和思考强度紧邻发送按钮，并且选择值真实作用于当前发送；同时保留现有 Agent 默认配置、执行状态和三栏工作区能力。

## 已确认的交互语义

- 单聊支持按消息选择模型和思考强度。
- 选择只影响当前这一条消息，不修改 Agent 默认配置。
- Agent 编辑器继续负责 Agent 名称、系统提示词、权限、默认模型和默认思考强度。
- 群聊不做跨 Agent 的强制覆盖。由于成员可能使用不同 CLI，群聊沿用每个成员自己的配置；Composer 中显示“按成员配置”状态，不提供会造成误导的全局选择。
- 模型列表优先使用当前 Agent 的动态发现结果；没有结果时使用 capability fallback。
- 思考强度只显示当前模型支持的值。Kimi/OpenCode 等仅支持 `auto` 的 CLI 不显示不可用选项。

## 设计方案

### 1. 对话区布局

保留现有四块信息职责，但调整比例和视觉层级：

1. Agent 列表：窄侧栏，展示 Agent、在线/执行状态和群聊入口。
2. 会话历史：窄侧栏，突出新建会话和当前会话。
3. 主对话区：占用主要宽度，顶部显示 Agent/会话标题，中部展示消息，底部使用 Codex 风格 Composer。
4. 执行状态：保留右侧检查器，使用较窄宽度、弱化背景，继续展示权限和时间线。

Composer 结构：

```text
┌──────────────────────────────────────────────────────────────┐
│  多行消息输入区                                               │
│                                                               │
│  ＋  提示：Enter 发送，Shift+Enter 换行       模型⌄  思考⌄  ● │
└──────────────────────────────────────────────────────────────┘
```

- 发送按钮为圆形主按钮，空消息或执行中禁用。
- 模型和思考强度使用紧凑下拉按钮，不使用原生大表单样式。
- 模型下拉项同时展示模型 label 和必要时的 provider/id。
- 下拉菜单显示当前值、可选值和能力来源提示；模型过多时可滚动。
- 执行中锁定模型/思考选择，避免用户误以为正在修改已运行任务。
- 保留 Enter 发送、Shift+Enter 换行。

### 2. 前端状态与数据流

`WorkspacePage` 持有 Composer 状态：

```ts
type ComposerSettings = {
  model?: string;
  thinkingEffort: ThinkingEffort;
};
```

- 进入单聊或切换 Agent 时，根据 `agent.model` 和 `agent.thinkingEffort` 初始化。
- 当前模型改变时，如果原思考强度不被新模型支持，自动切换为该模型的默认值。
- 发送时将状态作为 `model`、`thinkingEffort` 放入 SSE 请求体。
- 发送成功或失败后保留选择值，便于连续发送；切换 Agent 时重新初始化。
- 群聊由 `isGroup` 控制为只读状态，不发送覆盖字段。

`ChatPanel` 只负责展示和交互回调，不读取 Agent 配置，不直接决定执行策略。

### 3. 服务端校验与执行

SSE 请求体扩展为：

```ts
{
  content: string;
  model?: string;
  thinkingEffort?: ThinkingEffort;
}
```

服务端处理规则：

- `content` 仍为必填。
- `thinkingEffort` 只能是 `auto | low | medium | high`，且必须属于目标 Agent 当前 capability 支持范围。
- `model` 必须是目标 Agent 动态发现列表或 fallback 列表中的模型；空字符串视为不覆盖，使用 Agent 默认模型。
- 校验失败返回 HTTP 400，不创建执行记录，不调用 CLI。
- 校验通过后构造本次运行用的 Agent 副本，只替换 `model`/`thinkingEffort`，不写回持久化 Agent profile。
- 群聊忽略 Composer 覆盖字段，按每个成员 profile 执行，并通过测试锁定该语义。

`ConversationAgentRunner` 接收可选的运行时覆盖配置，仍由现有 CLI capability 逻辑负责把思考强度转换成 CLI 参数。

## UI 优化范围

- 统一深色主题色板、边框透明度、圆角和间距，减少现有块状边界。
- 主对话区最大内容宽度保持可读性，消息气泡区分用户、Agent、系统消息。
- 顶部标题区压缩垂直占用，保留重命名和取消执行操作。
- 右侧执行检查器保留信息，不删除现有能力；空状态和时间线使用更清晰的层级。
- 修正本次触及组件中的中文显示，避免出现乱码文案。
- 不新增附件、语音、审批流、持久化“每条消息设置”等非本需求功能。

## 验收标准

### 功能

- 单聊 Composer 在发送按钮左侧可见模型选择和思考强度选择。
- 模型列表来自当前 Agent 的 `capability.modelOptions`，无动态结果时使用 fallback。
- 切换模型后思考强度选项只包含该模型支持的值。
- 发送请求包含当前选择；服务端将其传递给实际运行配置。
- 修改 Composer 选择不会修改 Agent 编辑器保存的默认配置。
- 不支持的模型或思考强度返回 400，且不会调用 CLI。
- 群聊 Composer 显示按成员配置，并且不覆盖成员配置。
- Enter 发送、Shift+Enter 换行、执行中禁用选择和发送均可用。

### 视觉

- 1440px 宽窗口下，三栏和右侧状态区同时可见，输入区不被遮挡。
- 960px 最小宽度下不发生横向溢出；小于该宽度显示明确的最小窗口约束。
- 模型/思考强度下拉层不被输入区或右侧面板裁剪。
- 发送、加载、错误、空会话和群聊状态均有清晰可见反馈。

### 自动化验证

- agent-core 测试通过，并覆盖运行时模型/思考强度覆盖。
- server 测试覆盖请求体校验、覆盖值传递、非法值不执行、群聊忽略覆盖。
- web 类型检查和生产构建通过。
- 能执行浏览器自动化时，完成单聊选择、发送、群聊只读和响应式布局检查；当前环境若无浏览器插件或 Playwright 依赖，必须在报告中明确记录阻塞原因。
