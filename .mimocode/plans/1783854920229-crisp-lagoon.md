# Code Review - Bug Audit Plan

## Overview
审查 agentos 项目代码中的 bug 和潜在问题。以下是发现的所有问题，按严重程度排序。

---

## Critical Bugs (必须修复)

### Bug 1: 同一任务可被并发执行，导致数据竞争
**文件**: `apps/server/src/routes/tasks.ts:69-224`
**问题**: `POST /:taskId/run` 路由没有检查任务是否已经在运行。如果用户快速点击两次"运行"，两个 pipeline 会同时操作同一个 task 对象，导致 `task.outputs` 被并发 push，`store.saveTasks` 写入的数据可能被覆盖。
**修复**: 在启动 pipeline 前检查 `task.status === 'running'`，如果已在运行则返回 409 Conflict。

### Bug 2: `mimo` 角色被错误映射为 `opencode_reviewer`
**文件**: `packages/agent-core/src/conversationRunner.ts:98-102`
**问题**: `toAgentConfig()` 函数将 `mimo` 角色映射为 `opencode_reviewer` 阶段，这会导致 mimo agent 使用 OpenCode 的 CLI 配置（`codex exec --dangerously-bypass-approvals-and-sandbox`），而不是其应有的配置。
```typescript
role: agent.role === 'kimi'
  ? 'kimi_worker'
  : agent.role === 'opencode' || agent.role === 'mimo'
    ? 'opencode_reviewer'
    : 'codex_manager',
```
**修复**: 需要为 `mimo` 角色添加独立的映射逻辑，或者确认当前映射是否有意为之（mimo 可能复用 opencode 的执行器）。

### Bug 3: PowerShell 脚本临时文件在 spawn 失败时可能泄漏
**文件**: `packages/agent-core/src/executor.ts:230-268`
**问题**: 如果 `createCommandInvocation` 成功（创建了临时目录和文件），但随后 `spawn` 抛出异常，catch 块会调用 `await invocation.cleanup()`。但如果 `invocation` 变量在 line 226 声明时未初始化，而 `createCommandInvocation` 成功赋值给 `invocation`，则 cleanup 会正常执行。然而如果 `prepareKimiCodeHome`（line 237）失败，临时文件不会被清理，因为 `invocation.cleanup()` 在 spawn 的 catch 块中被调用（line 264），而 kimi home 准备失败在之前的 catch 块（line 239-242）。
**修复**: 在 `prepareKimiCodeHome` 失败的 catch 块中也调用 `await invocation.cleanup()`。

### Bug 4: `appendTaskLine` 不创建带有表头的 TASKS.md
**文件**: `apps/server/src/routes/tasks.ts:264-271`
**问题**: `appendTaskLine` 直接追加一行到 TASKS.md 文件，但如果文件为空（或不存在），追加的内容没有表头，Markdown 表格无法正确渲染。
**修复**: 检查文件是否存在且有表头，如果没有则先写入表头。

## High Bugs (应该修复)

### Bug 5: `isCodexCli` 正则表达式重复且冗余
**文件**: `packages/agent-core/src/conversationRunner.ts:109-111`
**问题**: 两个正则表达式有重叠匹配：
```typescript
/(?:^|[\\/])codex(?:\.(?:exe|cmd|bat))?$/i  // 已经匹配 ^codex
/^codex(?:\.(?:exe|cmd|bat))?$/i             // 完全冗余
```
第一个正则的 `(?:^|[\\/])` 已经覆盖了以 `codex` 开头的情况。

**修复**: 合并为一个正则：
```typescript
/^(?:.*[\\/])?codex(?:\.(?:exe|cmd|bat))?$/i
```

### Bug 6: `resolveCommand` 的 PATH 扫描不处理 PATHEXT 大小写
**文件**: `packages/agent-core/src/resolveCommand.ts:54`
**问题**: `ext.toLowerCase()` 只对扩展名做了小写转换，但 Windows 文件系统是大小写不敏感的。这本身没问题，但 `PATHEXT` 环境变量通常是大写的（如 `.EXE;.CMD;.BAT`），而 `ext` 已经是大写，`toLowerCase()` 是多余的但无害。不过如果 PATHEXT 包含 `.Exe` 这样的混合大小写，`toLowerCase()` 可以确保匹配。这不是 bug，但代码意图不清晰。

### Bug 7: `useApi` 的 10 秒默认超时对长任务过短
**文件**: `apps/web/src/lib/useApi.ts:14`
**问题**: 默认 10 秒超时可能在服务器负载高时导致请求失败。特别是 `saveAgent` 等操作可能需要更长时间。
**修复**: 对不同的 API 调用使用不同的超时时间，或者将默认超时增加到 30 秒。

### Bug 8: `loadWorkspaces()` 在每次 `get()` 调用时都重新加载
**文件**: `apps/server/src/managers/WorkspaceManager.ts:17-19`
**问题**: `get(id)` 方法每次调用都从磁盘加载所有 workspace。在高频请求场景下（如 SSE 心跳期间），这会造成不必要的 I/O 开销。
**修复**: 添加内存缓存，或者使用 `Map` 存储已加载的 workspace。

### Bug 9: `WorkspaceManager.create()` 不验证 rootPath
**文件**: `apps/server/src/managers/WorkspaceManager.ts:21-43`
**问题**: `create()` 方法不验证 `rootPath` 是否为有效路径（如不存在的父目录、权限问题等）。虽然 `initializeWorkspaceDirectory` 会创建目录，但如果路径无效（如包含非法字符），操作会失败。
**修复**: 在创建前验证路径有效性。

### Bug 10: `updateExecution` 的 `startedAt` 使用 COALESCE 导致无法更新
**文件**: `apps/server/src/store/SqliteStore.ts:346-360`
**问题**: SQL 中 `started_at = COALESCE(?, started_at)` 意味着一旦 `startedAt` 被设置，后续的更新不会改变它。如果执行状态需要回退（如重试），`startedAt` 不会被重置。
**修复**: 如果需要支持重试，应该直接赋值而不是使用 COALESCE。

### Bug 11: `sendGroupMessage` 串行执行 worker agents
**文件**: `apps/server/src/services/ConversationService.ts:136-146`
**问题**: Worker agents 使用 `await` 在循环中串行执行。如果群聊有多个 worker，总执行时间是所有 worker 执行时间之和。这可能导致超时。
**修复**: 考虑使用 `Promise.all` 并行执行独立的 worker（如果它们之间没有依赖关系）。

## Medium Bugs (建议修复)

### Bug 12: `child.kill('SIGKILL')` 在 Windows 上不生效
**文件**: `packages/agent-core/src/executor.ts:309`
**问题**: `SIGKILL` 信号在 Windows 上不被支持。虽然 `child.kill()` 在 Windows 上会调用 `TerminateProcess`，但 `SIGKILL` 参数会被忽略。这不会导致错误，但行为不一致。
**修复**: 在 Windows 上跳过 `SIGKILL` 调用，或者使用 `taskkill /PID` 命令。

### Bug 13: 诊断日志文件无限增长
**文件**: `packages/agent-core/src/executor.ts:65-73`
**问题**: `executor.log` 文件会无限增长，没有日志轮转机制。长时间运行后可能耗尽磁盘空间。
**修复**: 添加日志轮转机制（如按大小或时间分割）。

### Bug 14: `useApi` 的 AbortController 外部无法取消
**文件**: `apps/web/src/lib/useApi.ts:13`
**问题**: `request` 函数内部创建 `AbortController`，但不暴露给调用者。如果需要在组件卸载时取消请求，无法做到。
**修复**: 返回一个包含 `abort` 方法的对象，或者接受外部 `AbortSignal`。

### Bug 15: `resolveCommand` 在 `which`/`where` 不可用时的回退逻辑可能失败
**文件**: `packages/agent-core/src/resolveCommand.ts:49-61`
**问题**: 如果 `which` 或 `where` 命令不存在（如在某些容器环境中），回退的 PATH 扫描可能找不到命令，因为 PATH 环境变量可能为空或格式不正确。
**修复**: 确保回退逻辑在 PATH 为空时能正确处理。

### Bug 16: `isCodexCli` 在 `executor.ts` 和 `conversationRunner.ts` 中重复定义
**文件**: `packages/agent-core/src/executor.ts:32-33` 和 `packages/agent-core/src/conversationRunner.ts:109-111`
**问题**: 相同的正则表达式在两个文件中定义，违反 DRY 原则。
**修复**: 提取到共享工具函数。

### Bug 17: `ConversationService.sendDirectMessage` 中的 `execution` 可能为 null
**文件**: `apps/server/src/services/ConversationService.ts:103-106`
**问题**: `this.store.listExecutions(...)` 返回的数组中查找 `execution.id`，如果没有找到（理论上不应该发生），会抛出 "Execution was not persisted" 错误。但这个检查是在异步操作之后，如果数据库有并发问题，可能会失败。
**修复**: 在 `createExecution` 后立即验证，或者使用事务确保一致性。

### Bug 18: `getWorkerEvidenceFailure` 过于严格
**文件**: `apps/server/src/routes/taskPipeline.ts:4-8`
**问题**: 要求 worker 输出同时包含 "Checks Run"、"Findings by Severity" 和 "Evidence" 三个部分。如果 worker 只产出了其中两个部分，任务就会失败。
**修复**: 放宽条件，或者根据任务类型动态调整要求。

## Low Bugs (可以修复)

### Bug 19: `defaultPermissions` 中 kimi 缺少 `review` 权限
**文件**: `apps/server/src/store/SqliteStore.ts:614`
**问题**: `kimi` 角色只有 `['read', 'write']` 权限，没有 `review`。这意味着 kimi 不能执行审查操作。这是设计意图还是遗漏？
**修复**: 确认是否需要为 kimi 添加 `review` 权限。

### Bug 20: `buildPreviousOutput` 对非 final 阶段只显示最后一个日志
**文件**: `packages/agent-core/src/prompts.ts:106-108`
**问题**: 对于 `kimi_worker`，只显示 `codex_manager` 的最后一个日志。如果 codex_manager 产出了多个日志，后续的日志会被丢弃。
**修复**: 确认这是设计意图（保持上下文简洁）还是 bug。

### Bug 21: `handleSend` 中 `selectedConversation` 可能过时
**文件**: `apps/web/src/app/workspace/[id]/page.tsx:130-191`
**问题**: `handleSend` 回调依赖 `selectedConversation`，但在发送过程中如果用户切换了会话，回调可能使用旧的会话。虽然 `sending` 为 true 时会禁用发送按钮，但状态可能不一致。
**修复**: 使用 ref 存储最新的 conversation，或者在发送前重新获取。

### Bug 22: `createGroupConversation` 的 `members` 验证可能遗漏
**文件**: `apps/server/src/routes/conversations.ts:59-78`
**问题**: 虽然验证了 `uniqueIds.includes(leaderAgentId)`，但没有验证 leader agent 是否在 `profiles` 中。如果 leader 被禁用，`profiles.get(leaderAgentId)` 会返回 undefined，导致 `roleTitle` 为 undefined。
**修复**: 在构建 `members` 数组前验证 leader agent 存在。
